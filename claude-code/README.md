# 長任務輔助技能（Claude Code 版）

來源規格：<https://github.com/jie9029420000303/long-task-support-instructions>（`SPEC.md` 為共用行為契約；本資料夾是其 `claude-code/` adapter 的實作）。

## 結構

```
.claude/
├── skills/long-task-supervisor/     研究對話承接、執行 session 建立、事件監看及獨立驗收
├── skills/long-task-orchestrator/
│   ├── SKILL.md                    技能本體：觸發、A／B／C 分工、路徑枚舉閘、C 研究線、模型／effort 鎖定、驗收與三次錯誤規則
│   ├── references/spec.md          共用規格逐字複本（不得在此改共同語意）
│   ├── references/execution.md     Claude Code 執行協定：狀態檔、派工、前台案例、續接／壓縮／cloud
│   ├── references/behavioral-cases.md  共同行為案例 + Claude Code 驗證對照
│   ├── templates/state.md          狀態檔範本（cp 後填寫）
│   ├── templates/state.example.md  實跑一輪後的完整範例
│   ├── scripts/screenshot.js       無頭截圖落檔工具（子代理把證據存成 PNG 給主線 Read）
│   ├── scripts/pixel-diff.js       長頁像素比對：每版截各寬度完整長頁，換版時與前一版逐像素比對，證明受影響範圍外沒變
│   ├── scripts/scope-overlap.py    並行派工閘：比對工作區／可修改範圍／實際共用資源，有交集 exit 1、缺段 exit 2
│   └── scripts/sidecar-guard.py    狀態檔容量與逐條驗收守門（只報告不改寫）
└── agents/                         十二個子代理定義（4 角色 × 3 個 effort 檔）
    ├── lt-visual-checker-{medium,high,xhigh}.md   A 線視覺查核（唯讀＋瀏覽器）
    ├── lt-tech-worker-{medium,high,xhigh}.md      B 線技術實作（可編輯，git 寫入被 hook 擋）
    ├── lt-researcher-{medium,high,xhigh}.md       C 線分面研究（唯讀＋WebFetch／WebSearch／瀏覽器；只能把來源快照存進 evidence/）
    └── lt-ui-tester-{low,medium,high}.md          介面真實操作蒐證（唯讀＋瀏覽器）
```

## 安裝

- 全域（所有專案）：把 `.claude/skills/long-task-supervisor/` 和 `.claude/skills/long-task-orchestrator/` 複製到 `~/.claude/skills/`，`.claude/agents/lt-*.md` 複製到 `~/.claude/agents/`。
- 單一專案／cloud session：把上述兩個目錄提交進該 repo 的 `.claude/`（cloud session 看不到 `~/.claude/`）。
- 後續新 session 會載入已安裝的技能與子代理；既有 session 更新技能後需重新呼叫 Skill，新增子代理定義須開新 session。
- 狀態面板（建議）：把 `plugins/lt-status/` 複製到 `~/.claude/plugins-local/lt-status/`，在 `~/.claude/settings.json` 的 `env` 加 `"CLAUDE_CODE_PLUGIN_DIRS": "<家目錄>/.claude/plugins-local/lt-status"`。設定只在對話啟動時讀取，之後新開的對話才有面板。面板只顯示監看狀態，不替監督打字。

## 使用

1. 先在 Claude Desktop Code 原對話研究並定案，再說「依剛才定案內容啟動長任務監督」。原對話保留作監督入口；技能準備帶唯一標記的執行 prompt。沒有桌面原生建對話工具時，在 App 新開 Code 對話並送出該 prompt，保留完整可見的執行紀錄和隨時插話能力。不得用背景 CLI session 當執行主線。
2. 執行對話使用 `long-task-orchestrator`，建立 `.claude/long-task/<日期>-<slug>/state.md`，完成工作並送候選版給監督。監督以桌面原生跨對話傳訊退件或代答；背景工具讀取新完成回合與派工快照，發現漏派、未收回成果、資源衝突或返工才通知監督查證並引導補派；相同問題去重。桌面通知須真實喚醒模型才算成功；App 在記憶體壓力下會暫停閒置對話，監督因此整場另掛保持載入指令（`claude-hold.cjs`），見監督 runtime。監督逐條接受才算整體完成。
3. 若只想使用單對話長任務，仍可說「啟動長任務：<目標>」或 `/long-task-orchestrator <目標>`；`/goal` 只由使用者視需要自行設定。監督中斷後先查原 run 狀態並對帳續接，不另開一輪相同任務。

## 工作區隔離與狀態檔容量守門（2026-09-23，對應 Codex 09536d4）

對應 SPEC 不變量 12 與 tests 17／18：工作區（worktree／整體測試）也是共用資源；多個 B 技術包並行改程式時，主線預設為每包建立綁定同一 base 的隔離 worktree，成果在主線整合進單一候選版並跑完整回歸前只是草稿；否定宣告（不使用／不安裝）不算占用。Claude Code 的落地方式：

- 工作包必填 `[工作區]`（`path:` 絕對路徑、`worktree:` 唯一識別值、`base:` commit／SHA-256）；`scope-overlap.py` 相同 path 或 worktree 判交集、相同 base 可並行，舊工作包缺段 exit 2。只讀或只寫 evidence 的包以自己的 evidence 目錄當工作區，避免 A／C／介面包因共用 canonical 路徑被誤擋。
- worktree 由主線 `git worktree add` 預建（登記「主線自做」），不用 Agent 的 `isolation: "worktree"`：它的路徑派工前不存在、無法先過閘。子代理 hook 照擋 `git worktree` 等寫入；`lt-tech-worker-*` 只在 `[工作區] path` 內讀寫與測試。
- 路徑解析改成以空白與標點切出完整 token（根因：舊 regex 的目錄段不收「.」且沒有結尾邊界），保留 Claude 既有的無目錄檔名、行內註記與 `app/(group)/` 支援。
- 新增 `sidecar-guard.py`（Codex 版同門檻；工作包列與批次列改按節計數，因 Claude 狀態檔的 id 是 `B-1` 形式）。

## 執行期資源收尾（2026-09-30）

對應 SPEC 不變量 27 與 tests 27。起因是 2026-09-30 一台 16GB 的機器變得很慢：記憶體需求 39.8GB、swap 用掉 97%、負載 21（10 核心）。逐一追查每個常駐程序與容器的來源後，發現已結束長任務留下的東西佔了大宗：

- **容器**：一個 Codex 全端長任務的各批候選版環境留下 50 個容器，佔 Docker CPU 的 95%；停掉之後，Docker 虛擬機的 CPU 從約 1.7 核降到 0.6 核。
- **dev server 與預覽**：Rillet 前一波工作包 ui-w1 的 next dev 與 vitest，在該波判定後又活了 10.5 小時（1.4GB）；預覽 server 活了 22–30 天。預覽配方規定要寫 pid 檔，實際一個都沒有。
- **等待迴圈**：6 個手寫的等待迴圈沒有逾時，空轉了 12–23 小時。其中一個用 `grep "[p]ytest"` 等 pytest 結束，但它自己的指令裡就有 pytest 這個字，所以永遠等不完。

根因：並行派工閘只問「現在誰在用這個資源」，從來沒有一步問「誰開的、誰負責關」。第 3 條的「主線自做」只登記起了服務，第 21 條要求等待要設逾時，但這兩條都只靠模型自律，沒有程式檢查。

- 還掛在 session 底下的背景程序（父程序不是 1）不在未登記掃描範圍內。它們會隨 session 結束，但 session 可能開好幾天；這部分靠 `wait` 必填逾時來約束，手寫迴圈仍然只靠規則文字。
- `path:` 路徑中含有空白時解析不到。TTL 只作用於由 `start` 啟動的程序，容器沒有 TTL。
- Linux 沒有 launchd 可以排除，systemd 服務也沒有做排除，本輪沒有在 Linux 上實測。
- 還沒有在真實長任務上跑完一整輪：需要新 session 載入新技能後，觀察主線是否照規則登記與收尾。Codex App 的背景行為也只測了腳本本身。
- `workflow/` 流程圖尚未加入收尾步驟。

已知限制：Browser pane 截圖只存在子代理的對話中，主線看不到；要讓主線目視，子代理需用 `scripts/screenshot.js` 落檔（agent 定義已寫明）。 套件安裝被 hook 一律擋下（含工作包授權的情況）——真需要安裝由主線自己做。Browser pane／playwright MCP／chrome-devtools MCP 各是 session 級共用瀏覽器，同一工具同時只能有一個介面代理。使用者自己的全域 PreToolUse hook 訊息（分支確認提示）會被子代理讀到並當作可疑注入回報，無害但會多一段文字。

- **新增 `scripts/pixel-diff.js`**（兩邊編排技能各一份、內容相同）：`capture` 用無頭瀏覽器每種寬度截一張完整長頁（固定 1 倍縮放、動畫直接跑到結束、等字型與圖片載入，同一版截兩次完全相同），並記下各區段位置；`compare` 逐像素比對、門檻為零，判成完全相同、只在受影響範圍內、範圍外也有差異或缺寬度，頁高改變時從上下各自對齊找出變動段，輸出報告與標色差異圖。工具只證明沒變，有差異的區塊仍由視覺查核子代理親眼看。
- **視覺查核子代理**：三個 `lt-visual-checker` 定義加入沿用核對的做法，回報格式新增「沿用核對」；Codex 側寫在編排技能對視覺查核包的回報要求。
- **契約優先**：契約明定執行端每一關都要同 commit 完整重驗、由主線做完整回歸或要求連續次數時照原要求，使用者另行授權後才改用新預設。
- **行為案例**：共同案例 7 改為「換版只重驗受影響與連帶範圍，不同候選版的證據不得未經沿用核對就拼接成 PASS；最終放行由獨立驗收者對最終候選版分功能段落全套驗收」，兩邊同步；新增像素比對工具測試（兩邊內容一致、同版重截相同、範圍內／外判定、頁高改變、遮罩、橫向溢出、缺寬度、長頁分段接合）。

依 GDB Website System（2026-10-15～16）的實測：開工約 25 小時、扣掉使用者暫停約 19 小時，真正閒置只約 2 小時，時間花在驗收量與排隊。共截約 4,640 張圖，Gate 2 兩版各整套重拍 1,335 與 1,009 張；瀏覽器控制只有 1 個名額，子代理的 Chrome 改不了寬度，Gate 3 視覺查核包 39 項卡住、真實操作全落回主線；Gate 3 一次修一個點，12:08～14:58 連續 9 輪；7 個效能量測與診斷包各自寫了量測或診斷程式，共 35 支。執行端已經用 `pixel-diff.js` 截長頁，卻只拿來比對，正式截圖又用瀏覽器控制重拍一次，還自己寫包裝程式逐頁呼叫。使用者 2026-10-16 核准：「未來有牽涉到視覺設計的任務都可以導入，不然真的太久太久太久了」。共用語意新增 SPEC 不變量 28 與共同案例 43～45，Codex 同步。

- **開工先測瀏覽器能力**：第一個視覺工作包前，主線與每個要用瀏覽器的子代理在契約各寬度實測寬度套用、非空白截圖與一次真實點擊鍵盤，結果記進狀態檔；做不到的一方改派，不等工具恢復。
- **靜態截圖與真實操作分兩條路**：各寬度首屏與完整長頁、內容長度壓力、與基準對照用 `pixel-diff.js capture-batch` 一次截完，這批就是正式的靜態畫面證據與下一版的比對基準，由查核子代理親眼判讀；各包用自己的無頭瀏覽器，可並行。Browser pane 等互動瀏覽器只跑真實事件的互動驗收，同一頁的互動一趟走完。契約明文指定截圖用的瀏覽器時照契約。
- **每關先掃完、再一次修**：第一次查核先掃完全部頁面、寬度、內容狀態與互動案例，收成一張缺陷清單才派修；分組依據加上「同一元件、同一份樣式來源或同一設計變數，跨寬度與內容長度合併」。原本只按「同一情境」分組，同一個 FAQ 元件的三種內容長度被拆成三輪。監督看到同一關逐點派修時，請執行端先掃完。

- **`pixel-diff.js` 新增批次模式**（兩邊內容相同）：`capture-batch <清單.json> <根目錄>` 只開一次瀏覽器截完清單上每一頁、每種寬度，某頁失敗照樣截完其他頁；`--top` 另存首屏；`compare-batch` 依頁名逐頁比對，受影響元件只套用在找得到它的頁，只在一邊有的頁判整頁重驗。
