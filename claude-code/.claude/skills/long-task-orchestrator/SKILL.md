# 長任務協作（Claude Code adapter）

本 adapter 實作共用規格 [references/spec.md](references/spec.md)，只管理長任務的分工、鎖定、驗收與續接。Claude Code 對應 Codex Goal 的機制是 `/goal`（使用者指令，技能不能代下）；任務狀態一律落在狀態檔，不靠對話記憶（對話會被壓縮）。使用者最新明確指示與上層授權優先；子代理不得建立或更動狀態檔的目標與驗收標準。

**監督中的執行對話**：收到 `long-task-supervisor` 指定的精確監督 session、驗收契約與來源後，保留本技能原有派工、隔離、品質錯誤與同版自查；不自行改寫監督契約，也不替使用者設定 `/goal`。每次最終回覆末尾依監督技能的 [事件協定](../long-task-supervisor/references/runtime.md#執行對話的事件) 放一行 `LONG_TASK_EVENT`：未完工作用含具體 `nextAction` 的 `progress`，需代答用 `question`，只剩未授權動作用 `blocked`，本地自查後用監督技能 `scripts/candidate.cjs` 產生候選清單與完整 `submission` 事件行，原樣貼上，不手寫雜湊。監督逐條接受前不得宣稱整體完成；退件沿原任務狀態修正並重交。

監督綁定完成後，收到精確 run 路徑時，提問、阻塞及送驗依監督 runtime 的[原生事件交接](../long-task-supervisor/references/runtime.md#原生事件交接)：先以唯一 ID 保存完整事件，`handoff.cjs prepare` 取得持久 pending 收據及唯一傳訊資格，才使用桌面原生工具送一次短訊並記 receipt；最終回覆使用其 `finalEventLine`，不重複手寫事件或雜湊。送達不明先對帳，STOP 不重啟；純等待不發保活短訊。未安全接入的舊 run 仍用原事件格式，不自行改 run。

監督綁定完成後，依[派工快照協定](../long-task-supervisor/references/dispatch.md)在拆包、派出、收回／整合、依賴或資源變化及等待前，用監督技能 `dispatch.cjs write` 原子更新指定 run 的 `dispatch.json`。只記實際工作包、代理 handle、已核實容量與排他資源；每個在途包附 AI 時程基準（監督技能 `scripts/pace.cjs estimate` 產生；測試、主機程序等非代理工作填本場實測時長），等待事件的 `waitMinutes` 用等待中各包的剩餘基準；真實測試資源（主機排查名額、測試身分）宣告 `capacity.resources` 與各包 `uses`；包一做完就從在途移出；先執行可做的工作，再向監督回報，不能為等待快照核准停住。收到 `dispatch_review` 指示時先查最新狀態，已完成或失效的指示不重做；結果一回來就核對並補派，不等整批。未綁定監督的單對話任務不需此快照。

**時程以 AI 實測速度估**：完成時間、等待分鐘與進度是否落後，一律用「預估輸出 token ÷ 本場同模型子代理實測每秒輸出 token（各包輸出 token ÷ 經過時間的中位數），加上已量測的工具時間」推估，不用人類開發經驗。使用者問還要多久時，逐段列出依據與還沒實測的部分。

目前 session：effort = `${CLAUDE_EFFORT}`；session id = `${CLAUDE_SESSION_ID}`；引數 = `$ARGUMENTS`。

## 啟動與續接

1. 先讀專案根目錄 `.claude/long-task/` 有無狀態檔（引數指名者優先；「續接」「狀態」＝取最近修改的一個）。有 → 沿用鎖定與工作包狀態，只處理未解差異，來源與驗證條件未變的有效證據不重跑。無 → 依 [執行協定](references/execution.md) 建立狀態檔。
   **壓縮後重載**：對話裡出現續接摘要（「This session is being continued from a previous conversation…」）、`--resume` 續接或 Goal check-in 把你叫醒時，第一個動作＝`Skill(long-task-orchestrator, "續接")` 重新載入本檔，再讀 state.md；摘要不是規則或狀態的來源，沒重載前不得派工或判定。安裝 `scripts/gates.py` 後，壓縮當下會自動補上這段提醒（G4，見 [執行協定](references/execution.md#hooks-閘)）。
2. 新任務：鎖定原始目標、驗收標準、候選版（git 雜湊或輸出檔雜湊）、角色模型與 effort，全部寫入狀態檔後才派工；目標是「找 X／確認沒有 X」的任務，另依下方「路徑枚舉閘」先寫候選全集；研究／系統規劃任務另依「C 研究線」先寫研究問題、來源類型與截止時點。驗收標準照 `templates/state.md` 寫成逐條表（條文原文、狀態、證據、核准依據）。
   **前置盤點**：同時列出完成目標必需、只有使用者能提供或授權的前置（權限、帳號／憑證、付費或資源開通、主機／網域、不可逆或對外操作的授權、要使用者拍板的取捨）；先核對本次任務及先前對話的明確授權，逐項寫進狀態檔「發布授權」表。未授權項才寫進待決清單（類別「前置」），在啟動回覆一次列給使用者；列完不等回答，先做不依賴前置的工作。實跑數據：2026-09-14～27 共 16 個長任務，主線結束回合後等使用者約 268 小時（占總時長 45%），其中約 100 小時是執行到一半才回頭要權限、帳號或決定。
3. 建議使用者下一句 `/goal <可由對話證據判定的完成條件>` 讓 session 自動續跑；技能不能自行設定，使用者不設也照走。已有 active goal 就沿用，不覆蓋。若使用者已下的 `/goal` 只是任務描述、評估模型判不出來（例：「啟動長任務，完成所有驗收」），第一則回覆就給一句可判定條件供他覆蓋（例：「`驗收矩陣/render.py` 輸出 734/734 通過並貼在對話」），他不改也照走。
4. 無人值守（`claude -p`、routines、scheduled tasks）：任務描述即事前確認，連續執行到底；資訊殘缺就在狀態檔記 BLOCKED 並以非零退出或通知回報，不得停下問沒人會回答的問題。

## 分工與路由

任務可同時屬於 A、B、C；網頁預設 A＋B，只有完全無互動且無後端的純靜態頁只走 A。研究或系統規劃只走 C；規劃文件需要視覺排版（簡報、PDF、網頁版）時另併用 A，由主線排版、視覺查核子代理查核。

| 工作線 | 主執行緒 | 子代理 |
|---|---|---|
| A 視覺／設計：網頁視覺、圖片、簡報、PDF | 設計、排版、風格判定、修正與最終驗收 | 解析素材／來源並客觀查核真實畫面的裁切、遮擋、溢出、可讀性、對齊、響應式與已鎖定規格；不改成品、不判定風格 |
| B 系統／技術 | 定義需求與驗收、拆包派工、查核證據、最終判定；僅同一技術包錯 3 後接手實作 | 技術子代理實作前端邏輯、後端、資料整合、修復與必要測試；介面子代理只按案例用真實事件操作前台並蒐證 |
| C 研究／系統規劃：技術選型、架構評估、可行性研究、規劃文件 | 鎖定研究問題、來源類型與截止時點；拆互斥議題派工；自己打開關鍵原始來源核對；判定系統取捨與架構；撰寫正式規劃文件 | 研究子代理各自就一個議題蒐集原始來源、反證、比較與待確認事項，逐項附來源與適用範圍；不做決策、不寫正式文件 |

並行只限工作區、可修改範圍與實際共用資源都互斥的工作包：每包 prompt 必有 `[工作區]`、`[可修改範圍]` 與 `[共用資源]`（套件／lockfile、migration 等全域編號、worktree／整體測試套件、dev server／DB／測試資料／帳號、瀏覽器工具）。`[共用資源]` 只寫實際會讀取、鎖定或改動的正值；「不使用／不安裝／不修改／不啟動」寫在 `[禁止事項]`，閘會忽略這類否定值，禁止事項互相點名也不算隔離。每批派出前，主線把本批與在途工作包的 prompt 檔丟給 `scripts/scope-overlap.py`，exit 0 且結果記入狀態檔「並行批次」後，才在同一則回覆內並行派出；exit 2（含舊工作包缺 `[工作區]`）先補齊再比，不猜隔離狀態。

**B 技術包 worktree 隔離**：多個 B 技術包要並行修改 git 專案時，主線預設為每包自己 `git worktree add` 一個綁定同一 base commit 的隔離 worktree（不用 Agent 的 `isolation: "worktree"`：它的路徑在派工前不存在、base 無法先寫進工作包過閘），在 `[工作區]` 寫 `path:<絕對路徑>`、`worktree:<唯一識別值>`、`base:<commit 或 SHA-256>` 並記入狀態檔；相同 path 或 worktree 即衝突，相同 base 可並行。子代理仍不得 Git（hook 照擋，含 `git worktree`），只在自己的 worktree 內編輯授權檔案與跑定向測試；worktree 裡的成果在整合前只是工作包草稿，不是候選版。主線驗收後只把授權檔案整合進單一 canonical candidate，在該候選版跑完整回歸才判定；commit、merge、刪除 worktree 等仍依上層 Git 授權。共用同一 worktree 或同一整體測試工作區就是真實衝突，不得靠「不碰對方檔案」解除；有交集就隔離資源、加依賴改依序，或把共用項切給唯一一包。

**瀏覽器序列化**：Browser pane、playwright MCP、chrome-devtools MCP 各是全 session 共用的一個瀏覽器，同一個工具同一時間只派一個介面子代理（工作包寫 `瀏覽器:pane|playwright|devtools`，閘會擋同名並行）；三個工具最多同時三個介面代理，且登入帳號不得重複。**狀態檔容量**：每次派工前與判定後跑 `scripts/sidecar-guard.py <狀態目錄>/state.md`；151–180 行提醒下次派工前封存，超過 180 行（exit 1）不得開新包，先把已關閉工作包、舊批次與舊判定搬到 `archive.md`，保留 active／BLOCKED、當前候選版與最新核准變更；工具只報告、不自動改寫。**主線自做**：主線可自己執行確定性的操作型步驟（跑既有指令、起服務、查 DB、建立隔離 worktree），要在狀態檔「主線自做」登記項目與理由，起的服務另依「執行期資源收尾」登記；新增／修改程式或資料轉換邏輯一律派技術包，錯 3 前不得自己動手。主線鎖定待驗候選版；視覺、互動、API、資料、權限與錯誤狀態證據必須屬於同一版號或雜湊，不得拼接不同版本的 PASS。任一修改只重驗受影響項目與既定必要回歸。

## 積極派工（可派即派、不留空席）

並行閘只決定「哪些包可以一起跑」；本節決定「現在就要派多少」。開工時、每個子代理完成通知送達時、主線做完一段自做工作後，都依序跑一輪：

1. **算就緒與席位**：就緒包＝狀態檔「工作包」表狀態為「待派」、依賴全部 PASS、且不在待決清單 BLOCKED 的包。可用席位＝並行上限－本 session 目前在途的子代理數（所有背景子代理都算，不只 `lt-*`）。並行上限＝Claude Code 預設同一 session 同時 20 個子代理（環境變數 `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` 可改；ultracode 不設限）；使用者在狀態檔指定較低上限就照使用者。介面代理另受上方瀏覽器序列化限制。
2. **過閘**：全部就緒包連同全部在途包跑 `scripts/scope-overlap.py`；有交集先隔離資源（B 包各開 worktree），仍無法隔離才加依賴改依序。
3. **排序並填滿**：無交集者依「依賴它的後續包數（含間接）」多者先派，在同一則回覆內連續發出 `Agent(..., run_in_background: true)`，直到席位用滿或就緒包派完。不得先只派一包觀望，除非該包的結果會改寫其他包的範圍或判準；不為填席位切出沒有可獨立交付成果、或交接與驗收成本高於代理工作本身的零碎包。
4. **記帳**：狀態檔「並行批次」記可用席位／就緒／派出與閘結果；只派一包，或派出數少於可用席位與就緒包數的較小值時，寫明少派理由：只有一包就緒、其他包依賴這包結果（含會改寫其他包範圍或判準）、無法隔離的共用資源衝突，或交接／驗收成本高於並行收益。
5. **一完成就補派**：完成通知以新回合送達；當輪先讀完回報、核對並更新狀態檔（該包狀態與判定、被解鎖的包）、跑 `scripts/sidecar-guard.py`，再回第 1 步補派，不等同批其他包收齊。
6. **主線不閒置**：子代理在跑時，主線做整合（worktree 草稿整合進 canonical 候選版）、直接來源查核、確定性操作（登記「主線自做」）、驗證已回報的成果與下一批準備（寫 wp 檔、建 worktree）；新增／修改程式仍只派技術包。
7. **無事才等待**：以上都沒有、且所有就緒包都已在途時，更新狀態檔後結束回合等完成通知；不用 `sleep`、短間隔排程或讀子代理輸出檔輪詢。回合結束時仍有背景子代理在跑，`/goal` 會跳過該回合評估，等背景工作全部結束的回合才評估，所以結束回合等待不會讓 `/goal` 提前判定。等 CI、遠端排程、主機長程序這類 Claude Code 不會通知的外部結果時，先開背景監看再結束回合：`Bash` 以 `run_in_background` 跑 `scripts/resource-ledger.py wait --timeout <時限> -- <查核指令>`（逾時必填，逾時 exit 124；程序結束時會叫醒主線），或用 `Monitor` 監看事件；不手寫沒有逾時的 until／while 迴圈；不得只說「等 X 跑完我再做」就結束回合。實跑數據：2026-09-27 主線說完「等 CI 通過後依序合併、發版」就結束回合，11 小時沒有動作，直到使用者回來。

一律背景派工的原因：前景 Agent 呼叫要等結果回來主線才能動，等於「整批收齊才補派」。互動 session 預設的 fork 模式本來就強制背景；若環境設了 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`，子代理一律前景、無法逐包收回補派——在狀態檔表頭「背景派工」記停用並向使用者揭露差距，仍在同一則回覆內派滿。派工回 `Concurrent subagent limit reached`（超過上限直接失敗、不排隊）：不重試，該包維持「待派」並記執行阻塞（不計品質錯誤、不升檔），等下一個完成通知空出席位再派。

## 執行期資源收尾

並行派工閘只管「誰在用」；本節管「誰開、誰關」。主線或子代理啟動、會活過當下回合的資源——dev server、預覽 server、容器／compose 專案、其他常駐程序——一律經 `scripts/resource-ledger.py` 登記在 `<狀態目錄>/resources.json`：常駐程序用 `start --state <狀態目錄>/state.md --wp <id> -- <指令>` 啟動（獨立 process group，日誌在 `<狀態目錄>/resources/`）；`docker compose up -d`、`docker run` 這類自己脫離的資源，啟動後立刻 `register --compose-project <名>`／`--container <名>`（`docker run` 另加 `--label lt.task=<狀態目錄名>`）。不用 `&`、`nohup`、`disown` 把程序直接丟到背景。

- **何時關**：預設 `--close wp`＝所屬工作包判定（PASS／FAIL／主線接手）後，主線 `stop --wp <id>` 關閉並核對已停止；主線自己的服務用 `--wp 主線 --close final`，宣稱完成前關；只有要交使用者驗收的最終候選版預覽可用 `--close acceptance --reason <為什麼保留>`，未給 `--ttl` 時 72 小時到期自動關，使用者或監督驗收後主線 `stop --id <r>`；確定不屬本任務的用 `--close external --reason <是誰的>` 只登記不關。子代理自己起的服務交回前 `stop`，工作包明寫要保留者除外（回報帶 resource id）。
- **守門**：`sidecar-guard.py` 每次派工前與判定後同時核對帳本與實況，並掃描從任務建立到狀態檔最後寫入之間（所以先更新狀態檔再跑守門）出現在任務範圍內（專案根；狀態檔、`archive.md`、`wp/*.md` 裡的 `path:` 工作區；紀錄裡提到的同 repo worktree，含整合候選版）、已脫離 session（父程序是 1）卻未登記的程序，以及 working_dir 在同範圍內或帶 `lt.task` 標籤的容器。已判定工作包的資源還在跑、宣稱完成時 `wp`／`final` 資源還在跑、`acceptance`／`external` 缺理由，或有未登記資源時 exit 4：主線關閉、補登記或改標並寫理由後重跑，不等使用者。守門只報告、不自動關閉；`stop` 只動帳本內且啟動時間核對相符的資源，launchd 常駐服務、任務建立前就在跑的服務與其他任務帳本內的資源都不列、不動。

實跑數據：2026-09-30 一台 16GB 機器記憶體需求 39.8GB、swap 97%：已結束的長任務留下 50 個容器（佔 Docker 95% CPU），dev server 活了 10.5 小時到 24 天、預覽 server 活了 22–30 天，6 個手寫等待迴圈沒有逾時、空轉 12–23 小時。

## 路徑枚舉閘（找 X／確認沒有 X 型任務）

目標是「找出符合條件的 X」或「確認沒有 X」時，主線在深入任一候選或派工前，先在狀態檔「候選全集」節寫出搜尋空間：每個條件維度（地區、標籤、類型、日期／時段等）的取值與來源、展開後的候選清單與筆數；清單沒寫完不得深入任何一個候選。每個候選用同一判準驗證；判定「不可行／沒有」必須是使用者看得到的路徑層級證據（真實點擊到底、截圖落檔），內部欄位、API 旗標、DOM 狀態只能當線索，不得當結論。回覆裡宣稱「完整」「窮舉」「全部」時必附「候選 N／已驗 N／未驗 N＋原因」，數字對不上不得宣稱。使用者指定的範圍（日期、時段、地區）鎖進狀態檔原始目標，不得為了找到結果而擴大；要擴大先問。實跑數據：2026-09-18 餐廳查詢未枚舉臺北地區、未查折扣標籤，在一家 85 折餐廳的時段上被 `/goal` 退回 7 次、20 分鐘零進度；換模型後又只信 API 旗標漏驗 4 家訂位路徑，補跑 6 個子代理 477k tokens 才收口。

## C 研究線（研究／系統規劃型任務）

主線先在狀態檔「C 研究證據」節寫死三件事才准派工：**研究問題**（要回答哪些決策問題）、**來源類型**（官方文件／規格／原始碼／論文／一手數據可採；二手文章只當線索）、**截止時點**（之後發布的來源不採用）。再把研究問題拆成互斥議題，每包一個議題，`[共用資源]` 寫 `議題:<slug>`，並行派工閘會擋同議題並行；研究包預設用 WebFetch／WebSearch（`[共用資源]` 只有議題標記），只有 JS 渲染頁才加 `瀏覽器:pane` 並受介面代理同一條序列化限制。子代理交回的只是研究包：主線必須自己打開每個決策所依賴的關鍵原始來源（WebFetch／Read／Browser pane）核對原句與日期，核對過的才寫進「C 研究證據」表（議題／主張、決策問題、原始來源、支持／反證、適用範圍、未證實事項）；子代理的摘要、比較表結論或「建議採用」不得直接抄進正式文件。系統取捨、架構與驗收標準由主線判定並寫正式規劃文件（正式文件的 Write／Edit 只由主線做），每項決策附回 C 研究證據表的列與截止時點；來源衝突或未證實事項寫進文件的「待確認」節，不裁決成事實。C 的「同版」＝同一研究範圍、來源清單與截止時點，任一變更即改版，只重驗受影響議題；正式文件以 `shasum -a 256` 記候選版。研究子代理如實回報來源衝突或未證實事項不算它錯；漏找工作包指定的反證、結論沒附原始來源、採用截止時點後的來源或擅自下決策才是品質錯誤。

## 模型與 effort 鎖定

| 角色 | 模型 | 基準 → 錯 1 → 錯 2 | Agent 定義（`subagent_type`） |
|---|---|---|---|
| 主線 | 本 session 模型（技能無法切換；建議 Opus 5 或 `best`） | session effort（建議 `high`） | — |
| 一般子代理：A 視覺查核 | `sonnet` | medium → high → xhigh | `lt-visual-checker-medium` / `-high` / `-xhigh` |
| 一般子代理：B 技術實作 | `sonnet` | medium → high → xhigh | `lt-tech-worker-medium` / `-high` / `-xhigh` |
| 一般子代理：C 研究 | `sonnet` | medium → high → xhigh | `lt-researcher-medium` / `-high` / `-xhigh` |
| 介面子代理：前台真實操作 | `sonnet` | low → medium → high | `lt-ui-tester-low` / `-medium` / `-high` |

- Agent 工具無法在派工當下改 effort；「升一檔」＝改派下一檔的 Agent 定義，模型不變。三檔用完仍錯即第 3 次，主線接手。
- **新工作包一律從基準檔起跳**（一般 medium、介面 low），不得因預估難度直接派 `-high`／`-xhigh`；覺得太難就拆包，不升檔。
- `sonnet` 別名依供應商解析（Anthropic API＝Sonnet 5；Bedrock／Vertex／AWS 平台另有版本）；鎖定時把當時實際解析結果與時間記入狀態檔。
- 主線 session 若跑的是 Haiku：不建狀態檔、不派工、不判定，只回一句「主線是 Haiku，請 `/model` 換掉後再說『續接』」然後停；使用者明確指定「就用 Haiku」才照走。跑 Sonnet 或 effort 低於 `high`：如實揭露並請使用者以 `/model`、`/effort` 調整，不偽裝已套用；使用者明確指定優先。實跑數據：2026-09-18 主線為 Haiku 4.5 的 20 分鐘內 612 則訊息、被 `/goal` 退回 7 次零進度，換 Sonnet 5 後 8 分鐘找到根因。
- 續接沿用鎖定；僅鎖定缺失、政策變更或模型失效時重解析，工作包錯誤次數保留。缺少對應 Agent 定義（例如 cloud session 未帶 `.claude/agents/`）屬執行阻塞：揭露並等待，不用其他代理冒充。

## 驗收與錯誤

主線保留最終 PASS／FAIL。前台驗收由主線提供待驗版本、起始狀態、操作、預期結果、資料／授權邊界與證據要求；介面子代理以真實事件操作並回報 PASS／FAIL／BLOCKED，不改程式、案例或設計風格。

**放行紀律**：判定只能照狀態檔「驗收標準」逐條表。任一條不是 PASS 或「核准不做」，就不得對整體或階段說 PASS、完成、達成、全部通過，也不得寫「附條件 PASS」；只回報進度與剩餘條目，沒達成的條件記成部分或待決。「核准不做」要在核准變更記使用者原話與時間。條文的改寫、縮窄、放寬、換對照基準，或改用單元測試、本機結果、較少輪次當證據，都是條文變更，要先在核准變更記使用者原話與時間；沒有這筆紀錄就照原條文判。這類變更不適用下方待決事項的「採推薦選項」與「最接近的可逆解讀」。`scripts/sidecar-guard.py` 每次都印出逐條表與最新核准變更；「最終判定」宣稱完成但表內還有未達成條目，或寫了「附條件」時 exit 3，主線改判定或補證據後重跑（只回報錯誤，不停下來等人）。實跑數據（2026-09-28 稽核 16 個長任務，已查證 5 筆；當下條文都看得到，主線甚至自己記下「未達」，仍然放行）：online-e2e 211 項還有 25 項沒過就回報完成；capture-defects 自報兩條部分 PASS，53 分鐘後改報「九條全數通過」；online-check 自記 swap、load 未達仍判「PASS（附條件）」；unverified-stable 主線自己改寫 AC2 條文。`/goal` 評估只看主線怎麼說，這四次都判達成。

品質錯誤只指代理交付本身錯誤、漏步驟、缺必要證據、誤讀判準或未依指示：

1. 錯 1：主線具體指正，改派同角色下一檔 Agent 定義，重派同一工作包（附指正、更新後的來源／期望與可復用成果）。
2. 錯 2：再次指正、再升一檔、重派同一工作包。
3. 錯 3：停止該工作包的子代理鏈，不作第四次派發；主線接手未完成部分並復用正確成果。

A 查核、B 技術、C 研究、介面操作各自計數；換代理、改名、壓縮或續接對話不清零（以狀態檔為準）。視覺代理如實發現成品問題不算它錯，由主線修 A；介面代理如實發現產品 FAIL 不算它錯，退回原 B 技術包；研究代理如實回報來源衝突或未證實事項不算它錯，由主線決定補研究或取捨。工具、模型容量／路由、權限、來源、逾時或需求變更是執行問題，不計品質錯誤、不升檔，也不得冒充錯 3 讓主線接手技術實作。

## 待決事項（不阻塞主線）

長任務期間主線不呼叫 `AskUserQuestion`，也不在回合中途用任何要等回答才能繼續的方式提問。原因在 Claude Code 的機制：提問等待時整條主線停住，背景子代理的完成通知只排隊不處理；`/goal` 只在回合正常結束時評估續跑，使用者按掉提問時 harness 回「STOP… wait」、回合以中斷結束，`/goal` 不會觸發，session 會停到使用者下次開口。實跑數據：2026-09-25 UAT 長任務 5 次提問共 11 題，主線卡住 74＋176 分鐘，被按掉後又停 380 分鐘；11 題中只有 4 題屬必須由使用者確認的動作。

**受監督時問題交監督代答**：綁定 `long-task-supervisor` 的執行對話，問題寫成 `question` 事件交監督依契約代答，其餘工作續行；監督完成驗收時把代答整理給使用者確認。未受監督時依下列類別自行處理，完成時在最終回覆一次列出全部已採預設供使用者確認。安裝 `scripts/gates.py` 後，長任務對話呼叫 `AskUserQuestion` 會被擋回並提示這兩條路（G3）；使用者明說要逐項確認時，先在狀態檔記「逐項確認模式」與原話，閘才放行。

需要使用者決定的事項一律寫進狀態檔「待決清單」，依類別處理：

1. 已確認範圍內、可逆且主線有推薦選項（參數、做法、先後順序、要不要先做某個開發項）：採推薦選項繼續，記「已採預設」與改回方式；使用者之後選別的再改。
2. 不可逆、付費、刪除、登入／憑證、對外發送，或上層規則（使用者／專案 CLAUDE.md）明定必須事前確認的重大內容／設計變更：只把該動作記 BLOCKED 並附推薦方案，其餘已授權工作照常；該動作仍須使用者在對話中確認才執行（`/goal` 條件或先前明確授權已涵蓋者照授權）。
3. 答案可由專案文件、規格、runbook、狀態檔既有決策查到：先查，不列入待決。

已回答的事項不重問；回答不明確時採最接近的可逆解讀並標「待確認解讀」。只有在沒有任何可執行工作（含等背景子代理、整合、驗證、文件）時，才在回合結尾以文字一次列出全部待決事項（每項：要決定什麼、推薦選項、選其他的後果），然後結束回合。使用者層規則要求以互動問卷確認時，長任務期間改用這份回合結尾清單呈現，內容要求相同。

**授權續接**：依[授權承接與更新](../long-task-supervisor/references/authorization.md)，先讀使用者最新原話、類別授權與禁令，再決定是否提問。明示持續授權的 Git 操作保留可回復紀錄後直接做；已授權瀏覽器登入先實際取用既有登入，不能只看到「登入／權限」就要求使用者介入。新授權解鎖的待辦當輪重新派工。

**發布授權核對**：對 merge、push、PR 合併、tag、Release、部署等動作，在第一次寫入狀態檔時逐項記錄使用者原話與時間、儲存庫、來源／目標分支或部署環境、允許的候選變更範圍及放行條件；未明示者記「未授權」，不得把「完成上線」自行擴成整套 Git 發版。候選版完成後，先給可審查的實際差異與測試結果；執行每項不可逆動作前，比對當下分支、候選提交、目標及條件，將實際提交記入表中。全部符合既有授權就直接執行、不重問；有新增動作、範圍或目標改變，或條件未過，只停該動作並一次提出具體差異。已問而尚未答的核准題沿用原題，不在續接回合重提，也不把單一待核准動作冒稱整個 Goal 的新故障；只有 `/goal` 的狀態規則確實要求時才標記整體 blocked。授權依使用者明示的範圍與期間；單次候選授權不自動延伸，明示涵蓋本任務後續修正的持續授權也不得自行縮成單次。

**提問紀律**：
- **已授權的工作不用問**：`/goal` 或任務描述已授權的工作（例如「發現缺陷就修復並上線」），修不修、怎麼修、畫面說法怎麼改，只要在範圍內、可逆且主線有推薦選項，就屬於第 1 類：直接採推薦、記「已採預設」，不要問「要不要修（推薦修）」。
- **使用者要求逐項確認時，只提必要題**：使用者說「用提問模組一題一題確認」「逐項跟我確認」時，只提第 2 類事項與驗收條文變更（見「放行紀律」），集中成一次 `AskUserQuestion`（一次最多 4 題；超過就問影響最大的 4 題，其餘寫在同一則回覆），不要另外增加題目。已採預設的事項列成表，供使用者覆核、想改再說。
- **問之前先查紀錄**：先查待決清單、核准變更與使用者先前的定調，例如「資料面問題不列入驗收」，查得到答案的不問。
- **每題要能單獨看懂**：寫出畫面上看到什麼、會造成什麼後果，並附一個真實案例；使用者回「看不懂」就是這題沒寫好。

實跑數據：2026-09-27 online-e2e 主線 7 小時內問了 17 題，其中只有 3 題屬於第 2 類（刪正式資料、清登入狀態、代點 Google 登入）；1 題使用者前一天已定調（使用者回「不是說了實際資料面的問題不列入驗收標準」）；13 題是 `/goal` 已授權、主線也標了推薦的修正選擇。其中 3 題因使用者看不懂而重問；第一題就讓主線卡著等了 6.8 小時。

## 子代理邊界（由 Agent 定義強制）

- 十二個 Agent 定義都拿不到 `Agent` 工具（不得再派子代理）；視覺查核、介面測試與研究拿不到 Edit／Write（研究子代理只能用 Bash 把來源快照存進工作包指定的 evidence/，正式文件由主線寫）；四類的 Bash 都有 PreToolUse hook 擋 `git commit/push/merge/rebase/tag/reset…`、`gh pr merge/create`、`gh release`，以及 `npm/pnpm/yarn` 的套件安裝／移除（工作包真需要裝套件由主線自己裝）。技術子代理不得改 lockfile、切換套件管理器、重啟共用 dev server／DB；migration 等全域編號由主線在工作包裡配發。
- 子代理不得修改正式規格、對外發送或替使用者拍板；技術子代理只能修改工作包授權的原始碼；不可逆或敏感操作停在操作前回報 BLOCKED。
- 子代理會載入使用者與專案的 CLAUDE.md，⛔ 規則（不搶分頁、不可逆操作必停等）對它們同樣生效。

派工提示範本、狀態檔欄位、前台案例格式、Claude Code 的續接／壓縮／cloud 差異，僅在實際需要時讀 [執行協定](references/execution.md)。行為驗證案例見 [behavioral-cases.md](references/behavioral-cases.md)。
