# 長任務協作（Claude Code adapter）

本 adapter 實作共用規格 [references/spec.md](references/spec.md)，只管理長任務的分工、鎖定、驗收與續接。Claude Code 對應 Codex Goal 的機制是 `/goal`（使用者指令，技能不能代下）；任務狀態一律落在狀態檔，不靠對話記憶（對話會被壓縮）。使用者最新明確指示與上層授權優先；子代理不得建立或更動狀態檔的目標與驗收標準。

目前 session：effort = `${CLAUDE_EFFORT}`；session id = `${CLAUDE_SESSION_ID}`；引數 = `$ARGUMENTS`。

## 啟動與續接

1. 先讀專案根目錄 `.claude/long-task/` 有無狀態檔（引數指名者優先；「續接」「狀態」＝取最近修改的一個）。有 → 沿用鎖定與工作包狀態，只處理未解差異，來源與驗證條件未變的有效證據不重跑。無 → 依 [執行協定](references/execution.md) 建立狀態檔。
   **壓縮後重載**：對話裡出現續接摘要（「This session is being continued from a previous conversation…」）、`--resume` 續接或 Goal check-in 把你叫醒時，第一個動作＝`Skill(long-task-orchestrator, "續接")` 重新載入本檔，再讀 state.md；摘要不是規則或狀態的來源，沒重載前不得派工或判定。
2. 新任務：鎖定原始目標、驗收標準、候選版（git 雜湊或輸出檔雜湊）、角色模型與 effort，全部寫入狀態檔後才派工；目標是「找 X／確認沒有 X」的任務，另依下方「路徑枚舉閘」先寫候選全集；研究／系統規劃任務另依「C 研究線」先寫研究問題、來源類型與截止時點。
3. 建議使用者下一句 `/goal <可由對話證據判定的完成條件>` 讓 session 自動續跑；技能不能自行設定，使用者不設也照走。已有 active goal 就沿用，不覆蓋。若使用者已下的 `/goal` 只是任務描述、評估模型判不出來（例：「啟動長任務，完成所有驗收」），第一則回覆就給一句可判定條件供他覆蓋（例：「`驗收矩陣/render.py` 輸出 734/734 通過並貼在對話」），他不改也照走。
4. 無人值守（`claude -p`、routines、scheduled tasks）：任務描述即事前確認，連續執行到底；資訊殘缺就在狀態檔記 BLOCKED 並以非零退出或通知回報，不得停下問沒人會回答的問題。

## 分工與路由

任務可同時屬於 A、B、C；網頁預設 A＋B，只有完全無互動且無後端的純靜態頁只走 A。研究或系統規劃只走 C；規劃文件需要視覺排版（簡報、PDF、網頁版）時另併用 A，由主線排版、視覺查核子代理查核。

| 工作線 | 主執行緒 | 子代理 |
|---|---|---|
| A 視覺／設計：網頁視覺、圖片、簡報、PDF | 設計、排版、風格判定、修正與最終驗收 | 解析素材／來源並客觀查核真實畫面的裁切、遮擋、溢出、可讀性、對齊、響應式與已鎖定規格；不改成品、不判定風格 |
| B 系統／技術 | 定義需求與驗收、拆包派工、查核證據、最終判定；僅同一技術包錯 3 後接手實作 | 技術子代理實作前端邏輯、後端、資料整合、修復與必要測試；介面子代理只按案例用真實事件操作前台並蒐證 |
| C 研究／系統規劃：技術選型、架構評估、可行性研究、規劃文件 | 鎖定研究問題、來源類型與截止時點；拆互斥議題派工；自己打開關鍵原始來源核對；判定系統取捨與架構；撰寫正式規劃文件 | 研究子代理各自就一個議題蒐集原始來源、反證、比較與待確認事項，逐項附來源與適用範圍；不做決策、不寫正式文件 |

並行只限可修改範圍與共用資源都互斥的工作包：每包 prompt 必有 `[可修改範圍]` 與 `[共用資源]`（套件／lockfile、migration 等全域編號、dev server／DB／測試資料／帳號、瀏覽器工具）；每批派出前，主線把本批與在途工作包的 prompt 檔丟給 `scripts/scope-overlap.py`，exit 0 且結果記入狀態檔「並行批次」後，才在同一則回覆內並行派出；有交集就加依賴改依序或把共用項切給唯一一包，禁止事項互相點名不算隔離。**瀏覽器序列化**：Browser pane、playwright MCP、chrome-devtools MCP 各是全 session 共用的一個瀏覽器，同一個工具同一時間只派一個介面子代理（工作包寫 `瀏覽器:pane|playwright|devtools`，閘會擋同名並行）；三個工具最多同時三個介面代理，且登入帳號不得重複。**主線自做**：主線可自己執行確定性的操作型步驟（跑既有指令、起服務、查 DB），要在狀態檔「主線自做」登記項目與理由；新增／修改程式或資料轉換邏輯一律派技術包，錯 3 前不得自己動手。主線鎖定待驗候選版；視覺、互動、API、資料、權限與錯誤狀態證據必須屬於同一版號或雜湊，不得拼接不同版本的 PASS。任一修改只重驗受影響項目與既定必要回歸。

## 路徑枚舉閘（找 X／確認沒有 X 型任務）

目標是「找出符合條件的 X」或「確認沒有 X」時，主線在深入任一候選或派工前，先在狀態檔「候選全集」節寫出搜尋空間：每個條件維度（地區、標籤、類型、日期／時段等）的取值與來源、展開後的候選清單與筆數；清單沒寫完不得深入任何一個候選。每個候選用同一判準驗證；判定「不可行／沒有」必須是使用者看得到的路徑層級證據（真實點擊到底、截圖落檔），內部欄位、API 旗標、DOM 狀態只能當線索，不得當結論。回覆裡宣稱「完整」「窮舉」「全部」時必附「候選 N／已驗 N／未驗 N＋原因」，數字對不上不得宣稱。使用者指定的範圍（日期、時段、地區）鎖進狀態檔原始目標，不得為了找到結果而擴大；要擴大先問。實跑數據：2026-09-18 餐廳查詢未枚舉臺北地區、未查折扣標籤，在一家 85 折餐廳的時段上被 `/goal` 退回 7 次、20 分鐘零進度；換模型後又只信 API 旗標漏驗 4 家訂位路徑，補跑 6 個子代理 477k tokens 才收口。

## C 研究線（研究／系統規劃型任務）

主線先在狀態檔「C 研究證據」節寫死三件事才准派工：**研究問題**（要回答哪些決策問題）、**來源類型**（官方文件／規格／原始碼／論文／一手數據可採；二手文章只當線索）、**截止時點**（之後發布的來源不採用）。再把研究問題拆成互斥議題，每包一個議題，`[共用資源]` 寫 `議題:<slug>`，並行派工閘會擋同議題並行；研究包預設用 WebFetch／WebSearch（`[共用資源]` 只有議題標記），只有 JS 渲染頁才加 `瀏覽器:pane` 並受介面代理同一條序列化限制。子代理交回的只是研究包：主線必須自己打開每個決策所依賴的關鍵原始來源（WebFetch／Read／Browser pane）核對原句與日期，核對過的才寫進「C 研究證據」表（議題／主張、決策問題、原始來源、支持／反證、適用範圍、未證實事項）；子代理的摘要、比較表結論或「建議採用」不得直接抄進正式文件。系統取捨、架構與驗收標準由主線判定並寫正式規劃文件（正式文件的 Write／Edit 只由主線做），每項決策附回 C 研究證據表的列與截止時點；來源衝突或未證實事項寫進文件的「待確認」節，不裁決成事實。C 的「同版」＝同一研究範圍、來源清單與截止時點，任一變更即改版，只重驗受影響議題；正式文件以 `shasum -a 256` 記候選版。研究子代理如實回報來源衝突或未證實事項不算它錯；漏找工作包指定的反證、結論沒附原始來源、採用截止時點後的來源或擅自下決策才是品質錯誤。

## 模型與 effort 鎖定

| 角色 | 模型 | 基準 → 錯 1 → 錯 2 | Agent 定義（`subagent_type`） |
|---|---|---|---|
| 主線 | 本 session 模型（技能無法切換；建議 Opus 5 或 `best`） | session effort（建議 `high`） | — |
| 一般子代理：A 視覺查核 | `sonnet` | medium → high → xhigh | `lt-visual-checker-medium` / `-high` / `-xhigh` |
| 一般子代理：B 技術實作 | `sonnet` | medium → high → xhigh | `lt-tech-worker-medium` / `-high` / `-xhigh` |
| 一般子代理：C 研究 | `sonnet` | medium → high → xhigh | `lt-researcher-medium` / `-high` / `-xhigh` |
| 介面子代理：前台真實操作 | `sonnet` | low → medium → high | `lt-ui-tester-low` / `-medium` / `-high` |

- Agent 工具無法在派工當下改 effort；「升一檔」＝改派下一檔的 Agent 定義，模型不變。三檔用完仍錯即第 3 次，主線接手。
- **新工作包一律從基準檔起跳**（一般 medium、介面 low），不得因預估難度直接派 `-high`／`-xhigh`；覺得太難就拆包，不升檔。
- `sonnet` 別名依供應商解析（Anthropic API＝Sonnet 5；Bedrock／Vertex／AWS 平台另有版本）；鎖定時把當時實際解析結果與時間記入狀態檔。
- 主線 session 若跑的是 Haiku：不建狀態檔、不派工、不判定，只回一句「主線是 Haiku，請 `/model` 換掉後再說『續接』」然後停；使用者明確指定「就用 Haiku」才照走。跑 Sonnet 或 effort 低於 `high`：如實揭露並請使用者以 `/model`、`/effort` 調整，不偽裝已套用；使用者明確指定優先。實跑數據：2026-09-18 主線為 Haiku 4.5 的 20 分鐘內 612 則訊息、被 `/goal` 退回 7 次零進度，換 Sonnet 5 後 8 分鐘找到根因。
- 續接沿用鎖定；僅鎖定缺失、政策變更或模型失效時重解析，工作包錯誤次數保留。缺少對應 Agent 定義（例如 cloud session 未帶 `.claude/agents/`）屬執行阻塞：揭露並等待，不用其他代理冒充。

## 驗收與錯誤

主線保留最終 PASS／FAIL。前台驗收由主線提供待驗版本、起始狀態、操作、預期結果、資料／授權邊界與證據要求；介面子代理以真實事件操作並回報 PASS／FAIL／BLOCKED，不改程式、案例或設計風格。

品質錯誤只指代理交付本身錯誤、漏步驟、缺必要證據、誤讀判準或未依指示：

1. 錯 1：主線具體指正，改派同角色下一檔 Agent 定義，重派同一工作包（附指正、更新後的來源／期望與可復用成果）。
2. 錯 2：再次指正、再升一檔、重派同一工作包。
3. 錯 3：停止該工作包的子代理鏈，不作第四次派發；主線接手未完成部分並復用正確成果。

A 查核、B 技術、C 研究、介面操作各自計數；換代理、改名、壓縮或續接對話不清零（以狀態檔為準）。視覺代理如實發現成品問題不算它錯，由主線修 A；介面代理如實發現產品 FAIL 不算它錯，退回原 B 技術包；研究代理如實回報來源衝突或未證實事項不算它錯，由主線決定補研究或取捨。工具、模型容量／路由、權限、來源、逾時或需求變更是執行問題，不計品質錯誤、不升檔，也不得冒充錯 3 讓主線接手技術實作。

## 子代理邊界（由 Agent 定義強制）

- 十二個 Agent 定義都拿不到 `Agent` 工具（不得再派子代理）；視覺查核、介面測試與研究拿不到 Edit／Write（研究子代理只能用 Bash 把來源快照存進工作包指定的 evidence/，正式文件由主線寫）；四類的 Bash 都有 PreToolUse hook 擋 `git commit/push/merge/rebase/tag/reset…`、`gh pr merge/create`、`gh release`，以及 `npm/pnpm/yarn` 的套件安裝／移除（工作包真需要裝套件由主線自己裝）。技術子代理不得改 lockfile、切換套件管理器、重啟共用 dev server／DB；migration 等全域編號由主線在工作包裡配發。
- 子代理不得修改正式規格、對外發送或替使用者拍板；技術子代理只能修改工作包授權的原始碼；不可逆或敏感操作停在操作前回報 BLOCKED。
- 子代理會載入使用者與專案的 CLAUDE.md，⛔ 規則（不搶分頁、不可逆操作必停等）對它們同樣生效。

派工提示範本、狀態檔欄位、前台案例格式、Claude Code 的續接／壓縮／cloud 差異，僅在實際需要時讀 [執行協定](references/execution.md)。行為驗證案例見 [behavioral-cases.md](references/behavioral-cases.md)。
