# 長任務輔助指令：共用規格

此規格定義平台無關的行為；平台 adapter 只負責把角色、模型與工具映射至可用能力，不能改變本檔的不變量。

```text
任務啟動／續接 → 鎖定目標、候選版、角色配置 → 選 A／B／C 工作線
  A：主線設計與排版 → 子代理客觀視覺查核 ─┐
  B：子代理技術實作 → 必要時子代理真實前台操作 ─┼→ 主線同版整合查核 → 完成
  C：子代理分面研究 → 主線驗證、系統決策與正式規劃 ─┘
                                                   └→ 未達標：判定歸屬 → 重派／第三次主線接手
```

可互動流程圖：[長任務協作流程](https://github.com/jie9029420000303/long-task-support-instructions/blob/main/workflow/long-task-workflow.html)；可審閱原始規格：[workflow JSON](https://github.com/jie9029420000303/long-task-support-instructions/blob/main/workflow/long-task-workflow.json)。

## 不變量

1. 主線保存原始目標、核准變更、驗收、候選版、工作包狀態與最後 PASS／FAIL。
2. A 是視覺／設計工作：主線負責設計、排版、風格判定與修正；子代理只解析來源並客觀檢查裁切、遮擋、溢出、可讀性、對齊、響應式與既定規格，不改成品或判定風格。
3. B 是系統／技術工作：子代理實作前端邏輯、後端、資料整合、修復與必要測試；主線定義驗收、查核證據與最終判定。只有同一技術包累積三次品質錯誤，主線才接手未解實作。主線可自行執行確定性的操作型步驟（執行既有指令、啟動服務、查詢資料），但任何新增／修改程式或資料轉換邏輯的工作都派技術包；主線自做的步驟必須在任務狀態登記項目與理由。
4. C 是研究／系統規劃工作：子代理依可隔離的議題蒐集來源、反證、比較與待確認事項；主線定義研究問題、來源與時點邊界，核對關鍵原始證據，判定系統取捨、架構與驗收，並撰寫正式規劃文件。子代理不得以研究摘要代替主線決策，也不得修改正式文件；需視覺排版時另併用 A。
5. 網頁預設同走 A＋B；僅完全靜態、無互動、無後端的頁面只走 A。
6. 前台驗收由主線提供待驗版本、起始狀態、操作、預期結果、資料／授權邊界與證據要求；介面子代理以真實事件完成操作並回報 PASS、FAIL 或 BLOCKED。
7. 候選版的視覺、互動、API、資料、權限與錯誤狀態須有有效證據才可合併為 PASS；C 的結論須可回溯至同一研究範圍、來源清單與截止時點。換版保存實際變更與影響對照，執行端只重驗受影響範圍、其連帶範圍及既定必要回歸，不整套重跑；未受影響項目的舊證據預設沿用、不必另取授權，但每筆都要記來源版本、未受影響的依據與核對紀錄（文件外觀頁依本條末段）。範圍由實際變更依成品類型往外追：畫面從改到的樣式與元件，追到用到它們的元件與頁面；程式、API、資料、權限與互動從改到的檔案與函式，沿引用與呼叫鏈追到使用者碰得到的入口（頁面、API、排程、指令），再對到驗收條文；研究從改到的來源、研究範圍或截止時點，追到引用它們的結論與段落，截止時點往後移時，有時效的事實（價格、版本、現況、排名、名單）全部列入，來源與時點都沒變的才沿用。改到共用基礎（設定與環境變數、資料庫結構、套件版本、登入與權限、共用函式、設計變數、全站樣式、共用版型）時，連帶範圍是用到它的每個功能段落，基礎全站共用時就是全站；判斷不出影響時，重驗該功能段落。自動化測試每版整套跑。有畫面的成品，受影響元件在契約要求的每種寬度重驗；每一版都用 `scripts/pixel-diff.js` 截各寬度完整長頁並保留，換版時與前一版同寬長頁逐像素比對，受影響範圍以外有差異就把該處併入重驗。最終放行（契約最後一關或整案送驗）由獨立驗收者對最終候選版分功能段落做一次全套驗收，這一次不得沿用：受監督時由監督做（不變量 24），未受監督時由主線派不帶開發過程上下文的子代理做；執行端不另跑全套人工回歸，交出影響清單、整套自動化測試結果與最終候選版各寬度完整長頁。契約明定執行端每一關都要同 commit 完整重驗、由主線做完整回歸或要求連續次數時照原要求，使用者另行授權後才改用本條預設。同一區的修正先湊齊，再跑一次完整測試：規劃時和每次收回成果時，主線把待做、待修項目依同一情境、同一段程式、同一條測試路徑分組；同組一起改，實作工作包只跑定向測試；主線把同組成果整合成單一候選版，該候選版只跑一輪完整測試（範圍即前述受影響範圍、連帶範圍、既定必要回歸與契約要求），通過才發版、部署、送驗。完整測試失敗時，先把這一輪的失敗全部歸因、修正湊齊再重跑，不修一項跑一次。同組新冒出的項目，該組還沒開測就併入，已開測就排進下一組。驗收條件要等定時工作（每日、每小時等排程）才跑得到時，開發測試期間不等正式排程，改在已授權的環境手動觸發該路徑取得證據；不刪除、不覆蓋正式環境既有資料（例如遠端已存在的備份集），需要時用強制參數或另一個目的地。文件類成品（說明文件與由它衍生的流程圖、簡報、影片；建構型程式工作不適用）先定唯一內容來源（完整說明 .md），其他形式只從它取材，不另寫新數字。事實表先行：開發驗收或部署完成、最後一次變更主機或設定之後，以一支腳本在同一時點讀出文件要用的數字、設定值、主機讀回與程式行號，表頭寫明讀取時間；之後又有變更就整批重讀，不拼接不同時點的值。.md 的數字與事實陳述都要對得回事實表；衍生件每頁與每句旁白在出處對照表記下取自 .md 的哪一段。執行端的文件檢查只用腳本（簡體字、連結、程式行號、數字與事實表及 .md 一致、保留清單、出處對照），不另派子代理預檢內容或外觀；獨立驗收只做一次，受監督時由監督做（不變量 24），未受監督時由主線派一個不帶開發過程上下文的子代理做。外觀逐頁查核只在整包做一次，之後只重查改到的頁，其餘頁以位元組或像素對照確認未變、留下核對紀錄後沿用原查核。文件開工時以本任務開發實測時間的 1.5 倍設文件時間預算並記入任務狀態，用掉一半與用完時各核對一次；用完仍未完成，向使用者回報現況與選項，不自行延長。
8. 品質錯誤只包括代理交付的錯誤實作、漏步驟、缺必要證據、誤讀判準或未依指示。產品 FAIL、工具／權限／模型／來源／逾時問題與需求變更不計品質錯誤。
9. 每個工作包與工作線分開計數。第 1、2 次品質錯誤：主線具體指正，並在平台支援時提高同一代理的推理投入後重派。第 3 次：停止該包子代理鏈，由主線接手；不得無限重派。新工作包一律從該角色的基準投入起跳，不得因預估難度預先提高；覺得太難就拆包，不升檔。
10. 平台 adapter 在每個新長任務首次需要角色時，依可用且可驗證的能力鎖定主線、一般子代理與介面子代理的模型／投入；續接沿用鎖定。使用者明確指定優先，能力不支援時如實揭露，不偽裝為已套用。
11. 子代理不得自行修改正式規格、進行未授權的不可逆或敏感操作、未授權的對外發送，或替使用者做決策；未經工作包明列授權，不得安裝／移除套件、更動 lockfile 或套件管理器、重啟或重建共用服務、刪除不是自己在本工作包建立的測試中間產物（列明者仍依不變量 16 的保留範圍），也不得自行選用 migration 等全域編號（由主線配發）。子代理可刪自己在本工作包建立、位於工作區或自己暫存目錄內的檔案（證據與測試結果除外），並在回報列出，由主線記入刪除清冊。
12. 並行只允許可修改範圍與共用資源都互斥的工作包：同一批並行派出的工作包之間、以及與任何在途工作包之間，可修改的檔案／元件、資料表與全域編號、套件與 lockfile、共用服務（開發伺服器、資料庫、測試資料、帳號）、瀏覽器不得有交集。每個工作包必須宣告會觸碰的共用資源；主線每批派出前逐項比對並把結果記入任務狀態；有交集者改為依序（加依賴）或把共用項切給唯一一包。同一個瀏覽器工具或登入狀態同一時間只能由一個介面子代理使用；並行介面測試必須各自使用隔離的瀏覽器。只在禁止事項互相點名、範圍仍重疊，不算隔離。工作區也是共用資源：同一個工作目錄（Git worktree 或非 Git 的工作資料夾）與在其中執行的整體測試，不得由兩個並行工作包共用；多個技術包要並行修改程式時，主線預設為每包建立綁定同一基底版本的隔離工作區，並在工作包與任務狀態記錄其絕對路徑、唯一識別值與基底版本；缺少工作區宣告的工作包不得進入並行比對，也不得猜測其隔離狀態。子代理不得操作版本控制；隔離工作區的成果在主線核對並只把授權檔案整合進單一候選版、跑完整回歸之前只是草稿，不得作為候選版證據。共用資源只宣告實際會讀取、鎖定或改動的項目；「不使用／不安裝／不修改」屬禁止事項，不構成占用，也不能作為隔離證據。
13. 上下文被壓縮、續接或恢復後，主線必須先重新載入本規格的 adapter 技能與任務狀態，才可再派工或判定；自動產生的對話摘要不是規則或狀態的來源。
14. 目標為「找出符合條件的 X」或「確認沒有 X」時，主線在深入任一候選或派工前，先在任務狀態枚舉搜尋空間：每個條件維度的取值與來源、展開後的候選清單與筆數。每個候選以同一判準驗證；「不可行／沒有」只能以使用者可見路徑層級的證據（真實操作到底）判定，內部欄位、API 旗標、DOM 狀態只作線索。宣稱完整、窮舉或全部時必附候選、已驗、未驗計數與未驗原因，數字不符不得宣稱。使用者指定的範圍（日期、時段、地區等）不得為了得到結果而自行擴大。
15. 平台 adapter 判定主線模型低於該平台定義的最低能力時，不建立任務狀態、不派工、不判定，只揭露差距並等待使用者切換；使用者明確指定沿用者除外。
16. 長任務執行中，主線與監看中的監督都不得以會停住自己回合的方式向使用者提問（例如須等回答才能繼續的互動提問工具）；監督的回合一停，執行端的提問、送驗與背景監看事件都喚不醒它。需要使用者決定的事項依類別處理：在已確認範圍內、可逆且主線已有推薦選項者，採推薦選項繼續，並在任務狀態的待決清單記下已採選項與改回方式；不可逆、付費、刪除、登入／憑證、對外發送，或上層規則明定必須事前確認的重大內容／設計變更，只把該單一動作記為 BLOCKED 並附推薦方案，其餘已授權工作照常進行；先核對既有授權，已涵蓋且平台允許預先授權者直接做，其餘才須取得使用者確認。長任務屬開發或測試階段、最終只驗交付成果，所以本任務自己產生的測試中間產物（暫存容器與資料卷、測試票與測試紀錄、草稿與暫存檔、已被取代的中間輸出，以及變更已整合進候選版或確定不採用、刪前已把狀態與差異存進證據且不再作證據的隔離工作區）預設已授權在必要時刪除，不列待決；有封存、結案、中和等可逆做法能滿足需要時，刪除就不算必要。刪前記入刪除清冊並寫明其識別值在驗收結果帳、證據與決策帳的搜尋結果，刪後讀回確認。還原與排查最終結果所需的歷程（決策帳、驗收證據、測試結果、產物與刪除清冊、版本控制歷史），以及識別值出現在驗收結果帳、證據或決策帳中的測試物件，一律不刪；非本任務產生的資料仍屬前述刪除類。使用者原話點名特定資源或資料、或明說涵蓋測試中間產物的刪除禁令優先；「不准刪東西」「只准依需求新增」「刪除須逐項確認」這類泛用禁令只保護本任務未建立的既有資源與資料；之後改同一限制時以新原話為準。答案可由專案文件、規格、操作手冊或既有決策查得者，先查不問；使用者已回答的問題不得重問，回答不明確時採最接近的可逆解讀並記入待決清單。只有在沒有任何可執行工作時，主線才在回合結尾一次列出全部待決事項、推薦選項與後果後停下。受監督時，需要使用者決定的事由監督的待決帳承接：待決帳放在 run 目錄、由程式維護，不靠對話記憶，只收前述須確認的類別、驗收條文變更、推翻使用者禁令與須使用者本人操作者，其餘由監督依授權自行決定；監督每次喚醒讀取的內容都附完整未決與已結清單；新問題先與清單比對，同一件事更新原項，已回答或已撤下者除非記明改變題目的新事實不再提問；監督提問時一次列完全部未決項（含先前已列而未答者），不挑子集、不分批，沒有變動不重列；提問時機為使用者在線，或執行端除這些事項外已無其他可做工作。使用者的回答要登記成授權或驗收修訂（不變量 24）時，以登記該修訂的同一步結案它回答的待決項，待決項記下修訂識別，不另以原話各自結案。任務描述或長任務完成條件已授權的工作（例如「發現缺陷就修復並上線」），其做法選擇若在已確認範圍內、可逆且主線有推薦選項，即屬前述可逆事項，不向使用者提問。使用者要求逐項確認待決事項時，只提出不可逆、付費、刪除、登入／憑證、對外發送、上層規則明定須事前確認的變更與驗收條文的變更，集中一次提出，不另增題目；已採預設的事項列成清單供使用者覆核。提問前先查任務狀態的待決清單與核准變更，已有答案或已定調的不再問；每個提問須能單獨看懂並附具體實例。

prompt。執行回合結束時送出進度與具體下一步、提問、阻塞或候選版事件；監督一次只處理一個事件，前一事件未決時再送來的提問、阻塞與候選版依送出先後持久排隊，不得丟棄、覆蓋或回報為執行端錯誤，決策後依序送出下一個，已被執行端後續回合取代的一般進度可不排隊；佇列裡有較新的候選版時不得接受目前候選版，先記為被該送驗取代再處理它；佇列只有提問或阻塞時驗收照常，監督讀到排隊事件原文，驗收時一併結案並列入給使用者的收尾清單；可續做的進度由背景程序短訊續接，停滯、提問、送驗、異常、意外結束及監督自己的進度時鐘才喚醒監督。監督的進度時鐘不以執行端宣告的等待為準，分層查核：先由程式確認工作有在動（執行對話、子代理、在跑的測試程序都算），再以派工快照的 AI 時程基準比對有無超過預期，每 30 分鐘留一筆查核紀錄；只有發現問題才喚醒模型分析並給推進指令——全部靜止 15 分鐘（從執行對話、子代理、測試程序與監督最後一次送出判定或決策中最晚者起算，執行端等監督判定的時間不算靜止）、在途工作包沒有基準或經過時間達基準 1.5 倍與 3 倍（同一基準在 1.5 倍與 3 倍各最多喚醒一次，不論該包是否仍有產出或仍有程序在跑；監督判斷它是否仍在跑、卡關、可否加速，或範圍已擴大須重估基準；已叫醒過的那一級，只有重估把該級的叫醒時點（開始時間加該倍數的基準）往後延到比先前叫醒過的都晚（範圍擴大或換新階段），才算新基準、重新起算，基準改小或只是重算數字不再叫醒；一包超時叫醒時，其他在途且已達基準 1.2 倍的包一併交監督分析，這些包的 1.5 倍那一級記為已叫醒，3 倍那一級照舊各自叫醒；為防預估時長報得過長使超時永不觸發，平台可在距上一次真正執行事件滿 1 小時時主動查核一次，新事件回來或監督裁決執行端事件時重新計時）、測試程序 15 分鐘沒有產出、同一失敗指令重複 3 次、同一下一步連報兩次。執行回合被平台錯誤中斷（平台以錯誤結束回合，例如限速、登入過期、連線失敗、伺服器錯誤）屬意外結束，執行端自己的紀錄出現新工作即視為已恢復。寫明重置時間的限速是已知等待，到重置時間或執行端已自行恢復為止：不換帳號，除非使用者已明示授權也不換模型（平台另有使用者授權的換模型路徑時依該路徑）；與監督共用額度且程式讀得到重置時間時，期間不叫醒監督，到重置時間仍未恢復才叫醒一次請執行端從中斷處接續；讀得到重置時間但程式無法自動等待時，叫醒一次由監督記下恢復時間等待，不回覆執行端、不請使用者處理。其他平台錯誤（含讀不到重置時間的限速）在執行對話 2 分鐘（扣掉電腦睡眠）仍未恢復時叫醒監督一次並附錯誤原文，監督先請執行端從中斷處接續，續接後同一錯誤再出現或錯誤本身須本人處理（例如重新登入）時，才告訴使用者要做的具體動作；子代理的非限速平台錯誤由執行端重派處理。執行端停在要本人處理的地方（例如權限確認）或電腦睡眠時，直接通知使用者；睡眠時間不算進工作包經過時間。真實測試資源（主機名額、測試身分）有空位，且有依賴已全部完成、可立即開跑的工作包在等時，提醒監督評估並行；同一資源的這組可派工作包沒變就不再提醒。監看期間監督對話必須一直喚得醒。保持載入：平台會暫停或卸載閒置對話時，adapter 要讓監督對話在監看程式交出事件的當下仍保持載入，優先用不呼叫模型的常駐程序；平台只認模型回合時，閒置期間至多定期送一則短回合。備援喚醒：平台允許時，只在事件久候未處理時補送一次短喚醒，不定時保活；和被喚醒的對話在同一程序裡的備援，只在該對話保持載入時有效，不能當作對抗暫停或卸載的手段。落後或重複時在授權範圍內給具體加速建議，進度正常只記錄、不傳訊。時程基準、等待時間與完成估計一律以 AI 實測速度推估：預估輸出 token ÷ 本場同模型實測每秒輸出 token，加上已量測的工具時間，不用人類開發經驗；執行端把基準寫進派工快照，同一工作包換新階段或範圍擴大時當下重估並寫入新基準，不沿用前一階段的基準；監督以同一公式重算覆核。剩餘時間只用派工快照中剩餘工作包的基準估算並寫明依據，沒有基準就標「未估」，不以每小時通過條數等通過率換算。訊息以唯一標記送出並讀回確認；送達不明先對帳，不盲目重送。背景程序或平台停止時，狀態不得假稱仍在即時監看；恢復時從已保存的游標、收件與決策續接；saved inflight 的延遲收件只讀對帳，不重送，STOP 與已完成仍優先。 對純確認或已登記在待決帳（不變量 16）的待核准事項，監督可記錄具體原因，靜默處理該事件後繼續接收新事件；不為了繼續監看傳送無必要回覆，也不把單一待核准動作變成停止監看。靜默處理不代表授權或驗收通過；使用者明確停止仍優先。15 分鐘查核核對後若只剩未變等待，可保存具體條件靜默監看；新授權／執行事件、條件檔或已有期限變動再查核，不反覆喚模型，也不停止接收。候選否決不自動撤回持續代判授權，重做依最新意圖判斷。
26. 放行界線：只有監督對原契約加有來源的使用者修訂形成的有效條文逐條作出有證據的 PASS，並通過同版決策檢查，才可回報整體完成。新的商業取捨、不可逆或其他未授權動作按上層確認規則處理；只擋該動作，其餘已授權工作續行。執行者回報完成只視為送驗，監督未放行前不可對使用者宣稱整體達標。
27. 執行期資源收尾：主線或子代理啟動、會在當下回合或工作包結束後繼續存活的執行期資源（開發伺服器、預覽伺服器、容器與 compose 專案、其他常駐程序），啟動時即登記於任務狀態的資源帳本：所屬工作包、可核對的識別（程序與其啟動時間、埠、容器或 compose 專案名）、啟動指令與工作目錄、關閉時點。關閉時點預設為所屬工作包判定之後；主線自用的服務在宣稱完成前關閉；只有要交使用者驗收的最終候選版預覽可保留至使用者驗收，須寫明理由並設到期自動關閉的期限；確定不屬本任務的資源只登記、不關閉，須寫明歸屬。等待迴圈與背景監看一律設逾時。工作包判定後，主線關閉該包的資源並核對確已停止。平台 adapter 須提供在每次派工前與判定後執行的檢查：以實際程序與容器狀態核對帳本，並掃描任務開始後出現在本任務工作區內、已脫離對話卻未登記的常駐程序與容器；已判定工作包的資源仍在執行、宣稱完成時仍有未保留的資源在執行、保留或歸屬缺理由，或有未登記資源時，回報錯誤交主線處理，不以等待使用者確認的方式阻塞。檢查只報告、不自動關閉；關閉只作用於帳本內且身分核對相符的資源，不屬本任務者（開機常駐服務、任務開始前已在執行的服務、其他任務登記的資源）不得關閉。
28. 畫面成品查核：成品有畫面（網頁、圖卡、簡報、PDF 等）時，第一個視覺工作包前，主線與每個要用瀏覽器的子代理先在契約的每種寬度實測寬度確實套用、截圖不是空白、能完成一次真實點擊與鍵盤操作，結果記入任務狀態；做不到的一方改派，不等工具恢復。第一次在任務中採用批次截圖時，以平台瀏覽器同版截圖抽查至少兩種寬度的代表頁，換行、標題行數、按鈕與元素位置一致才採用；顏色與對比以批次截圖判定，平台瀏覽器的截圖可能把高彩度顏色調淡。靜態畫面（各寬度首屏與完整長頁、內容長度壓力、與基準對照）由批次截圖腳本一次截完，這批截圖就是正式的靜態畫面證據與下一版的比對基準，由查核子代理親眼判讀；同一輪要看的圖超過 15 張時，預設按頁分給 2～3 個查核子代理並行判讀，同一頁的各寬度與內容狀態由同一個子代理看，只有一頁或只剩一個子代理名額時才由一個子代理看完；各子代理用自己的無頭瀏覽器。平台瀏覽器只用於真實事件的互動驗收，同一頁的互動合併成一趟走完。每關第一次查核先掃完全部頁面、寬度、內容狀態與互動案例，收成一張缺陷清單才派修，只有擋住掃描的缺陷先修；視覺缺陷依同一元件、同一份樣式來源或同一設計變數分組，跨寬度與內容長度合併，整合成一版後一次重驗。有效能門檻時，第一個效能包交出量測腳本與固定設定，之後每一版與每次診斷都重跑同一支；改設定須寫明理由，並以新設定重量前一版當基準。契約明文指定截圖用的瀏覽器或工具時照契約。

## 平台適配界線

- `codex/`、`claude-code/` 各自包含監督與執行兩個技能，並管理觸發方式、長任務機制、模型與推理控制、子代理工具、安裝位置及平台限制。
- Adapter 可加上平台特有的安全規則，不能放寬本規格。
- 如果平台不支援某項模型或子代理控制，adapter 必須採最接近且可驗證的替代方式，並揭露差距。
