# 執行協定（Claude Code）

只在建立狀態檔、派工、前台操作、模型解析、續接或驗收證據需要細節時讀本檔；核心分工與錯誤規則以 `SKILL.md` 與 `references/spec.md` 為準，不在此重述。

## 狀態檔

位置：`<專案根>/.claude/long-task/<YYYY-MM-DD>-<slug>/state.md`，證據放同目錄 `evidence/`。範本：`templates/state.md`（用 `cp` 複製後填寫）。不想進 git 就把 `.claude/long-task/` 加進 `.gitignore`（由使用者決定）。

保存：原始目標、最新核准變更、驗收標準（逐條表：條文原文、狀態 PASS／未達／部分／待決／核准不做、證據、核准依據；見 SKILL「放行紀律」）、候選全集（找 X／確認沒有 X 型任務：維度取值、清單、候選／已驗／未驗計數）、C 研究證據（研究／系統規劃任務：研究問題、來源類型、截止時點，以及主線核對過的議題／主張、決策問題、原始來源、支持／反證、適用範圍、未證實事項）、目前階段與停止點；模型／effort 鎖定（角色、`subagent_type`、當時解析到的實際模型、時間）；每個工作包的 id、類型、負責 Agent 定義、依賴、候選版號／雜湊、工作區（path／worktree／base）、狀態（待派／在途／PASS／FAIL／BLOCKED）、錯誤次數、目前 effort 檔、成果與證據位置；並行上限與背景派工是否可用（表頭）；每輪派工的可用席位／就緒／派出數、範圍比對結果與少派理由（「並行批次」節）；主線自做的步驟與理由（「主線自做」節）；需要使用者決定的事項與啟動時盤點的前置（「待決清單」節，類別含「前置」；處理方式見 SKILL「待決事項」與「前置盤點」）；PASS／FAIL 判定紀錄。

**快照不是日誌**：「目前階段」只寫一兩行；每個工作包收口（PASS／FAIL／主線接手）都在「判定紀錄」補一列；狀態改成 PASS 或關閉的工作包整列搬到同目錄 `archive.md`（保留 id 供追溯），讓 state.md 以 150 行為目標、派工前不得超過 180 行，每次派工前都讀得起；每次寫入都更新表頭「最後更新」。實跑數據：一份 58 KB 的 state.md 讓主線 38 小時只重讀 9 次。

**容量守門**：收到回報後先更新當前結果；每次派工前與判定後跑 `python3 <技能目錄>/scripts/sidecar-guard.py <狀態目錄>/state.md`。≤150 行 exit 0；151–180 行 exit 0 但提醒下次派工前封存；>180 行 exit 1，不開新包，先保留 active／BLOCKED 工作包、當前候選版、最新核准變更與未解差異，再把已關閉工作包、舊並行批次、舊判定與已取代的主線自做紀錄搬到 `archive.md`，重跑到 exit 0 才派工。工具每次也印出「驗收標準」逐條與最新一筆核准變更，讓主線每次派工前、判定後都重看條文原文（壓縮後 Claude Code 會附回技能快照，但狀態檔 2026-09-15～27 實測 15 次壓縮只附回 2 次）；「最終判定」宣稱 PASS／完成／達成但逐條仍有未達成條目，或寫了「附條件」時 exit 3，主線改寫最終判定或補證據後重跑，不得對使用者宣稱完成。舊格式（驗收標準是編號清單）照樣印出條文，只提示改用逐條表。工具只報告、不自動改寫；封存不得刪除或重寫歷史。

每次派工前、收到回報後、判定前都更新狀態檔；每次判定前先重讀（對話壓縮後尤其如此）。

候選版：git 專案用 `git rev-parse --short HEAD`（工作樹有未提交修改時加註 `+dirty` 與 `git diff --stat` 摘要）；非 git 專案用交付檔的 `shasum -a 256`。C 線的候選版＝正式規劃文件的 `shasum -a 256`，並在「C 研究證據」節記該版所依據的研究範圍、來源清單與截止時點；三者任一變更即改版，只重驗受影響議題，不同截止時點的來源不得拼成同一版結論。

## 模型解析（Claude Code）

- 主線：從本 session 的系統提示讀目前模型名，effort 用技能載入時顯示的 `${CLAUDE_EFFORT}`；技能不能切換主模型或 effort，只能揭露差距請使用者用 `/model`、`/effort`。
- 子代理：`sonnet` 別名，Anthropic API 解析為 Sonnet 5；Claude Platform on AWS 為 Sonnet 4.6；Bedrock／Google Cloud Agent Platform 為 Sonnet 4.5。鎖定時記角色、`subagent_type`、解析結果、時間。
- 升一檔＝改派同角色下一檔 Agent 定義（medium→high→xhigh；介面 low→medium→high），模型字串不變。不可為升檔換模型，也不可用相同 effort 冒充升檔。
- Agent 定義缺失（cloud session 沒帶 `.claude/agents/`、或使用者移除）、模型不可用、`sonnet` 解析到不支援 effort 的版本：記執行問題，揭露並等待，不靜默降級；模型重解析時保留工作包錯誤次數。

## 派工（Agent 工具）

- 每包 prompt 先存成 `<狀態目錄>/wp/<id>.md`（重派、續接都從檔案讀），再派工：`Agent(subagent_type="<定義名>", prompt="<工作包>", description="<3–5 字>", run_in_background=true)`。有依賴的等前包 PASS 才派；已就緒的依 SKILL「積極派工」在同一則回覆內派到席位用滿。
- **並行派工閘**：同一批要並行的包，連同所有在途包，先跑
  `python3 <技能目錄>/scripts/scope-overlap.py <狀態目錄>/wp/<本批>.md … --in-flight <狀態目錄>/wp/<在途>.md …`
  exit 0＝無交集，把輸出貼進狀態檔「並行批次」後才在同一則回覆內並行派出；exit 1＝列出交集項與涉及的包，B 技術包先改用隔離 worktree 與獨立測試資源，仍無法隔離才把後派的加依賴改依序或把共用項切給唯一一包（另一包 prompt 明寫「不改該項，需要時寫進回報待決」），改完重跑；exit 2＝prompt 檔缺 `[工作區]`、`[可修改範圍]` 或 `[共用資源]` 段，或 `[工作區]` 缺 path／worktree／base、path 不是絕對路徑、base 不是 commit／SHA-256——補上再跑，舊工作包不猜測隔離狀態。script 比對：`[工作區]` 的 path 與 worktree（相同即交集，base 相同可並行）＋路徑（以空白與標點切成完整 token，`.worktrees` 等含點目錄不截斷；含 `**`／`*` 前綴涵蓋與無目錄前綴的檔名）＋ `[共用資源]` 裡的 `鍵:值` 正值（同名即交集；`瀏覽器:playwright` 兩包同寫就擋，C 研究包的 `議題:<slug>` 同名也擋；`不使用`、`不安裝`、`無` 等否定值忽略）。
- **B 技術包 worktree 隔離**：多個 B 技術包要並行修改 git 專案時，主線在派工前自己跑 `git worktree add <repo>.worktrees/<wp-id> <base>`（同一批用同一個 base commit；非 git 專案複製出獨立資料夾並記交付檔 SHA-256），把 `path`／`worktree`／`base` 寫進 wp 檔 `[工作區]` 與狀態檔「工作包」表，登記在「主線自做」。`[可修改範圍]` 仍寫相對於 repo 根的路徑，讓兩包改同一檔在整合時會撞的情況照樣被閘擋下。子代理只在 `[工作區] path` 內讀寫與跑定向測試，仍不得 Git；它回報的 `git status --short`／`git diff --stat` 只是該 worktree 的草稿。主線收回後核對實際變更檔 ⊆ 授權範圍、base 未漂移、定向測試輸出，只把授權檔案整合進 canonical worktree 形成單一候選版，再在該候選版跑完整回歸後判定；草稿各自的 PASS 不得拼成候選版 PASS。commit、merge、cherry-pick 或對外操作仍依上層 Git 授權；變更已整合（或確定不採用）的 worktree 屬測試中間產物，依[測試中間產物的刪除](../../long-task-supervisor/references/authorization.md#測試中間產物的刪除)：要清時先把 `git status --short` 與 `git diff` 存進 evidence/、記入刪除清冊。只讀或只寫 evidence 的包（A 查核、介面操作、C 研究）以自己的 `<狀態目錄>/evidence/<id>` 絕對路徑當 `[工作區] path`、`worktree:evidence-<id>`、`base:` 寫待驗候選版的 commit／SHA-256。
- **介面代理序列化**：Browser pane、playwright MCP、chrome-devtools MCP 都是 session 級共用瀏覽器，cookies／登入狀態在同一工具的所有子代理間共享。同一工具同一時間只派一個介面代理；要並行就分配不同工具（最多三個）且登入帳號不重複。實跑數據：三個介面代理共用 playwright 造成互相干擾與一次全域登出，可歸因的重跑 5 批＝125 分鐘、1.39M tokens。
- 補問或補充同一檔次的資訊：`SendMessage(to="<agent 名或 id>")` 續用同一子代理（保留它的上下文）。重派（升檔）一律新開 Agent，prompt 附上主線指正、更新後的來源／期望與可復用成果，不把整段對話貼進去。
- 子代理一律背景跑（互動 session 預設的 fork 模式本來就強制背景）；完成通知以新回合送達，一到就依 SKILL「積極派工」第 5 步收回、更新狀態檔並補派。回合結束時仍有子代理或背景 shell 在跑，`/goal` 跳過該回合評估，等背景工作全部結束的回合才評估；背景工作讓 goal 等滿 30 分鐘會插入 check-in（之後間隔加倍），屆時讀輸出、還在進展就繼續等、卡住的就停掉並診斷，不放置。
- 平台事實（2026-09-27 查 Claude Code 官方文件 sub-agents、goal 兩頁）：同一 session 預設最多 20 個子代理同時在跑，`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` 可改、ultracode 不設限；超過時 Agent 呼叫直接回 `Concurrent subagent limit reached` 並要求不重試（不排隊），在跑數降到上限以下才能再派；`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 讓所有子代理改前景。上限數字寫進狀態檔表頭「並行上限」，改用環境變數或使用者指定值時一併記來源。
- 每包只負責一類工作，prompt 至少包含：

```
[工作包] id、類型（A 查核／B 技術／C 研究／介面操作）、依賴、目前錯誤次數與本次 effort 檔
[狀態] 一行 JSON，是這包狀態的唯一紀錄：新建 {"list":"ready"}；派出 {"list":"inFlight","handle":"agent:<id>","baseline":{…}}；收回 {"list":"returned","resultEvidence":["<回報檔>"]}；核對完 {"list":"completed"}；受阻 {"list":"blocked","kind":"…"}；不再是當前工作 {"list":"archived"}。受監督時用 `dispatch.cjs mark` 改，同一指令重產派工快照
[驗收條目] 這包推進的驗收條件 ID（受監督時成為快照的 acceptanceIds）；沒有就省略
[候選版] 版號／雜湊、來源路徑或 URL
[工作區] 每行一個：path:<絕對路徑>、worktree:<唯一識別值>、base:<commit 或 SHA-256>
[問題] 要做什麼、精確範圍
[判準] 客觀可核對的 PASS 條件（實作包只寫定向測試；完整測試由主線整合同組成果後跑一次）
[可修改範圍] 檔案／目錄清單（相對於 repo 根）
[共用資源] 實際會讀取、鎖定或改動的正值：套件:安裝（預設不准）、migration:<主線配發的編號>、worktree:<id>、測試套件:<id>、服務:<port 或名稱>、DB:<名稱>、資料:<測試資料集>、帳號:<登入帳號>、瀏覽器:pane|playwright|devtools（介面包必填）、議題:<slug>（C 研究包必填）；沒有就寫「無」；「不使用／不安裝」寫進 [禁止事項]
[常駐資源] 本包會啟動、交回後還活著的 dev server／預覽／容器：一律 `resource-ledger.py start|register --wp <id>`（主線在本段寫明 `resource-ledger.py` 與狀態檔的絕對路徑）；交回前 `stop`，要留給後續包或使用者驗收時寫明理由並在回報列 resource id；沒有就寫「無」
[資料副作用] 本包要刪的、別人建立的測試中間產物逐項列明，主線派工前已記入刪除清冊；沒列的不刪（自己在本包建立、位於 [工作區] path 或自己暫存目錄內的檔案可刪並在回報列出）。授權依據：監督技能 authorization.md#測試中間產物的刪除，使用者 2026-10-13 原話
[禁止事項]；[隔離／還原方式]
[回報格式] 結論（PASS／FAIL／BLOCKED）、實際覆蓋、發現與影響、證據位置（evidence/ 下的檔名）、未查項目及原因
```

- **C 研究包**另加四段，缺一不派（`[問題]`＝研究議題、`[判準]`＝每項結論附原始來源且反證清單逐條有交代）：

```
[研究議題] 這一包只負責的單一議題（與同批其他包互斥；[共用資源] 寫 議題:<slug>）
[決策問題] 主線要靠這包回答的取捨問題原文（例：「同步用 CDC 還是批次？」），子代理回答事實不回答取捨
[來源與截止時點] 可採用的來源類型（官方文件／規格／原始碼／論文／一手數據；二手只當線索）、截止日期；之後發布的來源列未證實不採用
[必找反證] 主線已知或懷疑的反面主張清單，每條都要回「找到什麼」或「查過哪裡沒找到」
[可修改範圍] 只有 <狀態目錄>/evidence/<id>/**（來源快照；寫 ** 才受閘比對）；[工作區] path 寫 evidence/<id> 的絕對路徑、worktree:evidence-<id>、base:待驗正式文件或 repo 的 SHA-256／commit；[共用資源] 預設「議題:<slug>」，JS 渲染頁才加 瀏覽器:pane
[回報格式] 結論（DONE／PARTIAL／BLOCKED）、議題與決策問題複述、實際覆蓋（來源類型／數量／截止時點是否遵守）、發現（主張 → 原始來源 URL／路徑＋版本或日期＋擷取日期＋關鍵原句 → 支持／反證 → 適用範圍）、比較表（若要求）、未證實事項與來源衝突、證據位置、範圍外發現
```

  主線收到研究包後：①自己打開每個決策所依賴的關鍵原始來源（WebFetch／Read／Browser pane）核對原句與日期，②核對過的列寫進狀態檔「C 研究證據」表，③才寫正式規劃文件；子代理回報裡的取捨結論不抄進文件，來源衝突與未證實事項進文件「待確認」節。

只傳完成工作所需的最小上下文。主線完整閱讀回報，核對直接來源、實際影響路徑與候選版本，不把未查項目視為通過。

## 前台操作案例

每案寫明：URL／版本、帳號角色與起始狀態、測試資料、瀏覽器／尺寸、使用者工作、操作步驟、各節點預期、允許副作用與還原、禁止操作、必留證據。功能回歸可給明確步驟；自然旅程只給起始狀態、目標、成功條件與禁止事項，不提示控制項位置。

介面子代理須以真實點擊、輸入、選擇、拖拉或切換完成路徑；不得以狀態注入、內部 API、DOM 或 OCR 取代操作／視覺證據。畫面或狀態改變後重新讀取介面；空白或異常截圖不算證據，換工具截到可視畫面為止。回報 `PASS`、`FAIL` 或 `BLOCKED`，附實際步驟、結果、期望差異與未測範圍。

工具路徑（依使用者 CLAUDE.md「瀏覽器工具路由」）：免登入頁用 Claude Code 的 Browser pane（`mcp__Claude_Browser__*`）或 headless playwright；需登入態用 `chrome-relay` 技能接管使用者已登入的 Chrome。一律另開新分頁，只關自己開的分頁。

證據落檔：Browser pane 的截圖只存在子代理自己的對話裡，主線看不到；要給主線 Read 目視的證據，子代理用 Bash 跑 `scripts/screenshot.js <url> <out.png> --size WxH [--click <selector>:<n>]`（無頭瀏覽器，輸出含 scrollWidth）存進 evidence/，主線判定前自己 Read 一次。

使用新開且可隔離的測試分頁／資料。付款、刪除正式資料、對外發送、身分驗證、個資、憑證或正式環境不可逆操作，未獲明確授權就停在操作前回報 BLOCKED。產品 FAIL 修正後，重測受影響案例與既定必要回歸。

## 續接、壓縮與 cloud

- 續接：`claude --continue`、`--resume`、desktop 續接都會恢復尚未完成的 `/goal`（回合數與計時歸零，條件不變）。技能被觸發後第一件事永遠是讀狀態檔，只讀狀態、必要來源與未解差異。
- 對話壓縮：壓縮後 Claude Code 會把「最後一次呼叫時」的技能內容快照附回（2026-09-15～27 實測：技能呼叫後的 15 次壓縮有 14 次附回），所以技能檔中途更新後，要重新呼叫才會生效（2026-09-16 回顧的「規則更新從未生效」即此原因）；狀態檔則幾乎不會附回（15 次只 2 次），驗收條文靠 `sidecar-guard.py` 每次印出。看到續接摘要就先 `Skill(long-task-orchestrator, "續接")` 重載，再讀 state.md；摘要不是規則或狀態來源，任何判定前重讀狀態檔。
- Cloud／web session：只看得到 repo 內的 `.claude/skills/` 與 `.claude/agents/`，看不到 `~/.claude/`。要在 cloud 用本技能，必須把這兩個目錄提交進 repo。`/goal` 可在 `claude -p`、desktop、Remote Control 使用。
- 並行技術包的 worktree 由主線依「B 技術包 worktree 隔離」預先建立並寫進 `[工作區]`；不用 Agent 工具的 `isolation: "worktree"`（路徑派工前不存在、無法先過閘，且未修改時會被自動清掉）。同一檔案／元件仍依序交接，不得同時寫。

## hooks 閘

`scripts/gates.py` 把三條自律規則改成事件當下的檢查，只會放行（可附一行備註）或 exit 2 把原因交回模型，不跳確認框：

- **G4 壓縮後重載**（SessionStart，`compact`）：本對話載入過本技能時，壓縮後直接印出狀態檔重點：還沒通過的驗收條、還沒結的工作包、待決清單，並提醒派工或判定前讀完整狀態檔；對話裡沒有附回技能內容時，先 `Skill(long-task-orchestrator, "續接")`。
- **G3 不用提問框卡主線**（PreToolUse，`AskUserQuestion`）：本對話載入過本技能且任務未完成時擋下；受監督（有 `LONG_TASK_BIND` 綁定訊息）提示改交監督（本對話唯一的讀者是監督，逐項確認模式也不放行），未受監督提示採推薦並記已採預設，狀態檔「逐項確認模式」記有使用者原話時放行；最終判定為 PASS 時放行。正在監督 run 的監督對話（run 綁定檔記的監督就是本對話、run 未驗收未停止，且有待處理事件或接收器／保持載入在跑）不必載入本技能也同樣擋下，提示改用 `supervise.cjs ask` 取全部未決項、以不會停住回合的選擇卡一次列出；run 驗收、停止或停掉保持載入後放行（2026-10-13 A 開發監督在提問框裡等了 9 小時 57 分，期間送驗沒人處理）。
- **G1＋G2 派工前檢查**（PreToolUse，`Agent`）：只看 `lt-*`。工作包（派工提示加上它引用的 `wp/<id>.md`）缺 `[工作區]`／`[可修改範圍]`／`[共用資源]` 擋；錯誤次數（狀態檔工作包表優先，其次派工表頭「目前錯誤次數」）已滿 3 擋；派的檔次高於錯誤次數允許的檔次擋，訊息寫明狀態檔與派工表頭各記幾次；查不到錯誤次數放行加備註。同一套檢查也套用到 PreToolUse(`Workflow`)：長任務中只放行技能附的 `long-task-batch`，`args.packages` 逐包檢查（任一包不合格整批擋下），其他工作流程擋下，因為它們派出的代理不經過這兩道閘。

三道閘的狀態檔不假設在目前工作目錄（主線常在 git worktree 裡，或沿用舊版 `.codex/long-task`）：依序取派工引用的 wp 檔所在任務、本對話工具呼叫最近碰過的 `state.md`，最後才是目前工作目錄的 `.claude/long-task/`；工作包表的錯誤次數欄依表頭含「錯誤」的那欄定位。

安裝（使用者層，所有專案生效；`<skill>` 換成本技能的絕對路徑）：

```json
{"hooks": {
  "SessionStart": [{"matcher": "compact", "hooks": [{"type": "command", "command": "python3 <skill>/scripts/gates.py"}]}],
  "PreToolUse": [{"matcher": "AskUserQuestion|Agent|Task|Workflow", "hooks": [{"type": "command", "command": "python3 <skill>/scripts/gates.py"}]}]
}}
```

批次派工另需三項使用者層設定：把 `claude-code/.claude/workflows/long-task-batch.js` 複製到 `~/.claude/workflows/`；`permissions.allow` 加 `"Workflow(long-task-batch)"`，執行對話不是略過權限模式時才不會停在工作流程核准卡；`"workflowSizeGuideline": "large"`，預設的 `medium` 會讓模型把每次工作流程壓在 10 個代理以內。

## 並行與完成

依依賴並行，並依 SKILL「積極派工」每輪把就緒包派到席位用滿、任一完成即補派；共享檔案、瀏覽器、帳號、資料庫或測試資料無法隔離時排程。查核期間候選版被修改，受影響證據失效。

只在原始目標、核准變更與適用驗收全部有同版有效證據、且「驗收標準」逐條全為 PASS 或核准不做時完成，狀態檔記最終 PASS（`sidecar-guard.py` exit 0）。完成前帳本內 `wp`／`final` 資源都已關閉、沒有未登記的常駐資源（守門 exit 4 時先收尾）；保留給使用者驗收的預覽在使用者或監督驗收後由主線 `stop`，逾期由 `--ttl` 自動關。必要決策、授權或外部依賴未解時，依 SKILL「待決事項」把該單一動作記入待決清單（不以 `AskUserQuestion` 等阻塞方式提問），繼續其他已授權工作，只在無其他可執行項目時才如實停在等待／阻塞，不把階段候選或部分 PASS 當整體完成；若使用者設了 `/goal`，完成條件應由狀態檔的最終判定與證據在對話中被說出，評估模型才判得到。

## 受監督驗收的進度與重測

受監督時依[驗收進度協定](../../long-task-supervisor/references/acceptance.md)保存每個案例的實測結果與影響對照。測試完成即持久化；只記當前快照與證據索引，歷史留在帳本／archive，不壓成超長行。換版依[共用規格](spec.md)不變量 7 判定受影響範圍、連帶範圍及必要回歸，更新總表與實測成本排程。影響清單寫進 `acceptance.change.impactEvidence`（未受監督時寫進狀態檔），逐條寫「改了什麼 → 追到哪個入口或段落 → 對到哪些條文」：畫面追樣式與元件到頁面；程式、API、資料、權限與互動沿引用與呼叫鏈追到頁面、API、排程或指令；研究追來源、範圍與截止時點到結論與段落，截止時點後移時有時效的事實全部列入。改到共用基礎時重驗用到它的功能段落，判斷不出影響時重驗該功能段落。自動化測試每版整套跑。有畫面的成品，每一版都用 `node <skill>/scripts/pixel-diff.js capture <網址> <本版長頁目錄> --widths <契約寬度> --track <受影響元件選擇器> --revision <候選版>` 截各寬度完整長頁並保留，輪播、時間等每次會變的區塊加 `--mask`；這支是本技能的檢查腳本，主線可自跑，也可併入該版的視覺查核包。換版後用 `pixel-diff.js compare <前一版目錄> <本版目錄> --affected <受影響元件選擇器>` 比對：結束碼 0 表示受影響範圍外完全相同，沿用前一版查核；結束碼 1 時，報告 `needsReverify` 列出的寬度與區塊併入重驗，交視覺查核子代理親眼看；結束碼 2（本機沒有無頭瀏覽器）時，改由視覺查核子代理在受影響範圍外逐寬度目視確認，並在沿用紀錄寫明。視覺查核包的回報加一項「沿用核對」：每種寬度的比對結論與報告路徑，`needsReverify` 的區塊寫親眼看的結果。未受影響的證據沿用前一版，記來源版本、未受影響的依據與比對報告路徑。契約指定驗收用的瀏覽器時，驗收截圖照契約，這支工具只負責比對。最終放行時主線不另跑全套人工回歸，交出影響清單、整套自動化測試結果與最終候選版各寬度長頁，由監督分功能段落全套驗收、不沿用；未受監督時，由主線派不帶開發過程上下文的獨立子代理分段驗收。契約明定主線做完整回歸或每關完整同版重驗時照原要求。


受監督的 run 換候選或續接前，讀監督的 `supervise.cjs effective-contract RUN` 及最新授權來源；候選被否決不自行撤回監督代判權。驗收快照明列核准 EXCLUDED，其他條文照有效契約實測。舊 run 先由原監督在安全停點接入，不能因安裝新版就自行重建狀態。等待時更新真實在途／排他資源與結果，不催問同一條核准；通知和答案品質未達照實記缺口。

受監督時另外做到（2026-10-11 定案）：

- 派工快照的 ready、inFlight、blocked、returned 工作包都標 `acceptanceIds`，讓每條未通過的驗收條件都看得出有誰在做。某條 10 分鐘沒人負責，監督會被叫醒來點名派工。
- 開工拆包就把部署腳本、回退步驟、規格草稿、發布說明等準備工作列為就緒包，和測試並行。
- 同一包重做 2 次仍沒送驗，在 recurringRework 標出並停止原樣重跑，等監督指定新做法。
- 回合或子代理被平台錯誤中斷（限速、登入過期、連線失敗、伺服器錯誤）屬執行阻塞，不計品質錯誤；子代理的非限速平台錯誤自己重派；收到監督的續接訊息就從中斷處接續，不重做已完成的部分。限速（例如「You've hit your session limit · resets 3:40am (Asia/Taipei)」）不換模型、不換帳號；記下重置時間，先做不受影響的工作，重置後接續。
- 文件類成品送驗兩次（2026-10-15 定案，流程見 SKILL「文件類成品：事實表先行、只驗一次、不擋下游」）：.md 初稿完成、`doc-check.py` 結束碼 0，就用 `candidate.cjs` 產生含 .md、事實表、出處對照表與 doc-check 輸出的清單送 `submission`，同一輪立刻派出流程圖、簡報、影片的工作包，不等判定；監督回覆的問題清單照單修 .md，依出處對照表只改受影響的頁與旁白句，修正併入整包送驗。整包（全部交付檔、.md、事實表、出處對照表、doc-check 輸出）再送一次，accept 才算出貨；退件時必修項全改、順手項一併改，重送時逐項寫明改了哪裡、對應清單哪一項。樣片、樣張同樣交監督，不停下來等使用者。文件時間預算過半時監督會核對一次；預算用完仍未完成，在進度回報寫明現況、剩餘項與預估，交監督轉使用者決定，不自行改大 `docBudget`。

## 交接文件格式（啟用時）

監督開工時每個任務都會問使用者，本任務交付物是否採用這套交接格式（使用者 2026-10-15：「這種交付方式要在監督啟動時詢問是否要啟用這種交付格式。 每個監督任務都問，我會看需求決定」）；答案寫進契約（開工後才答的登記成修訂，執行端以 `supervise.cjs authorization RUN` 讀回）與執行 prompt，啟用才做，契約另有規定照契約。內容依使用者 2026-10-15 的定義：

1. 用 Archify 生成的完整流程說明文件，分成總體流程與細部流程單元；每張都以 `archify deliver --quality showcase` 通過並留收據。
2. 一份 15 頁以內、可以播放的 HTML 頁面，用途是系統交接說明會議：單一 HTML 與同資料夾的 mp4，離線雙擊可開，鍵盤與點擊都能換頁，有頁碼。第一頁放一支 5 分鐘以內的影片，內容是這個專案解決什麼問題、解決方案簡介、執行重點、觀察重點、預期結果，做完整 overview 讓同事聚焦後，才開始討論 HTML 內容；旁白每句在 .md 有出處，沒有出處的數字不寫。
3. 一份完整說明的 .md 純文字文件，讓使用者想知道細節時可以透過 AI 讀取進行 QA；它就是唯一內容來源，每張圖也寫成文字（AI 看不到圖）。監督驗收時會把 .md 交給只讀這份檔、沒有其他上下文的子代理，回答至少 15 題交接問題，逐題對照程式、設定與主機實況。

流程與驗收照 SKILL「文件類成品：事實表先行、只驗一次、不擋下游」：.md 初稿送驗後，Archify 流程圖、影片與 HTML 簡報同時開工，整包再送驗一次。簡報與影片直接套 [交接簡報模板](../templates/交接簡報模板.html) 與 [交接文件大綱](../templates/交接文件大綱.md)（事實表、出處對照表的格式與概覽影片的合成指令都在大綱裡）。
