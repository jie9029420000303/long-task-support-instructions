# 驗收進度、重測與成本

本協定追蹤有效成果，不以訊息、工作包數或測試執行次數代表完成。原始契約、最新使用者授權及獨立送驗判定仍決定放行；進度快照不能自動授權或放寬驗收。

## 執行與持久化

新 run 的派工快照包含 `acceptance`；舊 run 可繼續使用既有格式，接入前由原監督在安全停點核對相容性，不直接改 live run。每個測試完成即更新快照並執行 `dispatch.cjs write`，不要等整批結束才記錄。

`acceptance.revision` 是目前候選版，`items` 必須逐一覆蓋有效契約 ID 與有來源的排除項。每筆包含 `id`、`status`、`evidence`；status 為 PASS（已有通過證據）、FAIL（判準未達）、BLOCKED（具體前置阻塞）、PENDING（待執行或待判定）、INCONCLUSIVE（已執行但不足判定）。沒有足夠判定證據時不能填 PASS；已有代判授權則由監督查證判定，不把使用者未在場當成必等。有效契約中的排除項填 EXCLUDED，保存核准來源，不算通過次數。

每筆 `lastAttempt` 記最新完成案例：`id`（這次執行的唯一識別）、`caseId`（同一測試案例的固定識別，換代理／工作包／候選版仍沿用）、`revision`、`outcome`、`reason`、`evidence`、實際 `startedAt`／`finishedAt`。結果只允許 PASS、FAIL、BLOCKED、INCONCLUSIVE。使用者離開、逾時、未走到指定路徑，依逐字稿和後端證據判定原因；不能只按結束標籤判 PASS 或產品 FAIL。執行數、通過數、同案例連續通過數分開呈現。

寫入工具先將完成結果保存於 `acceptance-history.jsonl`，再原子替換當前快照。重試同一識別不重複計數，已記錄結果不可改寫；更正另建實測記錄並保留舊證據。只有執行主線寫此帳本，監督不能另行重寫或清空歷史。歷史缺失、為空、格式損毀或未涵蓋快照中的結果時，摘要與寫入會報錯，背景查核視為無效快照；先由原始結果與備份對帳修復，不能清檔重置計數。

同一 run 的寫入以 `dispatch-write.lock` 排他；重疊寫入回報忙碌，由執行主線等原寫入結束後以相同 attempt ID 重試。程序異常退出留下鎖時，核對鎖內 PID 確已退出、快照與歷史已對帳，才移除這個失效鎖續寫；不能移除仍有程序持有的鎖或刪掉結果帳。

背景程式沿用既有「同項至少重做兩次交監督」規則，從帳本查出同一案例反覆未通過，即使執行者未填 `recurringRework`、換計畫名稱或下一步文字，仍產生查核事件；先前 PASS 被撤回也須查核。這些都是診斷，不自動判缺陷或停止任務。同一問題持久去重，更新時間或增加一次相同返工不反覆喚醒；解決後重現才是新事件，兩次監督讀取之間發生的 PASS 與再次返工也由結果帳辨識。

## 換版與有效證據

換版先對照實際變更、直接呼叫、共享模組、環境、Client、權限與測試依賴，保存影響對照。`acceptance.change` 記 `id`、`fromRevision`、`toRevision`、`affectedCaseIds`、`requiredRegressionCaseIds`、`impactEvidence` 與 `policyEvidence`（此重測／沿用方式的依據：共用規格不變量 7 的預設沿用，或原契約、最新使用者授權的特別要求）。寫入工具拒絕無影響對照的候選切換；受影響與必要回歸案例的連續通過數重算，其餘保留。

換版後晚到的舊結果仍保存並計入歷史執行數與歷史 PASS 結果數。已失效版本的結果另列 `staleAttempts`，不增加目前有效連續通過數、不消除新返工，也不能據此把當前條目改成 PASS；未受影響案例的沿用仍須有前述核對依據。

未受影響案例的舊證據預設沿用（共用規格不變量 7；使用者 2026-10-16 定案，起因是 GDB Gate 2 三處小修正觸發整套視覺重驗、預估 176 分鐘；同日補充：「受到變動影響的連帶機制與研究可能都要檢查，但的確不應該是全套重跑，這樣太花時間，尤其是執行端，因為最終監督端還是會分功能段落全套驗收一次」）。執行端換版只重驗受影響範圍與連帶範圍；影響清單逐條寫改了什麼、追到哪個入口或段落、對到哪些條文。每筆沿用記來源版本、未受影響的依據與核對證據；有畫面的成品另附 `pixel-diff.js` 的各寬度長頁比對報告，報告 `needsReverify` 列出的區塊必須已併入重驗。改到共用基礎時重驗用到它的功能段落，判斷不出影響時重驗該功能段落。中間關卡監督抽查原始變更、影響清單、沿用紀錄與比對報告；沿用項不必重開瀏覽器重驗，有疑點只重驗那一項；影響清單漏追連帶範圍就退件，指出漏了哪一段。最終放行（契約最後一關或整案送驗）由監督對最終候選版分功能段落做一次全套獨立驗收，這一次不得沿用，可依本頁「平行驗收」每段派一個子代理；執行端不另跑全套人工回歸，交出影響清單、整套自動化測試結果與最終候選版各寬度長頁即可送驗。契約明定執行端每一關都要同 commit 完整重驗、由主線做完整回歸或要求連續次數時照原要求，使用者另行授權後才改用預設；不要用本協定覆蓋使用者既定條文，也不要在可沿用時無條件作廢所有舊證據。

換版前先把同組的耦合修正、必要修復與放行缺口湊齊，整合成一版只跑一次完整測試；執行端要為單一修正重跑完整測試或換版、而同組修正還沒湊齊時，監督請它先湊齊。會阻止目標達成的缺陷照常修，不以省 Token 留下必修問題。已跑通項目與剩餘項同步更新，不能把過期總表當成當前進度。整套自動化測試只在最終候選的乾淨匯出跑一次（使用者 2026-10-29 定案；GDB V32 每版跑 3～4 次）：監督不重跑整套，改做三件事——核對那份完整輸出確實出自最終候選（commit 或清單雜湊相符、通過與跳過數合理、沒有被略過的測試檔）；挑 1～2 處關鍵邏輯做突變抽查（在監督自己的副本改壞一行，確認對應測試會失敗，抽完還原）；對已部署的版本做主機讀回（版號、設定、關鍵資料），不只看本機結果。執行端每版都要重跑整套時，監督請它改跑受影響範圍。

有畫面的成品：執行端在同一關第一次全面掃描完成前就逐點派修（例如連續兩包修同一元件或同一頁，或同一元件逐寬度、逐內容長度各修一輪），監督請它先掃完、把缺陷收成一張清單再依元件分組派修；同一輪要看的圖超過 15 張卻只派一個查核子代理、另有閒置名額時，請它按頁分給 2～3 個子代理並行判讀；效能包各自另裝工具、另下載瀏覽器或另寫量測程式時，請它沿用第一個效能包的量測腳本與設定（執行技能「畫面成品查核流程」）。

## 品質方向與正式達標

視覺案先核對使用者明定參考、禁止元素與代表桌機／手機核心互動，依既有代判授權選方向；方向品質未成立前不要擴大整站細節 QA。已獲完整開發與代判授權時，代表畫面查核由監督完成，不新增本人核准閘；也不能把操作正確当作使用者設計意圖已滿足。視覺驗收先把設計圖或參考基準與成品並排，看整體觀感（版面結構、層次、配色、字級節奏、留白）；觀感對了才量間距、對齊、色值等細節，觀感不對就直接退件並寫明差在哪，不先花時間量細節（使用者 2026-10-29 定案）。

文件類成品（交接、說明、規劃文件及由它衍生的流程圖、影片、簡報；建構型程式工作不適用）由監督做唯一一次獨立驗收，文件核實以監督判定為準，執行端自評不算（使用者 2026-10-15：「文件核實還是以監督為準，因為執行對話可能夾帶太多開發過程的思考導致原始目標理解飄移」）。執行端只跑腳本檢查（`doc-check.py`），不派子代理預檢，所以監督這一次要查完整：①.md 送驗時：核對事實表表頭的讀取時間晚於最後一次主機或設定變更、整張表出自同一次讀取，不符就列進問題清單請執行端整批重讀；抽查 .md 的事實陳述與程式、設定、主機實況（派子代理平行查時，每個只給 .md、事實表與要對照的程式／設定路徑）；把 .md 交給只讀這份檔、沒有其他上下文的子代理作答、逐題對照。用 reply 回覆通過，或一次列完的問題清單，不擋下游開工。②整包送驗時：衍生件的數字與說法都在 .md、出處對照表涵蓋每頁與每句旁白，並做唯一一次外觀逐頁檢查；全部有效條文通過才 accept。③問題清單一次列完：每項寫位置、預期、實際，能確定的直接附「改成什麼」；分成必修（讀者照做會出錯、與事實不符、違反契約）與順手（措辭、排版小瑕疵），必修擋出貨，順手不擋。④重送只驗差異與上次列出的項目：差異以位元組或像素對照找出，未改的頁沿用原查核；不追加上次已看得到卻沒列的問題，新改動帶出的問題照列。樣片、樣張由監督驗，不停下來等使用者看（使用者另行要求除外）。開工時選擇啟用交接文件格式的任務另核：Archify 每張 `archify deliver --quality showcase` 的收據；HTML 簡報 15 頁以內，單一 HTML 與同資料夾 mp4 離線雙擊可開，鍵盤與點擊都能換頁、有頁碼；第一頁影片 5 分鐘以內，涵蓋專案解決什麼問題、解決方案簡介、執行重點、觀察重點、預期結果，旁白每句在 .md 有出處；.md 把每張圖寫成文字，盲測子代理回答至少 15 題交接問題。實跑數據：2026-10-14～15 GDB 開發 76 分鐘、文件 12 小時以上；逐件送驗讓監督來回 11 次，外觀檢查 14 輪、82 個子代理，其中一次複驗跑了 75 分鐘、用 1.33 億 token，結論是沒有新增要修的項目；退件 21 項中 15 項是內容與程式或主機不符（例：查詢查不到撤回、寫「會發 Telegram」實際不會、sudo 範圍不符），6 項是外觀。

問題回答按原規格的「正確原因／有效下一步」與安全邊界逐題判定，答案空泛、只說未越權或只跑完案例不能算產品達標。通知到達率、指定輪數及其他硬條文照有效契約，不把缺口改成可選。實測、安全、內容正確与整案驗收分開記錄。

## 開跑前與重新排程

先走真實 Client 的核心成功旅程及必要失敗分支，再擴大昂貴多輪模擬。確定性測試可補文字邊界、狀態轉換等覆蓋，不能替代契約指定的真實操作。

每個測試帳號實測登入、底層工作階段、應用授權與續期；修改有效期不代表舊登入已取得新效期。先用既有登入與已授權續期，只有確需本人驗證才交使用者；不自行放寬安全效期。

以實測單位耗時、規模、並行能力與排他資源建立剩餘排程，候選版、前置或影響範圍改變即重算。測試先核對底層共用資源：限流的實際 IP／帳號、工作階段、共用 DB／資料集及高負載主機。不同瀏覽器或代理不代表底層已隔離；沿用排他資源快照，把會干擾其他 UAT 的限流／故障演練隔離或排後，正常核心旅程可繼續。環境互相干擾造成的無效案例記 INCONCLUSIVE 並保留來源，不能當產品 PASS，也不能據此把未受影響證據全數作廢。

驗收路徑要等定時工作（每日、每小時排程）才跑得到時，開發測試期間請執行端手動觸發該路徑，不等正式排程，也不把其他驗收排在排程之後；不刪除、不覆蓋正式環境既有資料（例如遠端已存在的備份集），需要時用強制參數或另一個目的地（使用者 2026-10-15：「開發測試期間，驗收不要等這種正式上線的排程，直接手動啟動」；GDB 的備份驗收原本排在台北 08:00 的每日排程之後，改成直接觸發）。

排隊工作留 ready／blocked，不冒列 inFlight。監督查實際成果、未達條目、返工原因與可解鎖工作，不以「有活動」視為健康。依既有授權選擇可行方案，不重問已涵蓋的做法。

## 精簡讀取

`node <skill>/scripts/dispatch.cjs summary <ABS_RUN>` 輸出目前逐條狀態、分案例執行／通過／連續通過數、最近未通過原因與實測耗時中位數；沒有量測就回 null，不填估計值。一般事件先讀此摘要及待決帳，僅對變更項、失敗案例或授權疑點讀原始證據，不反覆整讀全部歷史。摘要不是獨立驗收證據。

等待、狀態讀取、計數、送達對帳與排程計算交確定性程式；模型只判影響、證據、授權及下一步。等待既有背景完成通知，避免每次 sleep／重查都經主模型。不得用週期長 prompt 保活，或為降低成本自行換模型、縮輪數、砍案例。

state.md 只留當前候選、逐條結果、有效證據索引、在途工作、阻塞與最新決策；歷史另存可查檔案，不把歷史壓成一條超長行。續接先讀精簡當前快照及來源差異，保留契約、授權、未解項、游標與收件，不能讓摘要變成新真相。

## 平行驗收（2026-10-11 定案）

同時有 2 份以上送驗待判時，監督用 Agent 工具派子代理，各自獨立驗一份或一組條件，並給每個子代理同版候選、條文原文和證據路徑。子代理的結論只算草稿；監督逐條核對證據雜湊和關鍵輸出，再寫入 accept／reject 決策。子代理不改執行端的檔案，也不傳訊給執行對話。
