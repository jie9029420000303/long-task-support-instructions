# 驗收進度、重測與成本

本協定追蹤有效成果，不以訊息、工作包數或測試執行次數代表完成。原始契約、最新使用者授權及獨立送驗判定仍決定放行；進度快照不能自動授權或放寬驗收。

## 執行與持久化

新 run 的派工快照包含 `acceptance`；舊 run 可繼續使用既有格式，接入前由原監督在安全停點核對相容性，不直接改 live run。每個測試完成即更新快照並執行 `dispatch.cjs write`，不要等整批結束才記錄。

`acceptance.revision` 是目前候選版，`items` 必須逐一覆蓋有效契約 ID 與有來源的排除項。每筆包含 `id`、`status`、`evidence`；status 為 PASS（已有通過證據）、FAIL（判準未達）、BLOCKED（具體前置阻塞）、PENDING（待執行或待判定）、INCONCLUSIVE（已執行但不足判定）。沒有足夠判定證據時不能填 PASS；已有代判授權則由監督查證判定，不把使用者未在場當成必等。有效契約中的排除項填 EXCLUDED，保存核准來源，不算通過次數。

每筆 `lastAttempt` 記最新完成案例：`id`（這次執行的唯一識別）、`caseId`（同一測試案例的固定識別，換代理／工作包／候選版仍沿用）、`revision`、`outcome`、`reason`、`evidence`、實際 `startedAt`／`finishedAt`。結果只允許 PASS、FAIL、BLOCKED、INCONCLUSIVE。使用者離開、逾時、未走到指定路徑，依逐字稿和後端證據判定原因；不能只按結束標籤判 PASS 或產品 FAIL。執行數、通過數、同案例連續通過數分開呈現。

寫入工具先將完成結果保存於 `acceptance-history.jsonl`，再原子替換當前快照。重試同一識別不重複計數，已記錄結果不可改寫；更正另建實測記錄並保留舊證據。只有執行主線寫此帳本，監督不能另行重寫或清空歷史。歷史缺失、為空、格式損毀或未涵蓋快照中的結果時，摘要與寫入會報錯，背景查核視為無效快照；先由原始結果與備份對帳修復，不能清檔重置計數。

同一 run 的寫入以 `dispatch-write.lock` 排他；重疊寫入回報忙碌，由執行主線等原寫入結束後以相同 attempt ID 重試。程序異常退出留下鎖時，核對鎖內 PID 確已退出、快照與歷史已對帳，才移除這個失效鎖續寫；不能移除仍有程序持有的鎖或刪掉結果帳。

不合格次數由 `rework.cjs` 按驗收條文記在 `acceptance-history.jsonl`（換工作包、改名、壓縮或續接都不清零），第 2 次時程式擋下該條文的下一次派工、送審與正式實測（見[正式案例](formal-cases.md#連續兩次未過)）。背景程式另從帳本查出同一案例反覆未通過，即使換計畫名稱或下一步文字，仍產生查核事件；先前 PASS 被撤回也須查核。這些都是診斷，不自動判缺陷或停止任務。同一問題持久去重，更新時間或增加一次相同返工不反覆喚醒；解決後重現才是新事件，兩次監督讀取之間發生的 PASS 與再次返工也由結果帳辨識。

## 區段驗收（使用者 2026-11-25 定案）

使用者原話：「把工作依照層級分層切碎了以後，盡可能地由執行組先，然後多派子代理去完成，然後再一層一層收回來，然後讓整體加速，同時品質是可控的」；「監督這個地方呢，也可以一段一段的去做驗收，而不是所有東西到最後一口氣大驗收」。起因是工區 E 11/18～11/24 送驗 122 次，11 天只有 1/45 條記為通過，驗收全壓到最後，開發期間監督多半只在記錄。

- **區段表**：監督開工時把有效契約的條文分成區段，每段是一組相關的驗收條文和它們的依賴，列條文 ID 與依賴的區段。隨 `init` 的 `segments` 寫入，或用 `supervise.cjs segments RUN FILE` 寫入、調整，檔案 `{"segments":[{"id":"S1","title":"…","criteria":["A1","A2"],"dependsOn":[]}]}`；每條有效條文正好在一段、依賴不得循環，程式會檢查。監督最了解全案，所以由監督劃分；主線發現更好的切法用提問提出，監督核對後改表。契約修訂增刪條文後同步改表。
- **四層分工**：全案由監督負責；區段由執行主線一次載入一個，只帶該段條文、依賴區段的產出摘要與進度檔；工作包由子代理做，工作包檔用 `[區段]` 標明所屬區段；收件判定由主線做（採用、品質不合格、非子代理責任三選一）。依賴已滿足的區段可並行。
- **送驗**：區段內工作包全部採用後，主線整合成區段候選、跑該段的完整測試（受影響範圍）後送驗。有區段表時 `candidate.cjs` 要求一次只送一個區段，事件帶 `segment` 與 `criteria`。主線送完就寫進度檔、壓縮上下文進下一段，不等判定。
- **判定**：監督逐條判定該段條文。通過的用逐包裁決（`packageRulings` 的 `accepted`）採認，執行端收件後記為 PASS 並沿用；沒通過的列位置、預期、實際與修正要求，主線重開該段相關工作包。兩個以上區段待驗時照「平行驗收」派子代理。brief 的 `segments` 與儀表板「區段進度」列出每段已通過的條文。
- **沿用**：後續區段改到已通過條文依賴的程式或資料時，送驗附影響清單，監督只重驗受影響的條文（下方「換版與有效證據」）。區段通過的條文不因尚未定版而作廢；定版只決定何時正式發版。
- **現役任務切換**：由監督補區段表後切換，已有證據依沿用規則轉成區段驗收；沒有區段表的 run 照原流程，`candidate.cjs` 不要求區段。

## 換版與有效證據

換版先對照實際變更、直接呼叫、共享模組、環境、Client、權限與測試依賴，保存影響對照。`acceptance.change` 記 `id`、`fromRevision`、`toRevision`、`affectedCaseIds`、`requiredRegressionCaseIds`、`impactEvidence` 與 `policyEvidence`（此重測／沿用方式的依據：共用規格不變量 7 的預設沿用，或原契約、最新使用者授權的特別要求）。寫入工具拒絕無影響對照的候選切換；受影響與必要回歸案例的連續通過數重算，其餘保留。

換版後晚到的舊結果仍保存並計入歷史執行數與歷史 PASS 結果數。已失效版本的結果另列 `staleAttempts`，不增加目前有效連續通過數、不消除新返工，也不能據此把當前條目改成 PASS；未受影響案例的沿用仍須有前述核對依據。

未受影響案例的舊證據預設沿用（共用規格不變量 7；使用者 2026-10-16 定案，起因是 GDB Gate 2 三處小修正觸發整套視覺重驗、預估 176 分鐘；同日補充：「受到變動影響的連帶機制與研究可能都要檢查，但的確不應該是全套重跑，這樣太花時間，尤其是執行端，因為最終監督端還是會分功能段落全套驗收一次」）。執行端換版只重驗受影響範圍與連帶範圍；影響清單逐條寫改了什麼、追到哪個入口或段落、對到哪些條文。每筆沿用記來源版本、未受影響的依據與核對證據；有畫面的成品另附 `pixel-diff.js` 的各寬度長頁比對報告，報告 `needsReverify` 列出的區塊必須已併入重驗。改到共用基礎時重驗用到它的功能段落，判斷不出影響時重驗該功能段落。中間關卡監督抽查原始變更、影響清單、沿用紀錄與比對報告；沿用項不必重開瀏覽器重驗，有疑點只重驗那一項；影響清單漏追連帶範圍就退件，指出漏了哪一段。結案不做全套：所有區段通過後，監督只重驗被後續改動影響到的條文，再交付真人QA驗收腳本（見[結案與真人QA](#結案與真人qa)）；執行端不另跑全套人工回歸或整套自動化測試，交出影響清單、受影響範圍的測試結果與各寬度長頁即可送驗。契約明定執行端每一關都要同 commit 完整重驗、由主線做完整回歸或要求連續次數時照原要求，使用者另行授權後才改用預設；不要用本協定覆蓋使用者既定條文，也不要在可沿用時無條件作廢所有舊證據。

換版前先把同組的耦合修正、必要修復與放行缺口湊齊，整合成一版只跑一次完整測試；這裡的「完整」是該版受影響範圍、連帶範圍、必要回歸及契約明定的測試，不等於每版重跑整套。執行端要為單一修正重跑完整測試或換版、而同組修正還沒湊齊時，監督請它先湊齊。會阻止目標達成的缺陷照常修，不以省 Token 留下必修問題。已跑通項目與剩餘項同步更新，不能把過期總表當成當前進度。

**候選版與定版**（使用者 2026-11-13：「這很重要，要確認清楚，還沒有定版舊作發版部署跟重測，太智障了」，定案採兩階段；A WebRPA 11/07～11/12 五天發了 16 個正式版本，其中 7 個的程式改動不到 100 行，子代理 38% 的 token 花在發版、部署與換版後重備證據）：

1. 開發與真實環境測試期間只出中途候選：以 commit 識別，部署到已授權的環境（每次部署照舊備好退回方法），只跑受影響範圍的測試。不合併發版分支、不打正式版號、不發 Release、不寫發版說明，也不為它改帶版本內容的文件；執行端要為中途候選發正式版時，監督請它改以 commit 部署。產品的部署或更新機制要靠版本字串辨識新舊時（例如現場程式回報的版本要和主機映像相同），用預發行版本字串（例如 `0.15.0-rc.2`），仍不發正式版。送到測試環境的中途候選必須已 commit 並推上工作分支，從該 commit 建一次映像，以映像摘要（sha256）部署，定版上正式環境用同一個摘要。產品要把版本字串打進映像時，定版映像從同一個 commit 與鎖定的相依檔重建，記下和測試映像只差版本字串，依第 5 點沿用證據。從未提交的工作資料夾或臨時副本建的映像不得送驗（工區 E 11/19～20 驗過十件的映像從臨時副本建，11/25 補搬重做約 162 分鐘）。
2. 缺陷先收清單：真實環境測試發現的缺陷，不擋後續情境的記進缺陷清單，同一場走完再依同組一次修、出下一個候選；會擋住後續測試或正在寫壞正式資料的才立刻修。
3. 定版由監督判定：需要真實環境的情境在同一個候選走完一輪、沒有要改程式的新缺陷、也沒有未決的新需求時，監督用 reply 通知執行端定版；執行端認為可以定版時以提問交監督，不自行發版。
4. 定版後各做一次：執行端合併發版分支、打版號、發 Release、部署定版並寫帶版本內容的文件，再重驗受影響項目與契約明定要在最終版做的項目；區段已通過的條文依影響清單沿用、不因定版作廢，之後進入[結案與真人QA](#結案與真人qa)。
5. 中途候選上取得的真實環境結果是有效證據，定版時依影響清單沿用：定版與最後一個候選的差異只有版本字串與發版檔時，記明差異後沿用。契約條文寫明須在同一版本、正式版號或最終版取得的項目，照條文在定版後做；現役任務的條文或授權原本要求每次修正都發正式版的，由監督以使用者原話登記修訂後才改用本節。
6. 定版後才發現的缺陷照既有規則處理（部署後 2 小時內發現、正式資料沒受損的小修併入下一版）；下一版同樣先走中途候選。

**測試分工**（使用者 2026-11-11：「執行端只就子代理交付成果做測試驗證，整套檢查是監督依照執行交付做一次。最後整套監督做一個大全套」；同日補正：「主線如果測過，監督就是看他的報告，而不是自己再測一次，反正最後大全套監督會總驗收」，起因是 v1.4.0 首日同一範圍由主線與監督各跑一次：WebRPA 第 1 段兩次共 50.7 分鐘，會計中途候選監督重跑 782 檔 47.6 分鐘；WebRPA 同日整場閘門跑了 11 輪、5 個版本，其中 6 輪從頭重跑，只差一個測試檔也整場重跑約 28 分鐘）：

1. 執行端與子代理只測交付影響到的範圍，中途版本不跑整套。某一段或某個檔失敗時，修正後只重跑失敗的段或檔（閘門腳本有選段參數就用它）及修正影響到的範圍，其餘段附實際差異、證明不受影響後沿用結果，不為一兩個檔整場重跑。執行端每版重跑整套或整場重跑時，監督請它改跑受影響範圍。
2. 執行端每次交付中途候選或部署前，監督看執行端的測試報告，不自己重跑：依下方「測試範圍與實際結果核對」核對影響清單有無漏追、選段是否足夠、受驗版本是否就是交付版本，以及逐檔或逐段的實際結果；報告只有總數、缺清單或有疑點時，請執行端補證據或補跑，監督不代跑。對已部署的版本做主機讀回（版號、設定、關鍵資料），不只看本機結果。
3. 結案不跑整套（使用者 2026-11-25：「所有東西做完後監督就是把有改的區段的地方，就是每一個區段條件有聯動到的地方再測一次」，取代 2026-10-29「整套自動化測試只在最終候選的乾淨匯出跑一次」）：監督只對聯動範圍，從最後候選的 commit 或清單自建乾淨匯出，在自己的工作區親自跑，不沿用執行端結果，執行端不另跑；同時挑 1～2 處關鍵邏輯做突變抽查（在監督自己的副本改壞一行，確認對應測試會失敗，抽完還原）；結果依下方「測試範圍與實際結果核對」保存，再寫真人QA驗收腳本（見[結案與真人QA](#結案與真人qa)）。
4. 監督的測試（結案聯動重測與突變抽查）放在監督工作區（例如 RUN 下另建的目錄），不改執行端的檔案與工作樹；會用到連接埠、測試資料庫、瀏覽器或帳號等排他資源時，先和執行端錯開或隔離。長測試依本頁「平行驗收」派子代理在監督工作區用 long-task-orchestrator 的 `scripts/test-run.py`（設逾時）執行，監督同時做突變抽查與寫驗收腳本，不空等。
5. 契約對中間關卡或最終整套另有具體要求時照契約。引用契約條文要求整套前，先確認該條的適用條件這次成立（例如只管 lockfile 的條文，lockfile 沒變就不適用）；單次授權裡的「完整閘門全過才部署」只適用那一次，不延伸成每版整套。
6. 程序錯誤與隔離環境（使用者 2026-11-23：「獨立隔離測試環境我們就會用開發環境去做，而不是每做一個測試就啟動一個」，這裡的開發環境指 Staging，2026-11-25 起統稱測試環境；工區E 一個 I04 封單從 V4 改到 V16）：驗收程序出錯（監督或執行端自訂的步驟出錯，不是產品或程式錯誤）當場修，只重跑出錯的那一步並留紀錄，整包照常有效，原核准與原時段照用；防止「重跑到碰巧過關」只用在 AI 判讀的結果；一個驗收期間用契約環境表上的同一套測試環境（見[環境分層](#環境分層)），結束才清，不每做一個測試就另起一套；隔離環境驗過的，上線後只做讀回與冒煙，不在正式環境重測。

### 環境分層

使用者 2026-11-25 定案：本機是開發環境，測試驗收在測試環境做，監督驗收完才 push 並部署到正式環境。

| 環境 | 做什麼 | 不做什麼 |
|---|---|---|
| 開發環境（Mac 本機） | 寫程式，跑不需要環境底層支援的程式功能測試，例如函式與單元測試；需要時打包要部署到測試環境的映像，打包後不在本機啟動或測試 | 不另起容器模擬伺服器。需要真實服務的驗收條文不以本機結果判定 |
| 測試環境（例如 Staging） | 整合測試、真模型與其他真實服務的驗收，一個驗收期間用同一套 | 不做壓力測試，它的規模比正式環境小，結果不能代表正式環境 |
| 正式環境 | 部署監督驗收過的同一個映像，部署後讀回與冒煙，上線後由 QA 做壓力測試 | 不重測測試環境驗過的項目 |

開案時把環境表寫成契約條文（見 SKILL「開案五項與環境」）。每個環境寫位置（主機、帳號或標籤）、用途與可做的測試層級、資料與權限、元件部署在哪裡與彼此怎麼呼叫，以及環境驗收清單：服務與版本、連線與權限、測試資料、健康檢查、能從 commit 部署也能退回。

這裡的「環境」指程式實際跑起來、做測試的地方。打包映像只是把已推上的 commit 和套件包成一個檔，在哪台機器打包都不算換環境，不必問使用者；條件是映像從已推上的 commit 建、部署前兩端核對映像摘要相同、打包的機器不啟動也不測試這個映像（使用者 2026-11-26：「建docker在我本機沒差，如果是為了部署Staging要先有映像的話，重點是城市跟驗收功能不能在測試環境以外的環境測試」，「城市」是語音輸入的「程式」）。測試不在環境表指定的環境做，結果不算有效證據。環境問題在原環境修好，只重跑出錯那一步（見測試分工第 6 點）。要把程式或驗收測試改到環境表以外的環境跑（換環境或另開環境），屬[「仍要問」](authorization.md#長任務預設類別授權)：監督用四段格式問使用者，答覆用 `amend` 登記契約修訂後才換，監督與執行端都不自行決定，有推薦也不代決（工區 E 11/25 19:27 監督自行改在 Mac 另起容器測交接，19:52 撤回；11/26 01:40 監督把在 Mac 打包登記成範圍外方向選擇自行代決，01:56 又把打包當成另開環境叫停並轉問使用者）。

正式環境的壓力測試選離峰時段，逐步加量，事先定好停止門檻與退回方法。不在正式資料庫寫入測試單據，必須寫入的部分先定好隔離與清除方式。

### 測試範圍與實際結果核對

執行端在中途候選送驗或升版前，依實際變更、直接與連帶影響、必要回歸及有效契約列出該次必跑範圍；結案的聯動範圍由監督重測時列出。針對該次必跑範圍核對專案的測試設定、收集方式、腳本與真正測試，區分輔助程式、測試資料和測試項目；不要求重新枚舉全 repo 或核對整套，契約另有明定時照契約；測試可能不全依檔名慣例命名，也可能由其他腳本或工具收集。盤點及比對範圍不等於執行全套，也不表示已實際執行。

對每次執行留候選版本（commit 或清單雜湊；有未提交變更時另留實際內容識別）、執行環境、不含秘密的命令、結束碼與可驗證的完整測試結果；含機密的原始輸出不進一般證據、對話或一般日誌，提供去敏後仍可核對執行範圍、各項結果與失敗細節的完整結果，必要原始紀錄依任務安全規則保存；不得刪除尚需的唯一證據。以工具產生的收集清單、逐檔或逐案例結果及安全日誌對照必跑範圍，分別記下已執行及結果、跳過／未執行及原因。輸出不足以判明某項是否執行時，補足收集或執行證據，不能用檔案存在、命令的 glob、預期清單或「0 失敗」推定通過。不在本次範圍的項目記明未納入及依據，不算已執行。

監督在送驗或升版前核對範圍、實際執行紀錄與候選版本一致；缺少必跑項、被跳過而沒有符合有效契約的處理依據、失敗或證據不足時，不把該測試或其支撐的驗收條文判為 PASS，也不得以此作為該次送驗或升版關卡通過的依據；請執行端補跑、修復或補證據，監督不自己重跑（見上方「測試分工」）；其他已授權工作照常。回報「0 失敗」要寫明實際執行範圍及跳過／未執行項目，不能以局部結果稱整套通過。此核對不新增每次 commit、送驗或升版都執行整套的要求；契約對範圍、重跑或連續次數另有規定時優先。

有畫面的成品：執行端在同一關第一次全面掃描完成前就逐點派修（例如連續兩包修同一元件或同一頁，或同一元件逐寬度、逐內容長度各修一輪），監督請它先掃完、把缺陷收成一張清單再依元件分組派修；同一輪要看的圖超過 15 張卻只派一個查核子代理、另有閒置名額時，請它按頁分給 2～3 個子代理並行判讀；效能包各自另裝工具、另下載瀏覽器或另寫量測程式時，請它沿用第一個效能包的量測腳本與設定（執行技能「畫面成品查核流程」）。

## 結案與真人QA（使用者 2026-11-25 定案）

使用者原話：「所有東西做完後監督就是把有改的區段的地方，就是每一個區段條件有聯動到的地方再測一次」；「不管AI演的怎麼樣，最終一定是真人要有一個QA」；驗收腳本要讓 AI「邊帶著人做邊記錄所有東西的反應的結果」，「不是AI帶著人做完之後，然後人看到了問題，然後人還要自己想辦法怎麼回報給AI」。這一節取代原本最終候選的整套自動化測試與分功能段落全套驗收。

1. **聯動重測**：所有區段通過後，監督合併各區段送驗附的影響清單，找出被後續區段改動影響到的已通過條文，只重驗這些條文、只跑它們的自動化測試，並做突變抽查（上方測試分工第 3 點）；不另跑全套驗收或整套自動化測試，執行端也不另跑。重驗不過的條文交回主線成為修正區段。
2. **真人QA驗收腳本**：監督依[真人QA驗收腳本範本](../templates/真人QA驗收腳本範本.md)寫「真人QA驗收腳本.md」，存在 run 目錄，交使用者轉給真人QA。真人QA把腳本交給一個 AI 對話：AI 用測試帳號登入、開瀏覽器或操作後台，一步一步帶真人做，每步自己記下實際結果，真人只確認或說明看到的問題；全部走完，AI 依[真人QA驗收結果格式](../templates/真人QA驗收結果格式.md)產出「真人QA驗收結果.md」，真人QA交回監督。寫完自我核對：每條驗收條文至少被一個情境涵蓋；腳本裡的網址、帳號、資料實際讀回確認存在。監督不自己把整個流程跑一遍。
3. **等待**：交付腳本後用 `supervise.cjs pending` 登記一項 `user_action`（請真人QA依腳本驗收並交回結果），等待用 checked wait 掛在這一項；背景監看保留，不耗模型。
4. **收結果**：監督逐項核對問題清單。要修的依對應條文交回主線成為修正區段；誤會或屬於新需求的記下判定依據，新需求依代決原則處理。修完只更新腳本裡受影響的情境，請真人QA重跑那幾段、交回新的結果。
5. **結案**：驗收結果全部通過才 accept；accept 的逐條 `results` 以區段判定、聯動重測與真人QA驗收結果為證據。

## 品質方向與正式達標

視覺案先核對使用者明定參考、禁止元素與代表桌機／手機核心互動，依既有代判授權選方向；方向品質未成立前不要擴大整站細節 QA。已獲完整開發與代判授權時，代表畫面查核由監督完成，不新增本人核准閘；也不能把操作正確当作使用者設計意圖已滿足。視覺驗收先把設計圖或參考基準與成品並排，看整體觀感（版面結構、層次、配色、字級節奏、留白）；觀感對了才量間距、對齊、色值等細節，觀感不對就直接退件並寫明差在哪，不先花時間量細節（使用者 2026-10-29 定案）。

文件類成品（交接、說明、規劃文件及由它衍生的流程圖、影片、簡報；建構型程式工作不適用）由監督做唯一一次獨立驗收，文件核實以監督判定為準，執行端自評不算（使用者 2026-10-15：「文件核實還是以監督為準，因為執行對話可能夾帶太多開發過程的思考導致原始目標理解飄移」）。執行端只跑腳本檢查（`doc-check.py`），不派子代理預檢，所以監督這一次要查完整：①.md 送驗時：核對事實表表頭的讀取時間晚於最後一次主機或設定變更、整張表出自同一次讀取，不符就列進問題清單請執行端整批重讀；抽查 .md 的事實陳述與程式、設定、主機實況（派子代理平行查時，每個只給 .md、事實表與要對照的程式／設定路徑）；把 .md 交給只讀這份檔、沒有其他上下文的子代理作答、逐題對照。用 reply 回覆通過，或一次列完的問題清單，不擋下游開工。②整包送驗時：衍生件的數字與說法都在 .md、出處對照表涵蓋每頁與每句旁白，並做唯一一次外觀逐頁檢查；全部有效條文通過才 accept。③問題清單一次列完：每項寫位置、預期、實際，能確定的直接附「改成什麼」；分成必修（讀者照做會出錯、與事實不符、違反契約）與順手（措辭、排版小瑕疵），必修擋出貨，順手不擋。④重送只驗差異與上次列出的項目：差異以位元組或像素對照找出，未改的頁沿用原查核；不追加上次已看得到卻沒列的問題，新改動帶出的問題照列。樣片、樣張由監督驗，不停下來等使用者看（使用者另行要求除外）。開工時選擇啟用交接文件格式的任務另核：Archify 每張 `archify deliver --quality showcase` 的收據；HTML 簡報 15 頁以內，單一 HTML 與同資料夾 mp4 離線雙擊可開，鍵盤與點擊都能換頁、有頁碼；第一頁影片 5 分鐘以內，涵蓋專案解決什麼問題、解決方案簡介、執行重點、觀察重點、預期結果，旁白每句在 .md 有出處；.md 把每張圖寫成文字，盲測子代理回答至少 15 題交接問題。實跑數據：2026-10-14～15 GDB 開發 76 分鐘、文件 12 小時以上；逐件送驗讓監督來回 11 次，外觀檢查 14 輪、82 個子代理，其中一次複驗跑了 75 分鐘、用 1.33 億 token，結論是沒有新增要修的項目；退件 21 項中 15 項是內容與程式或主機不符（例：查詢查不到撤回、寫「會發 Telegram」實際不會、sudo 範圍不符），6 項是外觀。

問題回答按原規格的「正確原因／有效下一步」與安全邊界逐題判定，答案空泛、只說未越權或只跑完案例不能算產品達標。通知到達率、指定輪數及其他硬條文照有效契約，不把缺口改成可選。實測、安全、內容正確与整案驗收分開記錄。

## 開跑前與重新排程

先走真實 Client 的核心成功旅程及必要失敗分支，再擴大昂貴多輪模擬。確定性測試可補文字邊界、狀態轉換等覆蓋，不能替代契約指定的真實操作。

每個測試帳號實測登入、底層工作階段、應用授權與續期；修改有效期不代表舊登入已取得新效期。先用既有登入與已授權續期，只有確需本人驗證才交使用者；不自行放寬安全效期。

以實測單位耗時、規模、並行能力與排他資源建立剩餘排程，候選版、前置或影響範圍改變即重算。測試先核對底層共用資源：限流的實際 IP／帳號、工作階段、共用 DB／資料集及高負載主機。不同瀏覽器或代理不代表底層已隔離；沿用排他資源快照，把會干擾其他 UAT 的限流／故障演練隔離或排後，正常核心旅程可繼續。環境互相干擾造成的無效案例記 INCONCLUSIVE 並保留來源，不能當產品 PASS，也不能據此把未受影響證據全數作廢。

驗收路徑要等定時工作（每日、每小時排程）才跑得到時，開發測試期間請執行端手動觸發該路徑，不等正式排程，也不把其他驗收排在排程之後；不刪除、不覆蓋正式環境既有資料（例如遠端已存在的備份集），需要時用強制參數或另一個目的地（使用者 2026-10-15：「開發測試期間，驗收不要等這種正式上線的排程，直接手動啟動」；GDB 的備份驗收原本排在台北 08:00 的每日排程之後，改成直接觸發）。

排隊工作留 ready／blocked，不冒列 inFlight。監督查實際成果、未達條目、返工原因與可解鎖工作，不以「有活動」視為健康。依既有授權選擇可行方案，不重問已涵蓋的做法。

## 時間條件縮短驗證

使用者 2026-11-10：「既然這叫測試驗收，那就是模擬時長，壓縮」；「或是只是測試機制 OK 不 OK，上線 beta 了以後再來投入使用了以後，再來去，然後再持續監看」。「開跑前與重新排程」一節手動觸發排程的規則（2026-10-15）因此擴大到所有時間條件：排程、間隔、逾時、到期、保留期限、「N 天沒動作」「N 天不登出」。

- 測試驗收只驗機制：直接觸發該路徑，或把時間參數縮短（30 天縮成 3 分鐘、30 分鐘縮成 3 分鐘），取得同一路徑的證據；週期性的行為至少看到兩次。
- 正式值另以設定讀回或自動化測試確認（例如讀出正式設定是 1800 秒、單元測試驗到期判斷）；測試腳本一開始就把時間參數做成可調。
- 只有條文明定要真實觀察一段時長（例如 WEB D2「觀察 12 小時」）才真等，等的期間其他工作照做。條文只寫出時間規則（例如「30 天內不會被登出」）時照上兩點縮短驗證。縮短比真等還慢時（例如要重建環境）可以真等，該工作包寫出兩邊估時。
- 不自行排「幾點以後再做」：要排就寫出規則或外部限制的出處（例如專案訂的上線時段、對方的測試時段）。
- 直接觸發、縮短時間與測試時鐘屬驗收方法，由監督依[依規格代決](authorization.md#依規格代決)決定，不問使用者，也不改驗收條文。
- 驗收收尾附「上線後觀察清單」：哪些時間條件只用縮短時間驗過，以及條文沒寫也不重要、監督照[代決原則](authorization.md#依規格代決)放行的問題（用 `delegate` 登記，`choice` 寫上線後觀察什麼）；每項寫上線後觀察什麼、何時看、怎麼看（例如「正式站第 30 天確認沒有被登出：看登入紀錄」）。清單列在結案報告，不擋驗收。

## 精簡讀取

`node <skill>/scripts/dispatch.cjs summary <ABS_RUN>` 輸出目前逐條狀態、分案例執行／通過／連續通過數、最近未通過原因與實測耗時中位數；沒有量測就回 null，不填估計值。一般事件先讀此摘要及待決帳，僅對變更項、失敗案例或授權疑點讀原始證據，不反覆整讀全部歷史。摘要不是獨立驗收證據。

等待、狀態讀取、計數、送達對帳與排程計算交確定性程式；模型只判影響、證據、授權及下一步。等待既有背景完成通知，避免每次 sleep／重查都經主模型。不得用週期長 prompt 保活，或為降低成本自行換模型、縮輪數、砍案例。

## 平行驗收（2026-10-11 定案）

同時有 2 份以上送驗（例如兩個區段）待判時，監督用 Agent 工具派子代理，各自獨立驗一份或一組條件，並給每個子代理同版候選、條文原文和證據路徑。子代理的結論只算草稿；監督逐條核對證據雜湊和關鍵輸出，再寫入 accept／reject 決策。子代理不改執行端的檔案，也不傳訊給執行對話。監督自己的測試（結案聯動重測與突變抽查）不論送驗份數都可這樣派：子代理在監督工作區用 long-task-orchestrator 的 `scripts/test-run.py` 跑，回報結束碼、總數、失敗行與紀錄路徑，監督核對紀錄後才採用。
