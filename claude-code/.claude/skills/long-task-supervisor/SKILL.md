# 長任務監督（Claude Desktop Code）

**目前可見的研究對話就是監督對話；執行主線必須是另一個 Claude Desktop Code 可見對話。** 先讀 [啟動與事件協定](references/runtime.md)，沿用本對話已定案的目標、驗收與授權。執行對話由使用者在桌面 App 開啟並送出準備好的 prompt；若當前環境真有可建立桌面 Code 對話的原生工具，可以直接建立。不得用 `claude -p`、`--session-id` 或背景 CLI 取代桌面執行主線，也不得把 CLI session 出現在清單中當成桌面啟動證據。

1. 保存定案原文、附件與規則的快照及 SHA-256，逐條建立驗收契約。執行 prompt 要帶唯一 `LONG_TASK_BIND:<uuid>` 標記、契約位置、既有授權、完整工作與 [事件格式](references/runtime.md#執行對話的事件)，要求執行者使用 `long-task-orchestrator`。明寫「問題交監督依契約查證並代答；只有具體未授權操作才暫停該操作，其餘工作續行」；送出前檢查並刪除舊 prompt 中「監督會把問題轉成使用者選擇題」等相反指示。新的商業取捨及不可逆動作仍按上層授權處理；不替使用者自行設定 `/goal`。
2. 若沒有原生桌面建對話工具，交付可直接貼上的 prompt 路徑及明確的桌面 Code 操作入口，等使用者在新對話送出。透過桌面對話搜尋工具用唯一標記找到精確 `local_...` 對話，再核對同一 prompt 所在的本機 transcript、`entrypoint=claude-desktop` 與專案路徑；有歧義就停在綁定階段，不猜 session ID。
3. 使用 `scripts/supervise.cjs init` 鎖定兩個對話與契約；在**監督桌面對話的背景 Bash 工具**執行 `scripts/claude-watch.cjs RUN`。它只讀精確執行 transcript，遇完成回合就輸出事件並結束；桌面 App 的背景完成通知應喚醒原監督對話，須以真實模型回合讀取輸出並核對事件 ID，才算喚醒成功。將 run 路徑及 runtime 的[原生事件交接](references/runtime.md#原生事件交接)交給執行者：提問、阻塞或送驗先用 `scripts/handoff.cjs prepare` 保存事件，取得唯一資格才發原生短訊；監督對帳同一 pending 再決策，避免背景通知被平台暫停吞掉。`status.active=true` 且 `readVerified=true` 才說「監看已啟動」；背景工具結束但沒有喚醒時，不得宣稱持續監看。

執行對話是唯一修改成品的主線；監督只做代答、具體退件與獨立驗收。每次喚醒後，對有可執行下一步的 `progress` 才傳一則具體短續接；純等待可用 `waiting` 或 `progress` 加 `waitMinutes`，保持安靜直到完成／到期；提問、阻塞、送驗、格式錯誤要依契約判定。`waiting` 只表示背景工作在跑；若同一回覆還有待決、授權遭拒或其他阻塞，執行端須改用 `question` 或 `blocked`，監督也須檢查整段回覆，不能只看事件標籤後靜默跳過。**執行者的 `question` 不是請使用者作答的指令。** 先查契約、已定案對話、專案決策與真實環境；在已授權範圍內選最可行的可逆做法，記錄所依來源、決定與改回方法，直接回覆執行對話。即使有多題，也不可把尚能由監督判斷的題目打包成使用者選擇題。條款同意、DNS／正式發布、付費、push／merge 等先核對既有授權；確實未授權時只暫停該具體動作，指示執行者完成研究、設定草稿、測試與其他獨立工作；等其餘可做工作完成，再集中呈現具體待核准操作，不提前打斷使用者。不可把待核准當作 PASS，也不可默認使用者同意。

回覆執行者使用桌面原生跨對話傳訊工具，附 `LONG_TASK_DELIVERY:<eventId>`，核對工具的送達／排隊結果及精確 transcript，再執行 `decision` 並重新掛上背景監看。送達不明時先對帳，不盲重送；不得用 CLI 續接執行對話。監督在 run 工作區保存決策帳，逐項記執行者問題、來源、代答、待核准動作與送達證據；完成驗收時一次交代做過的決定供使用者確認，不以每次決策中斷他。 **授權與來源核對**：規格列為必測／必做，不等於使用者已核准故障演練、真實資料寫入或對外發送；先查使用者直接授權的原文、目標資源、用途與副作用，缺授權只停該具體動作。代理查核、監督提案與使用者原話分開記，不把代理意見冒記為使用者要求；新增數值門檻只能作診斷線索，未核准不得變成驗收條件。

執行者自稱完成只算送驗。監督重算來源、候選清單與同版檔案，逐條留下預期、實際及實測證據；全數通過且 `decision` 成功才對使用者宣稱完成。需使用者核准的操作仍未完成時，明說驗收未完成及尚待的具體動作。電腦或 App 停止、背景工具結束後未重新掛上時，不宣稱持續監看。

每次代答前，把執行者提出的具體操作逐項對照最新使用者授權原文、適用專案／資源、副作用與禁令，分成「已授權」「確實須本人核准」「已提出但未回答」。第一類直接回執行對話續行，第三類不重問；只有第二類停該操作，其他工作繼續。決策帳保存原文來源與送達證據，不能把執行者的疑慮或監督自己的推論冒充授權缺口。

對執行者純確認或已知待核准事項，核對後使用 `observe`（記錄後繼續監看）決策，保存原因與仍待核准動作，不再向執行者發送「收到」而製造新回合。`needs_user` 必須附使用者明確要求整案暫停的原文來源，不能用來處理單一操作待核准。依 runtime 完成決策並維持背景監看；不得要求使用者先答業務核准題或再說「續監看」才接收其他新事件。待核准不等於已授權，靜默處理也不等於驗收通過。

**授權續接**：啟動、續接與提問前，讀[授權承接與更新](references/authorization.md)，核對使用者最新類別授權及禁令。Git 已獲持續授權就留存可回復紀錄後直接執行；瀏覽器已獲授權就先實際取用既有登入，不把可自行處理的登入或 Push 轉問使用者。後續授權另存原文快照、更新待決帳並傳給原執行主線，不改原驗收契約。

**派工效率監督**：依[派工狀態與監督檢查](references/dispatch.md)，讓執行對話在拆包、派出、收回與等待前更新精簡快照。新 run 預設啟用；init 綁定完成後只通知執行者一次 run 路徑，補齊首份快照。背景程式只在漏派、等待時未收回成果、資源衝突或返工等可處理事件喚醒監督，同一問題去重。監督核對真實代理、原驗收未達項、依賴與主機資源，給具體工作範圍及產出，再由執行對話當輪收回、補派；不只要求增加代理數。送出前重查目前狀態，過期指示不送；不能以加速為由降低原驗收。

**主動追蹤**：依[主動進度查核](references/runtime.md#主動進度查核)，靜默 15 分鐘後核對實際工作。仍可推進或證據不足時發具體短訊；只剩已知等待時，使用附查核來源及 wait 的 observe，重掛唯一背景接收器，不停止監看、不定時喚醒模型。新使用者答覆、執行結果或等待條件變更再觸發查核；STOP、accepted 仍優先。

**驗收進度與重測成本**：依[驗收進度、重測與成本](references/acceptance.md)，新 run 保存逐條成果與每次實測，背景程式從持久結果辨識反覆未通過及 PASS 撤回。監督先讀精簡摘要，核對變更影響、核心旅程、帳號續期與剩餘排程，再讀相關原始證據；執行次數不算通過次數。沿用證據以原契約及使用者授權為準，不重問已涵蓋的決定。
