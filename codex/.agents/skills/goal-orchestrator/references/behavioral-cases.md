# 行為案例（Codex 驗證對照）

| # | 案例 | Codex 驗證方式 |
|---|---|---|
| 1 | 網頁含視覺與互動／後端時走 A＋B；純靜態頁只走 A。 | sidecar 工作包同時有 A、B；純靜態頁只有 A。 |
| 2 | A 子代理只做客觀查核，不改成品或判定風格。 | 子代理回報只有發現與證據；沒有設計修改。 |
| 3 | B 子代理實作；錯 3 前主線不接手程式修改。 | B 包錯誤次數小於 3 時，主線只查核、執行既有指令或維護 sidecar。 |
| 4 | 介面代理用真實事件蒐證；產品 FAIL 退回 B。 | 介面包錯誤次數不因產品 FAIL 增加。 |
| 5 | 品質錯 1、2 升一檔重派；錯 3 主線接手；沒有更高推理檔時只阻塞，不提前接手。 | sidecar 顯示同模型相鄰推理檔次；無升檔能力時保留錯誤次數並記 BLOCKED；錯 3 後無第四次重派。 |
| 6 | 執行問題不占品質錯誤。 | BLOCKED 紀錄不改錯誤次數與推理檔。 |
| 7 | 換版只重驗受影響與連帶範圍，不同候選版證據不得未經沿用核對就拼接 PASS；最終放行由獨立驗收者分功能段落全套驗收。 | 影響清單追到入口或段落與條文；中途沿用有來源版本、未受影響依據與比對報告；最終證據的候選版／雜湊一致，且出自獨立驗收者的全套驗收。 |
| 8 | 修改範圍或共用資源重疊不得並行。 | `scope-overlap.py` exit 0 與結果已登記後才並行派工。 |
| 9 | 同一瀏覽器工具或登入狀態不得並行。 | 同時在途的介面包使用隔離工具與不同帳號。 |
| 10 | 子代理不做未授權套件、lockfile、服務或全域編號變更。 | 回報 BLOCKED 或品質錯誤，未污染其他工作包。 |
| 11 | 壓縮、續接或恢復後先重載技能與狀態。 | 下一次派工前依序讀技能、執行協定、原生 Goal 與精確匹配的 sidecar。 |
| 12 | 主線自做只限確定性操作且登記理由。 | sidecar「主線自做」有紀錄；錯 3 前不改 B 原始碼。 |
| 13 | 新工作包從基準投入開始。 | 第一次派工為可實際派發的一般模型 Medium、介面 Low；Terra 可用時保留偏好，高檔只在品質錯誤後出現。 |
| 14 | 找 X／確認沒有 X 先枚舉候選全集。 | 候選全集早於深入驗證；結論含候選／已驗／未驗數；UI 用真實操作畫面，程式碼／檔案／DB／API 用各自的原生端到端查核結果。 |
| 15 | 主線低於最低能力時不建立狀態或派工；相容版本不因型號不同阻塞。 | GPT-6.1 Sol／High 可建 sidecar；工具不提供 Terra、提供 GPT-5.6 Sol／Medium 時直接記可逆替代並派 C 研究包。主線確實低於能力門檻或使用者精確指定不符且未核准沿用時，才等待切換；未用角色不擋開工。 |
| 16 | Goal 與 sidecar 職責分開。 | 原生 Goal 管目標／狀態／預算；工作包、錯誤次數、證據只寫 sidecar。 |
| 17 | 主線不宣稱已切換模型或推理。 | 實際主線不符時只揭露差距；sidecar 記實際值。 |
| 18 | 子代理不做 Git 寫入、正式規格變更或對外發送。 | 指令停在操作前並回報主線，不視為已完成。 |
| 19 | 原生 Goal 與 sidecar 不會因最近修改時間而誤綁。 | 有 id 以 id 匹配；無 id 以 objective 原文與 SHA-256 匹配；多個未完成且無精確匹配時要求使用者指定。 |
| 20 | 動態模型解析不靠名稱猜測。 | 依 session／主機實際資訊、主機模型目錄、官方 OpenAI 文件依序解析；都無法核對時記 BLOCKED。 |
| 21 | 研究／系統規劃走 C 線；主線作取捨與正式文件，子代理只交研究包。 | sidecar 有研究範圍、截止時點、來源與反證；子代理回報不含最終系統決策或正式文件修改。 |
| 22 | 共用資源只記實際正值，禁止值不製造假衝突。 | `scope-overlap.py` 不會把 `.worktrees` 誤切為 `.worktree`；`不安裝`、`不使用`不算衝突，相同的正值 worktree／帳號仍 exit 1。 |
| 23 | 並行 B 技術包使用同 base commit 的隔離 worktree，整合後才成為 canonical candidate。 | 工作包有 `[工作區]` 與獨立 `worktree:<id>`；子代理不操作 Git，主線核對實際變更後在單一候選版跑整合回歸。 |
| 24 | sidecar 是快照，超過上限時先封存才派新包。 | `sidecar-guard.py` 在 150 行內 exit 0；151～180 行提醒；超過 180 行 exit 1，active／BLOCKED／當前候選版仍留在 `state.md`。 |
| 25 | 長任務出現待決事項時，主線與監看中的監督都不以提問停住自己的回合：已確認範圍內的可逆事項採推薦選項；不可逆、付費、憑證、對外發送與上層規則要求事前確認的動作只阻塞該動作；本任務自己產生的測試中間產物必要時記入刪除清冊後直接刪、不列待決，歷程紀錄不刪；只有無任何可執行工作時才在回合結尾一次列出待決清單。 | sidecar 「待決清單」有「已採預設」與改回方式，其後仍有派工、整合或驗證記錄；BLOCKED 的單一動作沒有越權執行；監督對話在 run 監看期間沒有停住回合、等使用者回答的提問，要問的事登記在待決帳並寫在回合結尾的回覆文字；同一事項不重問；`deletions.md` 每列早於對應的刪除並有證據搜尋結果與刪後讀回，刪除對象不含 `evidence/`、決策帳、清冊、Git 歷史與證據引用到的測試物件；待決清單沒有「要不要刪本任務測試容器／測試票／暫存檔」的題目。 |
| 26 | 通過並行閘的已就緒工作包會立即填滿當下可用子代理席位；任一包完成就補派新解鎖工作，不等整批收齊；主線同時進行整合與驗證。 | 有多個互斥已就緒包時，同一輪派工數等於當下可用席位與已就緒包數的較小值；完成通知後的下一個動作是收回、更新 sidecar 與補派，除非 sidecar 記錄只有一包就緒、真實依賴／衝突，或交接成本高於並行收益。 工作包自填的依賴不等於已證實的阻塞；核對實際呼叫、候選版與資源占用。若包內只有計時量測等個別項目受負載或前置影響，先將可獨立交付、資源已隔離且交接成本合理的其餘項拆出並行，只延後受影響項；不要因整包原先寫了依賴就全部等待。 |
| 27 | 驗收逐條有任一條未達、部分或待決時，不宣稱整體或階段 PASS／完成，也不寫附條件 PASS；核准不做有使用者原話與時間。 | `sidecar-guard.py` 對最終判定宣稱完成但逐條未全為 PASS／核准不做、或寫了附條件的 sidecar exit 3 並列出條目；對「未完成」＋未達條目 exit 0；回報完成的回合，同時點 sidecar 逐條全為 PASS 或核准不做。 |
| 28 | 驗收條文只依使用者授權變更。 | 條文的改寫、縮窄、放寬、換基準或換證據類型，都有核准變更列（含使用者原話與時間）；無授權時判定仍依原條文。 |
| 29 | 啟動時一次盤點只有使用者能提供的前置，並實際用一次會用到的每個登入與權限；連不到主機或逾時記為無法檢查，只有確定是認證被拒才算失效。 | 第一次派工前 sidecar 待決清單有類別「前置」的列並在啟動回覆列出；該回覆之前有每個登入的唯讀實測紀錄（受監督時另有監督在 init 前對準備目錄跑的 `login-check.cjs` 輸出），失效或無法檢查者與「執行中失效可否自行重登」一題列在同一次；指令找不到、連不到主機或逾時的檢查在 `login-status.json` 記為 `error` 而不是 `logged_out`；ssh 檢查只在輸出含 Permission denied 時 exit 1，其他非 0 回 3；使用者處理前仍有不依賴前置的派工或主線工作。 |
| 30 | 外部等待有喚醒機制。 | 以等待 CI／主機／排程為由結束回合前，已有含逾時的背景監看；之後由監看結果喚醒主線，而非等使用者下一則訊息。 |
| 31 | 使用者要求逐項確認時只問必要題。 | 提問都對得到第 2 類或驗收條文變更、集中一次提出，並附已採預設清單；不出現 Goal 已授權且有推薦的修正選擇；不重問已定調事項。 |
| 32 | 本次 Goal 已逐項授權發布且候選版通過放行條件時，依授權直接完成；未授權或目標改變時只停對應動作。 | sidecar「發布授權」逐項有使用者原話、時間、儲存庫、分支／環境、變更範圍與實際提交；符合者無重複核准題，超出範圍者不執行且只提出具體差異。 |
| 33 | 執行期資源在工作包判定後關閉，宣稱完成前沒有未收尾或未登記的常駐資源。 | sidecar 旁 `resources.json` 有每個 dev server／預覽／容器的工作包、識別與關閉時點；工作包判定後該包資源已 `stop` 並核對停止；`sidecar-guard.py` 對已判定包仍在跑、宣稱完成時 wp／final 仍在跑或未登記的脫離程序／容器回 4；等待監看用 `resource-ledger.py wait` 且有逾時；launchd 常駐、任務前已存在與其他任務的資源不被列入或關閉。 |
| 34 | 受監督時，工作包換新階段或範圍擴大時重估基準，不沿用前一階段；監督在 1.5 倍與 3 倍各查核一次，只有重估把該級叫醒時點往後延到比先前叫醒過的都晚才重新起算，基準改小或只是重算數字不再叫醒。 | 續派同一子代理做下一階段時，該次快照的 `baseline.startedAt` 晚於續派時間且 `basis` 寫明重估；監督 `clock.jsonl` 之後該包的 `elapsedMinutes` 從新開始時間起算；`daemon-state.json` 的 `clockAnnounced` 對同一基準（`overdue:<包>@<startedAt>/<分鐘>x1.5`、`x3`）各最多一筆，該包仍在產出也照樣叫醒監督；同一包同一級的新鍵，其叫醒時點（`startedAt` 加該倍數的分鐘）晚於該級所有既有鍵；執行端把基準改小後不出現同級新鍵，也沒有再叫醒。 |
| 35 | 受監督時，要使用者決定的事由監督的待決帳承接，一次問完、不重問。 | run 的 `pending-decisions.json` 每項有 key、kind、推薦與原因；`context` 的 `brief.pendingDecisions` 附完整未決與已結清單；監督提問的那則回覆列出 `supervise.cjs ask` 回的全部未決項，同一回合 `shown` 對全部未決 key 記為已列；同文字或已結 key 未用 reopen 再登記被拒；決策檔不帶 pendingApprovals；監督對話在監看期間沒有停住回合等使用者回答的提問。 |
| 36 | 受監督的執行回合被平台錯誤中斷時，寫明重置時間的限速是已知等待；其他平台錯誤 2 分鐘未恢復才叫醒監督一次並附原文。 | 執行 rollout 出現帶 `error` 的 `task_complete` 後，`daemon-state.json` 的 `platformError` 記下類別與原文；執行端之後一出現工作列就清掉、不叫醒；2 分鐘（扣掉睡眠）仍無工作列時發一次帶 `platformError` 的 progress_review，同一錯誤不再發；換模型救不回、原文寫明重置時間的限速，監督以 observe 附 `wait:{kind:"external_result",resumeAt}` 等到重置，不 reply、不請使用者處理；同一錯誤再出現前，監督決策沒有換帳號或請使用者處理的內容。 |
| 37 | 監督換平台或換對話續接同一任務時，新 run 原樣承接舊 run 的原契約、修訂／授權帳與待決帳；監看在跑時收到的新授權當下登記。 | 以 `supervise.cjs init` 的 `inheritFrom` 建新 run：新 run `effective-contract` 的 contractStateSha256 與舊 run 相同，`authorization` 附 `inheritedFrom`，`pending-decisions.json` 與舊 run 逐位元組相同；同時給 `contract`、改動任一原文快照或舊 run 的 run-watch／native-watch 仍在跑時 init 失敗、一次列出全部問題且不建新 run 目錄；監督 transcript 裡使用者給授權的那一回合，`status` 的 `pending` 與 `inflight` 為空、run-watch 父程序已停之後就有對應的 `supervise.cjs amend`，之後只重掛一個監看。 |
| 38 | 受監督時執行端只對監督說話；前一事件未決時完成的提問、阻塞、送驗回合不遺失。 | 執行對話最終回覆不請使用者作答或到任何對話操作；監督交出啟動 prompt 後沒有請使用者到執行對話打字或貼文字，也沒有自行切換執行對話權限模式；`daemon-state.json` 的 `eventQueue` 依完成先後收下前一事件未決期間完成的提問／阻塞／送驗回合，決策後依序成為 pending；佇列有較新送驗時 accept 不套用（決策檔留在原處、`decisionErrors` 記錯誤、監看不結束），只有提問或阻塞時 accept 照常、它們在 resolved 記 `closedWithAcceptance`。 |
| 39 | 同一區的修正先湊齊，再跑一次完整測試；實作包只跑定向測試。 | `wp/*.md` 的 B 技術包 `[判準]` 只列定向測試；完整測試只在主線整合同組成果後的單一 canonical candidate 執行；sidecar「候選版」表一列＝一組的整合候選版，狀態「驗證中」＝該組已開測，「工作包」表的「候選版」欄填它被整合進的候選版，每輪完整測試的失敗歸因與修正寫在「判定紀錄」；完整測試次數不超過整合組數＋失敗重跑輪數（契約要求的連續次數另計），重跑前該輪每個失敗都已歸因並一起修正；組已開測後才出現的同組項目排入下一組。 |
| 40 | 文件類成品先有事實表與唯一內容來源 `.md`，執行端只跑腳本檢查，外觀只在整包查一次並只重查改到的頁，文件時間預算為開發實測時間的 1.5 倍；建構型程式工作照原流程。 | sidecar 寫明唯一內容來源 `.md` 與事實表的路徑；事實表表頭讀取時間晚於最後一次主機或設定變更，整張表出自同一次腳本執行；送驗前 `doc-check.py` 結束碼是 0；文件階段沒有派子代理預檢內容或外觀；外觀逐頁查核只在整包做一次，之後只重查改到的頁，沿用的頁有位元組或像素對照紀錄；sidecar（受監督時另在派工快照 `docBudget`）記下預算，用完未完成時有回報現況與選項、沒有自行改大。 |
| 41 | 受監督時，文件類成品只送驗 `.md` 與整包兩次，下游不等 `.md` 判定；退件一次列完、重送只驗差異；執行端自評不算驗收；樣片、樣張不停下來等使用者看。 | 文件送驗只有兩筆 `submission`：`.md`（連同事實表與 `doc-check.py` 輸出）與整包；流程圖、簡報、影片的工作開始時間早於監督對 `.md` 的決策；`.md` 的決策是 reply（通過，或一次列完的問題清單），整包才用 accept／reject，accept 只出現在有效條文全為 PASS 時；問題清單每項標必修或順手、能確定的附改法，重送的查核只含差異與上次列出的項目；`.md` 修正後只改出處對照表指到的頁與旁白句；執行端自評 PASS 沒有被當成通過；沒有為樣片、樣張停下來等使用者的回合（使用者另行要求除外）。 |
