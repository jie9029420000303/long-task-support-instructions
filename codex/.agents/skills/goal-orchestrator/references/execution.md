# 執行協定

只在建立 sidecar、派工、前台操作、模型解析、Goal 恢復或驗收證據需要細節時讀本檔；核心分工與錯誤規則以 `SKILL.md` 與 `references/spec.md` 為準，不在此重述。

## Goal 與 sidecar 狀態

原生 Goal 保存目標、運行狀態與 Token 預算；不假定它能保存任意工作包欄位。執行 sidecar 放在 `<專案根>/.codex/long-task/<YYYY-MM-DD>-<slug>/state.md`，證據放同目錄 `evidence/`，工作包 prompt 放 `wp/`；由 `templates/state.md` 複製後填寫。是否納入 git 或 `.gitignore` 由使用者決定。

建立 sidecar 時綁定原生 Goal：工具有提供 Goal id／handle 就記該值；否則逐字保存 objective 並記 UTF-8 內容的 SHA-256。續接時先取原生 Goal，再以 id 精確匹配；無 id 才用 objective 原文與雜湊雙重匹配。只有一個未完成且 objective 明確相同者才可自動續接；多個未完成 sidecar 無精確匹配時請使用者指定，不得選最近更新者。

sidecar 保存：原始目標、最新核准變更、驗收標準（逐條表：條文原文、狀態 PASS／未達／部分／待決／核准不做、證據、核准依據）、候選全集（找 X／確認沒有 X 時含維度取值、清單與候選／已驗／未驗計數）、C 線研究範圍／來源／截止時點／關鍵結論、目前階段與停止點；角色模型／推理鎖定與時間；工作包負責者、依賴、候選版、狀態（待派／在途／PASS／FAIL／BLOCKED）、錯誤次數、目前推理、成果與證據；並行批次比對；主線自做項目與理由；待決事項（含啟動時盤點的前置）的已採預設／BLOCKED 動作／待確認解讀與改回方式；PASS／FAIL 判定。

狀態是快照不是日誌：目前階段只寫一兩行；工作包收口時補判定紀錄，並把已關閉工作包搬到同目錄 `archive.md`，讓 `state.md` 以 150 行為目標、派工前不得超過 180 行。收到回報後先更新當前結果；每次派工前與判定後執行 `python3 <技能目錄>/scripts/sidecar-guard.py <sidecar>/state.md`；它同時列出「驗收標準」逐條與最新核准變更，讓主線每次重看條文原文，並在最終判定宣稱完成但逐條仍有未達成條目或寫了「附條件」時 exit 3（主線改判定或補證據後重跑）。超過 180 行時不開新包，先保留 active／BLOCKED 工作、當前候選版、最新核准變更與未解差異，再把已關閉工作包、舊批次、舊判定及已取代的主線自做記錄搬到 `archive.md`；不得刪除或重寫歷史。判定前重新讀取。恢復時只讀 sidecar、必要來源與未解差異；來源與驗證條件未變的有效證據不重跑。

候選版：git 專案記 `git rev-parse --short HEAD`；工作樹有修改時加 `+dirty` 與 `git diff --stat` 摘要。非 git 專案記交付檔 SHA-256。

## 模型解析

依下列權威順序查目前模型、產品定位、必要模態與支援推理層級；技能偏好的型號不是使用者的精確指定：

1. 當前 session／主機明列的實際模型資訊。
2. 本回合派工工具 schema／描述實際允許的模型覆寫、推理層級與繼承規則。
3. 同一主機模型目錄與產品定位；只能佐證能力，不能覆蓋派工工具的可用性。
4. 該路線的官方模型文件（OpenAI 或 Anthropic）。仍無可核對資料時，只記受影響角色 `BLOCKED`，不猜型號、不靜默改用其他角色；主線合格者仍保存 sidecar 並推進其餘已授權工作。

監督交辦或未受監督執行主線的實際模型屬 Claude 時，依[Claude 模型路由](../../long-task-supervisor/references/model-routing.md)選同供應商 Claude Opus／Sonnet，不套用 OpenAI 限制。其他路線維持原 OpenAI 規則；預設不納入其他供應商或影像、語音、即時、資安等專用模型。只在角色首次需要時解析；未用的 A／B 角色沒有可派模型，不得擋住純 C 研究任務。選定後記錄角色、具體模型、基準及實際推理、證據、時間、替代原因與成本對照是否已驗；模板中的空模型欄位須填實際值，不照抄偏好型號。

主線沿用實際 session 模型，以已選路線的官方／主機定位與實際 High 核對最低能力；Claude 主線採 Opus，使用者明確指定其他模型優先。OpenAI 路線的 GPT-6.1 Sol／High 符合基準，不因不是 GPT-6 Sol 就要求核准。只有已確認的能力不足、使用者明示精確型號不符，或必要資訊仍無法查證時，才揭露真正差距，不能把版本差異推成權限問題。技能不能切換主模型或主線推理，不改全域設定。

一般子代理先核對已鎖定模型是否仍可派發；Claude 路線依對應規則使用 Sonnet，OpenAI 路線新角色優先 Terra／Medium。OpenAI 路線的工具未提供 Terra 時，從實際可派的 OpenAI 通用／代理模型中選滿足該角色必要能力者，保留 Medium 基準；工具只有 GPT-5.6 Sol 時，直接鎖定 GPT-5.6 Sol／Medium，將差距記為已採可逆替代，無總成本對照就明記未驗，不宣稱更便宜。已通過的 Terra 工作包不因主線升級而改派 GPT-6。使用者明確指定型號、禁用替代或成本限制不符合者，只阻塞對應派工並提出具體差距；不自動覆蓋其政策。

派發前核對工具的實際參數限制；若完整歷史 fork 不接受模型／推理覆寫，改用可接受覆寫的 fork 方式，並把必要來源與工作包內容明列在 prompt。工具只有繼承模式時，僅在可核對繼承的實際模型與推理且符合角色要求時使用，記繼承結果；不能把省略 model 寫成已指定 Terra。工具呼叫明確拒絕模型時才更新該角色可用性並重解析，不反覆重送相同失敗參數。角色無合格模型時不冒充品質錯 3，也不提前由主線接手 B 實作。

「升一檔」是在同一鎖定模型的已知支援層級中移到緊鄰較高值；不可為升檔換模型或以相同值冒充。若無更高層級或無法要求該值，停止重派、保留錯誤次數並記執行阻塞；不得因此提早由主線接手。能力恢復後再續派。模型不可用時可重解析，但保留工作包錯誤次數與當次應有推理檔，不能重設為新包；無合格模型／必要能力則只記受影響包的執行問題，不靜默降級。

## 工作包

每包只負責一類工作，至少包含：

- `id`、類型（A 查核／B 技術／C 研究／介面操作）、負責者、依賴、錯誤次數、模型與推理。
- 問題、必要來源與精確範圍、候選版號／雜湊、客觀判準（實作包只寫定向測試；完整測試由主線整合同組成果後跑一次）。
- 工作區（canonical 或工作包專用 worktree 的路徑、識別值與 base commit）、可修改範圍、實際共用資源（會讀取、鎖定或改動的 worktree／整體測試套件、套件／lockfile、全域編號、開發伺服器／資料庫／測試資料／帳號、瀏覽器工具）、資料副作用、禁止事項、隔離／還原方式。「不使用／不安裝／不修改」只寫禁止事項，不寫進共用資源。
- 常駐資源：本包會啟動、交回後還活著的 dev server／預覽／容器，一律以 `resource-ledger.py start|register --wp <id>` 登記（主線在工作包寫明工具與 sidecar 的絕對路徑）；交回前 `stop`，要留給後續包或使用者驗收時寫明理由並在回報列 resource id。
- 回報格式：結論、實際覆蓋、發現與影響、證據位置、未查項目及原因。

每包的 prompt 先存成 sidecar 目錄下 `wp/<id>.md`，再派工；重派與恢復都從檔案讀。

C 研究包另明列：議題與決策問題、來源類型與截止時點、可查範圍、必找反證、每項結論需回傳的原始來源與未證實事項。子代理只交研究包；主線核對關鍵來源後，才寫入正式規劃文件。

**並行派工閘**：同一批要並行的工作包，加上所有在途工作包，逐項比對「可修改範圍」與「共用資源」——檔案路徑（含 `**`／`*` 前綴涵蓋）、worktree／整體測試套件、資料表、全域編號、套件／lockfile、共用服務、測試資料、帳號、瀏覽器工具。任一正值出現在兩包以上即為交集；否定值會由工具忽略，禁止事項不能作為隔離證據。有交集時，先為 B 技術包建立綁定同一 base commit 的專用 worktree 並改用獨立測試資源；仍無法隔離才把後派包加依賴改依序，或把共用項改到唯一一包。跑 `python3 <技能目錄>/scripts/scope-overlap.py <sidecar 目錄>/wp/<本批>.md … --in-flight <sidecar 目錄>/wp/<在途>.md …`：exit 0 無交集、1 有交集並列出、2 缺必要段；共用資源用實際正值 `鍵:值`，如 `worktree:wp-b21b`、`測試套件:wp-b21b`、`瀏覽器:chrome`、`migration:134`、`服務:3300`、`帳號:ceo`。比對結果記入 sidecar「並行批次」後才派出；新增工作包須與所有仍在途者重比。

**可派即派排程**：每次派工前先從各 `wp/<id>.md` 的 `[狀態]` 行找出 `ready`、依賴全部 PASS、且不等使用者授權的已就緒包，再以當前在途代理數計算平台還有多少子代理席位。主線依以下順序處理：

拆包先依 SKILL「拆包與主線邊界」把同一情境、同一段程式、同一條測試路徑的項目合成一組，再對照逐條驗收：每條未通過條件至少有一條工作線，無真實依賴者並行；單包以 `pace.cjs estimate` 算出的 5～10 分鐘 AI 時間為目標。查核、取樣、回歸、讀大量資料、瀏覽器操作與證據整理也要在有獨立成果時成包派出，不能默認留給主線；交接與驗收成本高於工作的碎包不拆。

1. 將全部已就緒包連同所有在途包過並行派工閘；衝突者先隔離資源，仍無法隔離才改依序。
2. 無衝突者依「先完成會解鎖最多後續工作」排序，在同一輪連續派到當下可用席位用滿。不預留空席等待可能不會發生的工作；不為了填席位創建沒有獨立成果的零碎包。
3. 子代理完成通知一到，先收回該包、核對結果，把 `[狀態]` 改成 `returned` 或 `completed`（受監督時用 `dispatch.cjs mark`），sidecar 只在這個判定節點補記判定與錯誤次數（驗收逐條、候選版與核准變更也只在送驗、判定、發版節點改寫）；若它解鎖新包，當輪立即重跑並行閘並補派，不等原批全部完成。
4. 主線在子代理執行時做整合、直接來源查核、確定性指令、驗證與下一批準備。只有這些工作都沒有、且所有已就緒包都在途時，才呼叫等待工具；長等待使用較長的有界時限，不忙輪詢。等待平台不會通知的外部結果時，先掛背景監看（有間隔、逾時與失敗回報），再等待或結束回合。

如果只派一包，或派出數少於可用席位與已就緒包數的較小值，sidecar 必須能看到下列其中一個原因：當下只有一包已就緒、其他包依賴這包結果、無法隔離的共用資源衝突，或其他包的交接／驗收成本已高於它們可並行的工作本身。

**B 技術包 worktree 隔離**：主線建立專用 worktree 後，在 `[工作區]` 以 `path:<絕對路徑>`、`worktree:<唯一識別值>`、`base:<commit 或檔案 SHA-256>` 記錄；非 Git 任務也要以同樣三欄識別獨立工作區。子代理只編輯授權檔案，不執行 Git。主線收回後先確認實際變更檔、base commit、定向測試與不重疊條件；只將已授權檔案整合到 canonical worktree，再於單一候選版跑整合測試。worktree 內的結果在整合前只是工作包草稿，不是新候選版；任何 commit、merge、cherry-pick 或對外操作仍依上層授權。舊工作包沒有 `[工作區]` 時，並行閘必須 exit 2，先補齊而不猜測隔離狀態。

每包 prompt 至少包含：`[工作包]` id／類型／依賴／錯誤次數／模型與推理、`[狀態]`（一行 JSON，這包狀態的唯一紀錄：新建 `{"list":"ready"}`，派出改成 `inFlight` 並附 handle 與基準，收回 `returned`、核對完 `completed`、受阻 `blocked`、不再是當前工作 `archived`；受監督時用 `dispatch.cjs mark` 改，同一指令重產派工快照）、`[驗收條目]`（這包推進的驗收條件 ID，沒有就省略）、`[候選版]`、`[工作區]`、`[問題]`、`[判準]`、`[可修改範圍]`、`[共用資源]`、`[資料副作用]`（本包要刪的、別人建立的測試中間產物逐項列明，主線派工前已記入刪除清冊；沒列的不刪。授權依據：監督技能 authorization.md#測試中間產物的刪除，使用者 2026-10-13 原話）、`[禁止事項]`、`[隔離／還原方式]`、`[常駐資源]`、`[回報格式]`。只傳完成工作所需的最小上下文；重派只增加主線指正、更新來源／期望與可復用成果。主線完整閱讀回報，核對直接來源、實際影響路徑與候選版本，不把未查項目視為通過。

## 前台操作案例

每案寫明：URL／版本、帳號角色與起始狀態、測試資料、瀏覽器／尺寸、使用者工作、操作步驟、各節點預期、允許副作用與還原、禁止操作、必留證據。功能回歸可給明確步驟；自然旅程只給起始狀態、目標、成功條件與禁止事項，不提示控制項位置。

子代理須以真實點擊、輸入、選擇、拖拉或切換完成路徑；不得以狀態注入、內部 API、DOM 或 OCR 取代操作／視覺證據。畫面或狀態改變後重新讀取介面；空白或異常截圖不算證據，須換工具取得可視畫面。回報 `PASS`、`FAIL` 或 `BLOCKED`，附實際步驟、結果、期望差異與未測範圍；主線必須能直接讀取證據檔，不接受只存在子代理對話裡的畫面。

使用新開且可隔離的測試分頁／資料。付款、刪除正式資料、對外發送、身分驗證、個資、憑證或正式環境不可逆操作，未獲明確授權就停在操作前。產品 FAIL 修正後，重測受影響案例與既定必要回歸。

## 候選驗證證據

- 有 UI 的候選：必須以真實事件走到可判定終點，保存可視畫面；DOM、OCR、內部 API 或單一旗標只作線索。
- 純程式碼／檔案：保存來源定位、完整查詢範圍及可重跑的測試或靜態查核輸出。
- DB：保存實際查詢、資料範圍、筆數與結果；不得只讀應用層旗標。
- API：保存真實請求條件、回應與端到端判準；不得以 schema 或單一欄位推定完整結果。

每個候選使用相同證據類型與判準；證據須能由主線直接讀取並對應同一候選版。

## 文件類成品流程

適用於說明文件、交接文件、流程圖、簡報、影片等文件類交付物，不論是否啟用交接文件格式；建構型程式工作不受影響。使用者 2026-10-15 先定調「文件核實還是以監督為準，因為執行對話可能夾帶太多開發過程的思考導致原始目標理解飄移」，同日再定目標「我認為文件撰寫不應該比開發時間還長，或至多只能是1.5倍的時間」，並要求檢討「執行端驗收，監督端又驗收，然後沒驗好不會往下走」的流程。實測（GDB 2026-10-14～15）：程式、測試與部署共 76 分鐘，文件 12 小時以上；監督來回 11 次，外觀檢查 14 輪、82 個子代理，重建 32 次，文件階段約 14.6 億 token；退件 21 項中 15 項是內容與程式／主機不符。同一場 `.md` 初稿子代理只花 14 分鐘，照事實表畫的流程圖 6 分鐘一次通過；時間主要花在兩邊重複驗收與逐件等判定。

1. **唯一內容來源**：先寫完整說明 `.md`，路徑記進 sidecar；流程圖、簡報、影片只從它取材，不另寫新數字或新說法。要改內容先改 `.md`，再依出處對照表同步到受影響的頁與旁白句。
2. **事實表先行**：開發驗收或部署完成、最後一次變更主機或設定之後，寫一支腳本在同一時點讀出文件要用的數字、設定值、主機讀回與程式行號，表頭寫讀取時間；之後又改了主機或設定就整批重讀，不拼接不同時點的值。`.md` 每個數字與事實陳述都對得回事實表；衍生件每頁與每句旁白記進出處對照表（JSON 陣列，每筆 `file`、`page` 或句子、對到的 `.md` 標題 `md`）。
3. **執行端只跑腳本檢查**：`python3 <技能目錄>/scripts/doc-check.py --md … --facts … --derived … --source-map … --keep … --repo …`，查簡體字、連結、程式行號、數字與事實表及 `.md` 一致、保留清單、出處對照；結束碼 0 才送驗。不另派子代理預檢內容或外觀，獨立驗收只做一次。
4. **只送驗兩次、不擋下游**：受監督時 `.md` 初稿完成就用 `candidate.cjs` 產生含 `.md`、事實表、出處對照表與 doc-check 輸出的清單送 `submission`，同一輪立刻開工流程圖、簡報、影片，不等判定；監督 reply 的問題清單照單修 `.md`，依出處對照表只改受影響的頁與旁白句，修正併入整包送驗。整包再送一次，只有整包出貨要等監督 accept（accept 會結束整場監看）；退件時必修項全改、順手項一併改，重送寫明改了哪裡、對應清單哪一項，監督只驗差異與上次列出的項目。未受監督時，整包完成後派一個不帶開發過程上下文的子代理做這一次獨立驗收（內容抽查、只讀 `.md` 的盲測問答、唯一一次外觀檢查）。
5. **外觀只在整包查一次**：之後只重查改到的頁，其餘頁以位元組或像素對照確認未變、留下核對紀錄後沿用前次結果。
6. **時間預算**：文件開工時以本任務開發實測分鐘 × 1.5 設預算寫進 sidecar，受監督時另寫進派工快照 `docBudget`（[格式](../../long-task-supervisor/references/dispatch.md#文件時間預算)）；過半與用完時監督各核對一次。用完仍未完成就回報現況、剩餘項與預估（受監督時交監督轉使用者），不自行改大預算。
7. **樣片、樣張不等使用者看**：除非使用者另行要求，樣片與樣張由監督驗，不停下來等使用者先看（使用者 2026-10-15：「後續生成不用先看測試片」）。

受監督且監督交辦的啟動 prompt 寫明本任務啟用交接文件格式時，交付物照監督技能[交接文件格式](../../long-task-supervisor/references/acceptance.md#交接文件格式)那一套做，流程與驗收照上列 1～7；沒寫明啟用就不做這套。簡報與影片直接套 [交接簡報模板](../templates/交接簡報模板.html) 與 [交接文件大綱](../templates/交接文件大綱.md)（事實表、出處對照表的格式與概覽影片的合成指令都在大綱裡）。

## 續接、壓縮與環境

- 續接／恢復依序重載本技能、讀執行協定、原生 Goal、精確匹配的 sidecar；錯誤次數、模型鎖定與有效證據不清零。
- 舊對話曾因模型等待核准時，重載後先核對核准題是否源自使用者精確指定，或只是舊技能預設的型號差異。後者在當前能力及派工路由已符合時記為已解除，接續原研究與成果，不沿用失效問題再次索取核准；前者依使用者指定保留。原生 Goal 的 blocked／暫停狀態依平台恢復規則處理，不改目標、不另建 Goal，也不偽稱已恢復。
- 對話摘要只用來找到 sidecar，不用來替代規則、工作包狀態或判定依據。
- repo 內版本需完整包含 `.agents/skills/goal-orchestrator/`；只裝在使用者目錄的技能不應假定會出現在另一台主機或 Cloud 環境。缺技能、必要工具或模型能力時記執行阻塞並揭露，不靜默降級。

## 待決事項與不阻塞執行

有待決事項時，先依 `SKILL.md`「待決事項」分類寫入 sidecar，再重新掃描已就緒工作包、可整合成果與可驗證項目。發布前先讀「發布授權」逐項核對原話、操作、目標、候選變更與放行條件；已涵蓋者直接執行，未涵蓋者只阻塞該動作。單一動作需要確認，不等於整個 Goal 需要停下；只有沒有任何其他已授權工作可做時，才在回合結尾一次列出待決清單。上層授權與不可逆操作規則仍優先，不得用「不阻塞」為由越權執行。

## 並行與完成

依依賴並行，且每批先過「並行派工閘」；共享檔案、瀏覽器、帳號、資料庫或測試資料無法隔離時排程。介面子代理若共用同一個瀏覽器工具或登入狀態，一次只跑一個；要並行就各自用隔離的瀏覽器程序，並在工作包共用資源欄寫清楚。查核期間候選版被修改，受影響證據失效。

只在原始 Goal、核准變更與適用驗收全部有同版有效證據，且「驗收標準」逐條全為 PASS 或核准不做（`sidecar-guard.py` exit 0）時完成；完成前 `resources.json` 內 `wp`／`final` 資源都已關閉、沒有未登記的常駐資源（守門回 4 時先收尾），保留給使用者驗收的預覽在驗收後由主線 `stop`，逾期由 `--ttl` 自動關。必要決策、授權或外部依賴未解時，把該單一動作記入待決清單或執行阻塞，繼續其他已授權工作；只在無其他可執行項目時才停在等待／阻塞，不把階段候選或部分 PASS 當整體完成。

## 受監督驗收的進度與重測

受監督時依[驗收進度協定](../../long-task-supervisor/references/acceptance.md)保存每個案例的實測結果與影響對照。測試完成即持久化；只記當前快照與證據索引，歷史留在帳本／archive，不壓成超長行。換版依[共用規格](spec.md)不變量 7 判定受影響範圍、連帶範圍及必要回歸，更新總表與實測成本排程。影響清單寫進 `acceptance.change.impactEvidence`（未受監督時寫進狀態檔），逐條寫「改了什麼 → 追到哪個入口或段落 → 對到哪些條文」：畫面追樣式與元件到頁面；程式、API、資料、權限與互動沿引用與呼叫鏈追到頁面、API、排程或指令；研究追來源、範圍與截止時點到結論與段落，截止時點後移時有時效的事實全部列入。改到共用基礎時重驗用到它的功能段落，判斷不出影響時重驗該功能段落。自動化測試每版整套跑。有畫面的成品，每一版都用 `node <skill>/scripts/pixel-diff.js capture <網址> <本版長頁目錄> --widths <契約寬度> --track <受影響元件選擇器> --revision <候選版>` 截各寬度完整長頁並保留，輪播、時間等每次會變的區塊加 `--mask`；這支是本技能的檢查腳本，主線可自跑，也可併入該版的視覺查核包。換版後用 `pixel-diff.js compare <前一版目錄> <本版目錄> --affected <受影響元件選擇器>` 比對：結束碼 0 表示受影響範圍外完全相同，沿用前一版查核；結束碼 1 時，報告 `needsReverify` 列出的寬度與區塊併入重驗，交視覺查核子代理親眼看；結束碼 2（本機沒有無頭瀏覽器）時，改由視覺查核子代理在受影響範圍外逐寬度目視確認，並在沿用紀錄寫明。視覺查核包的回報加一項「沿用核對」：每種寬度的比對結論與報告路徑，`needsReverify` 的區塊寫親眼看的結果。未受影響的證據沿用前一版，記來源版本、未受影響的依據與比對報告路徑。契約指定驗收用的瀏覽器時，驗收截圖照契約，這支工具只負責比對。最終放行時主線不另跑全套人工回歸，交出影響清單、整套自動化測試結果與最終候選版各寬度長頁，由監督分功能段落全套驗收、不沿用；未受監督時，由主線派不帶開發過程上下文的獨立子代理分段驗收。契約明定主線做完整回歸或每關完整同版重驗時照原要求。


受監督的 run 換候選或續接前，讀監督的 `supervise.cjs effective-contract RUN` 及最新授權來源；候選被否決不自行撤回監督代判權。驗收快照明列核准 EXCLUDED，其他條文照有效契約實測。舊 run 先由原監督在安全停點接入，不能因安裝新版就自行重建狀態。等待時更新真實在途／排他資源與結果，不催問同一條核准；通知和答案品質未達照實記缺口。

受監督時另外做到（2026-10-11 定案）：

- 派工快照的 ready、inFlight、blocked、returned 工作包都標 `acceptanceIds`，讓每條未通過的驗收條件都看得出有誰在做。某條 10 分鐘沒人負責，監督會被叫醒來點名派工。
- 開工拆包就把部署腳本、回退步驟、規格草稿、發布說明等準備工作列為就緒包，和測試並行。
- 同一包重做 2 次仍沒送驗，在 recurringRework 標出並停止原樣重跑，等監督指定新做法。
- 派子代理前讀 `RUN/model-fallback.json`：原模型的系列在 limits 且 until 未到，就依 chain 改用同層級的下一個模型，到期後換回。收到「額度限速：…本對話自此改用…」的訊息時，直接從中斷處接續，不重做已完成的部分。回合或子代理被其他平台錯誤中斷（串流中斷、連線失敗、伺服器錯誤）屬執行阻塞，不計品質錯誤；收到監督的續接訊息也從中斷處接續，不重做已完成的部分。
