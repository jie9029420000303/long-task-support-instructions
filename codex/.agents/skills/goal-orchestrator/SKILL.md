# Goal 長任務協作

本 adapter 實作[共用規格](references/spec.md)，只管理 Goal 的分工、鎖定、驗收與續接。已有 Goal 就沿用；僅在使用者明確要求時建立 Goal 或設定 Token 預算。子代理不得建立或更動父 Goal。使用者最新明確指示與上層授權優先。

**監督中的執行對話**：若啟動訊息由 `long-task-supervisor` 指定精確監督對話、驗收契約及來源，照本技能原有的派工、隔離、不合格交付與同版自查流程執行；這種交辦本身不等於要求建立原生 Goal。驗收條文只讀監督鎖定的契約，不自行縮窄。受監督任務核對有效契約、使用者授權及本案規則；與全域規則有具體衝突時，依適用的長任務監督例外處理，不推翻使用者禁令或平台強制審查。觸發外部研究時由研究子代理上網查方案，執行主線選方案並在重做工作包第一步安排驗證小實驗；其餘既定目標與授權內的技術路線由監督安排比較、測試並判定，執行端提供實測證據。**本對話唯一的讀者是監督**（即使啟動 prompt 是使用者貼上的）：本技能凡寫給使用者的提問、待決清單、進度與收尾，受監督時一律寫給監督；需要任何人決定或回覆才能往下做的事寫成 `question`（不標成 progress／waiting），只剩未授權動作或被權限擋下寫成 `blocked` 並附拒絕原文，由監督依契約代答或決定何時轉給使用者，不受影響的工作照常派出；使用者只作為授權來源以第三人稱引用，不請使用者回覆、到任何對話操作或轉貼授權，監督遲未回覆也只找監督。每次最終回覆末尾依監督技能的 [事件協定](../long-task-supervisor/references/runtime.md#執行對話的事件) 放一行 `LONG_TASK_EVENT`：有未完工作用含具體 `nextAction` 的 `progress`，需代答用 `question`，只剩未授權動作用 `blocked`，本地自查通過後用監督技能 `scripts/candidate.cjs` 一步產生候選清單、登記送審的工作包並印出完整 `submission` 事件行，原樣貼上，不手寫雜湊。未收到監督逐條接受前，自己的 PASS 只表示「已送驗」，不得向使用者宣稱整體完成；退件沿原候選版修正再重交。

監督綁定完成後，依[派工快照協定](../long-task-supervisor/references/dispatch.md)在拆包、派出、收回／整合、依賴或資源變化及等待前，更新指定 run 的 `dispatch.json`：工作包狀態一變（派出、收回、受阻、完成、封存），用監督技能 `dispatch.cjs mark <RUN> <sidecar 目錄> <id> '<狀態 JSON>'` 一個指令同時改 `wp/<id>.md` 的 `[狀態]` 行，並由全部工作包檔重產快照，不手寫快照 JSON、不另寫產生器；容量、驗收逐條與文件時間預算等其他欄位用 `--base <JSON 絕對路徑>` 帶入（第一份必帶，之後沿用上一份），要整份重寫時才用 `dispatch.cjs write`。只記實際工作包、代理 handle、已核實容量與排他資源；每個在途包附 AI 時程基準（派出時在 `mark` 加 `--estimate <模型>[:<預估輸出 token>[:<工具分鐘>]]` 同一步填入，或由監督技能 `scripts/pace.cjs estimate` 產生；跑有效率預期驗收條文的實跑包用監督技能 `scripts/efficiency.cjs baseline` 以條文效率預期產生，其他測試、主機程序等非代理工作用前一次同類工作的實測單位耗時乘規模；同一包換新階段或範圍擴大時當下重估、寫入新基準，不沿用前一階段的基準）；真實測試資源（主機排查名額、測試身分）宣告 `capacity.resources` 與各包 `uses`；包一做完就從在途移出；先執行可做的工作，再向監督回報，不能為等待快照核准停住。收到 `dispatch_review` 指示時先查最新狀態，已完成或失效的指示不重做；結果一回來就核對並補派，不等整批。未綁定監督的單對話任務不需此快照。

## 啟動與續接

開發前，先依契約的環境表確認測試環境已架好並通過驗收。還沒有的，先派子代理架設，主線照環境驗收清單自驗後送監督，通過才派功能開發包。接著從規格確認每個元件實際部署的環境、執行身分和驗收位置，寫入[部署目標與收件](references/execution.md#部署目標與收件)，再拆實作包。收到監督的解卡研究時，主線安排小實驗與工作包，回報實測結果。

1. 依序讀本技能、[執行協定](references/execution.md)、原生 Goal，再找專案根目錄 `.codex/long-task/` 的 sidecar。使用者指名者優先；其次以原生 Goal id 精確匹配，無 id 時以 objective 原文與 SHA-256 匹配。多個未完成 sidecar 無法精確匹配時必須請使用者指定，不得以最近更新者猜測。原生 Goal 管理目標、狀態與 Token 預算；sidecar 保存 Goal 綁定、模型鎖定、工作包、收件判定與證據。沒有匹配 sidecar 時，依執行協定建立。
2. 新任務先鎖定原始目標、可判定的驗收標準（照 `templates/state.md` 寫成逐條表：條文原文、狀態、證據、核准依據）、候選版、角色模型與推理，寫入 sidecar 後才派工。「找 X／確認沒有 X」再先完成候選全集。同時盤點完成目標必需、只有使用者能提供或授權的前置（權限、帳號與憑證、付費或資源開通、主機與網域、不可逆或對外操作的授權、需使用者拍板的取捨）；先核對本次任務及先前對話的明確授權，逐項寫入 sidecar「發布授權」表。未授權項才進待決清單（類別「前置」），在啟動時一次列出。帳號與憑證不只核對授權：會用到的每個登入（網站、CLI／API token、ssh、MCP 授權、測試身分）在啟動時以唯讀操作實際用一次，失效或無法檢查（檢查本身跑不起來、連不到主機或逾時，都不當成已失效；只有確定是認證失效才算失效）的，連同對全部登入的一題「執行中任一登入失效、不需輸入密碼或驗證碼者，可否由主線自行重登」，列進同一次清單；受監督時這題由監督開工時問，監督 `RUN/login-sites.json` 還沒列的登入，則把名稱、唯讀檢查指令與失效時怎麼恢復以 `question` 交監督登記實測（見監督 runtime 的 `login_expired`）；未受監督時把檢查方法記在 sidecar 的「前置」或「發布授權」列，續接時重跑一次。列出後不等回答，先做不依賴前置的工作。
3. 上下文被壓縮、Goal 恢復或對話續接後，先依「本技能 → 執行協定 → 原生 Goal → 精確匹配的 sidecar」重建狀態，再派工或判定；自動摘要不是規則或狀態來源。受監督且 run 目錄有 `RUN/格式摘要.md` 時，壓縮後改為只重讀這一頁與 sidecar（常用格式、指令與判斷規則都在上面），摘要沒寫到的事才讀本技能或執行協定的那一段，不整份重讀（使用者 2026-10-29 定案：GDB V32 兩端重讀技能檔 293 次，約每天 1.4 小時）。
4. Goal 完成條件若只是任務描述、無法客觀判定，在第一則回覆提供一句可判定條件供使用者改設；使用者不改也照走，不自行覆蓋 Goal。

## 分工與路由

任務可同時屬於 A、B；網頁預設 A＋B，只有完全無互動且無後端的純靜態頁只走 A。研究計畫與系統規劃型任務不用本技能；本技能的研究只用在不合格查因與監督派的解卡研究。

**文件類成品**（說明／交接文件、流程圖、簡報、影片）事實表先行、只驗一次、不擋下游，細節見[文件類成品流程](references/execution.md#文件類成品流程)：先寫唯一內容來源（完整說明 `.md`），其他形式只從它取材、不另寫新數字；寫之前用一支腳本在同一時點讀出事實表，`.md` 每個數字都對得回事實表，衍生件每頁與每句旁白記進出處對照表；執行端只跑 `scripts/doc-check.py`，不另派子代理預檢；受監督時只送驗 `.md` 與整包兩次，`.md` 送出後流程圖、簡報、影片立刻開工，只有整包出貨要等監督通過，退件一次列完、重送只驗差異；外觀只在整包查一次；文件時間預算＝開發實測分鐘 × 1.5，用完仍未完成就回報選項、不自行延長；樣片、樣張不停下來等使用者先看（使用者另行要求除外）。建構型程式工作不受此流程影響。

**畫面成品**（網頁、圖卡、簡報、PDF 等有畫面的成品；不必在啟動指令另外指定）開工先測瀏覽器能力；靜態畫面用 `scripts/pixel-diff.js capture-batch` 一次截完、由查核子代理親眼判讀（同一輪超過 15 張預設按頁分給 2～3 個子代理並行看），平台瀏覽器只跑真實事件的互動，同一頁的互動一趟走完；每關先掃完全部頁面、寬度與內容狀態，缺陷收成一張清單再依元件分組一次修；效能量測只建一套環境，細節見[畫面成品查核流程](references/execution.md#畫面成品查核流程)。契約明文指定截圖用的瀏覽器或工具時照契約。

| 工作線 | 主執行緒 | 子代理 |
|---|---|---|
| A 視覺／設計：網頁視覺、圖片、簡報、PDF | 設計、排版、風格判定、修正與最終驗收 | 解析素材／來源並客觀查核真實畫面的裁切、遮擋、溢出、可讀性、對齊、響應式與已鎖定規格；不改成品、不判定風格 |
| B 系統／技術 | 定義需求與驗收、拆包派工、查核證據、最終判定；不接手實作，不合格依循環升檔與研究處理 | 一般子代理實作前端邏輯、後端、資料整合、修復與必要測試；介面子代理只按案例操作前台並蒐證 |

並行只限可修改範圍與實際共用資源都互斥的工作包：每包 prompt 必有 `[可修改範圍]` 與 `[共用資源]`（套件／lockfile、migration 等全域編號、worktree／整體測試套件、開發伺服器／資料庫／測試資料／帳號、瀏覽器工具）。`[共用資源]` 只寫實際會讀取、鎖定或改動的正值；「不使用／不安裝／不修改」寫在 `[禁止事項]`，不得當成共用資源來製造假衝突。每批派出前，以 `scripts/scope-overlap.py` 比對本批與所有在途包，exit 0 且結果記入 sidecar「並行批次」後才並行派出。

**跨來源盤點**：收到已登記的新定案、壓縮續接、收回子代理成果後、啟動長測試前及等待前，對照全部未完成驗收、最新有效使用者指示、已知在途工作與待解依賴，找出尚未拆包的可並行工作，不只檢查已登記的 ready 包。受監督時先讀 `dispatch.cjs reconcile RUN` 的有效決策版本、可派包與待核對阻塞；核對後在原有 mark／collect／from-wp 命令加 `--reviewed "本輪核對依據與結果"`，同一步保存版本對帳，不另寫快照或逐項回報。改時間或計畫名稱不算核對新定案。延展討論尚未定案的部分不改有效目標、授權、驗收與派工原則，也不停止原有已授權工作。逐項核對實際依賴、授權、可修改範圍與資源隔離；不確定的先查證，不把未定方向或未授權操作當作就緒。能安全並行且有獨立交付成果的先拆包、過並行閘並派出；有空席卻無合適工作時，在 sidecar「並行批次」記範圍及具體理由（例如真實依賴、無法隔離、尚待授權或並行成本過高）。不為填席位硬拆，不重跑未受影響的測試。

**長測試識別**：受監督時，僅當實際執行的長測試命令由支援 `#` 行註解的 shell（例如 sh、bash、zsh 或 PowerShell）解讀，在命令開頭加一行獨立註解 `# LONG_TASK_LONG_TEST`，換行後接原本命令，讓監督可從工具呼叫辨識啟動線索；不要把秘密寫入標記。工具或 shell 本身不支援此註解（例如 Windows cmd.exe）時照原命令執行，監督可能無法自動辨識；標記本身不代表命令已成功啟動或測試通過，也不阻止既有工作。平台審查拒絕該次命令時，不得刪除標記、更換工具或路徑重試以繞過拒絕；依既有平台拒絕流程處理。

**派工流程（開發情境，使用者 2026-11-26 定案）**：執行主線的工作是切分、派工與收件判定，盡快把工作交給子代理，不自己做程式與測試。

1. 接到區段後，第一回合只拆工作包（拆法見下方「拆包與主線邊界」）。
2. 每條未通過條文至少對應一包。
3. 依賴已滿足的包連同在途包過並行閘後一次全部派出。可用席位取 `dispatch.cjs reconcile` 回的 `capacity.free`，子代理數量不自訂上限（使用者 2026-11-25：「重型工作已經鎖定的話其他子代理就是全面放寬」）；撞到 OpenCodex 的 `workflow_sends_exhausted` 就等這 10 分鐘區間過去再續派，不換模型；錯開啟動由 `dispatch.cjs mark` 處理。不先只派一包觀望，除非它的結果會改寫其他包的範圍或判準。
4. 先派能解鎖最多後續工作的包。
5. 同一區段裡改同一個程式區塊或同一個 worktree 的後續包，用 `followup_task` 交給原本的子代理，不重讀整包背景。
6. 換區段、換程式區塊、不合格後要開新子代理（見「不合格交付」）、需要獨立查核，或模型降級換站時，才開新的子代理。換站時在途的包照舊做完，舊站的子代理交件後封存。
7. 主線只做 Git 合併與提交、建立 worktree、部署、派工與收件工具、狀態與送驗。建映像與部署一個區段整合完做一次，子代理不建映像，背景程式看到子代理建映像會提醒主線（使用者 2026-11-28）。
8. 改程式或設定檔（含解 Git 衝突）、跑任何測試、讀大量紀錄、查環境，一律派子代理；狀態檔、工作包檔、收件結果檔、證據與說明文件不算改程式。
9. 用 `wait_agent` 這類任一包交回就返回的等待，交回一包就先收；受監督時用 `dispatch.cjs collect` 一步寫入狀態、證據與驗收表，同時交回多包就在同一個指令一次收完，解鎖的包當輪補派。主線不自己 sleep（部署腳本內部的等待不算）。
10. 區段全部採用後整合成區段候選，派子代理跑一輪受影響範圍的測試，通過就送驗。

受監督時背景程式偵測到主線親手改程式或設定檔、跑測試或 sleep，第一次直接傳固定訊息要求改派；同一回合再犯，才叫醒監督處理（使用者 2026-11-26，不設緩衝次數）。

**時間條件與外部等待**：開發測試期間，驗收條件要等時間才跑得到時（排程、間隔、逾時、到期、保留期限、「N 天沒動作」「N 天不登出」）不等真實時間：在已授權的環境直接觸發該路徑，或把時間參數縮短（例如 30 天縮成 3 分鐘）取得證據；週期性的行為至少看到兩次，正式值另以設定讀回或自動化測試確認，測試腳本一開始就把時間參數做成可調（使用者 2026-10-15：「開發測試期間，驗收不要等這種正式上線的排程，直接手動啟動」；2026-11-10 擴大到所有時間條件：「既然這叫測試驗收，那就是模擬時長，壓縮」）。只有條文明定要真實觀察一段時長（例如「觀察 12 小時」）才真等，等的期間其他工作照做；縮短比真等還慢時可以真等，但在該工作包寫出兩邊估時。不自行排「幾點以後再做」，要排就寫出規則或外部限制的出處；真實時長留到上線後觀察，列進收尾的上線後觀察清單。不刪除、不覆蓋正式環境既有資料（例如遠端已存在的備份集），需要時用該程式的強制參數或另一個目的地。受監督的等待與回合續接先依[執行層完成通知與定期補漏](../long-task-supervisor/references/execution-wake.md)，完成來源先登記，一般結果及可自行處理的失敗由執行主線收回，不必先叫監督。等待平台不會主動通知的外部結果（CI、遠端排程、主機或外部系統上的長程序）時，先以背景程序掛上有間隔與逾時、結果出現或逾時會喚醒主線的監看（`scripts/resource-ledger.py wait --timeout <時限> -- <查核指令>`，逾時必填、逾時 exit 124；不手寫沒有逾時的 until／while 迴圈），才可結束回合；不得在沒有喚醒機制時以「等某事完成後再做」結束回合。

**受阻只限四種**（使用者 2026-11-10：「不要因為等待我就停下來動作」）：工作包只有下列原因才列 `blocked`，`kind` 寫對應的值，evidence 寫具體原因：前置結果還沒出來（`dependency` 寫等哪一包；`external` 寫等哪個人或系統的什麼結果）、要使用者本人（`user`，寫要他決定或做什麼）、資源正被占用（`resource_conflict`，寫哪個資源被哪一包占用）、時間還沒到（`time`，只限上一段允許真等的情況，寫出條文或外部限制的出處）。排在計畫後面不算受阻：輪到才做、等別包做完再一起做、最終回歸，都列 ready，或拆出能先做的準備包（規格草稿、測試腳本、部署與回退步驟、唯讀查核、事實紀錄）；帶版本內容的文件（手冊、發版說明、證據索引、授權依據清單、執行單與數值卡）等定版後一次寫，定版前列 blocked（kind `dependency`，寫等定版）、開發中只記事實紀錄，不拿來填空席，空席依序給測試、查核與下一批實作（使用者 2026-11-12 定案；A WebRPA 五天 552 個工作包有 194 個是文件類）；只有前一包的結果會改寫它的範圍或判準時，才算前置結果還沒出來。宣告等待或回報「沒有可並行工作」前，逐包寫出受阻原因與已派出的準備包；只寫「沒有可並行工作」不算交代，監督會退回。

**時間取系統時鐘**（2026-11-09～10 OPS 監督與主線互相沿用推估的時間，最多寫快 97 分鐘）：寫給監督、寫進狀態檔或證據的時間，在同一步用系統時鐘取得（例如 `TZ=Asia/Taipei date '+%F %T'`），或交給寫檔、送訊的程式自己產生；不憑上下文推估，不寫「05:5x」這類估計值；別的訊息裡出現的時間不是現在，背景程式訊息最後一行的「背景程式送出時間（台北）」只是那則訊息的送出時間。由模型填寫的時間欄位（例如派工快照的 `startedAt`）用含時區的完整 ISO 時間（例如 `2026-11-10T12:30:00+08:00`），不能晚於現在，否則程式拒收。發現寫錯就另記更正，已寫入的證據原檔不改。

**拆包與主線邊界**：依區段推進（使用者 2026-11-25：「把工作依照層級分層切碎了以後，盡可能地由執行組先，然後多派子代理去完成，然後再一層一層收回來」）。區段是一組相關的驗收條文和它們的依賴：受監督時由監督開工時劃分、寫在 run 的 `segments.json`，主線發現更好的切法用提問提出；未受監督時主線自己劃分並寫進狀態檔。主線一次只載入一個區段，只帶該段條文、依賴區段的產出摘要與進度檔；依賴已滿足的區段可並行。區段拆成工作包（工作包檔加 `[區段]` 行）派子代理，交回逐包收件判定；全部採用後主線把成果整合成區段候選，派子代理只跑一輪完整測試（受影響項＋既定必要回歸，不是整套；契約要求全套就全套），通過才部署、送驗（受監督時事件帶區段 ID 與條文 ID，由送審工具帶上；未受監督時派不帶開發過程上下文的子代理驗）；送完把狀態寫進進度檔、壓縮上下文再進下一段，不等判定。區段內的待做、待修項目依「同一情境、同一段程式、同一條測試路徑」分組（畫面缺陷依同一元件、同一份樣式來源或同一設計變數分組，跨寬度與內容長度合併），同組一起改，實作包只跑定向測試。開發與真實環境測試期間這一版只是中途候選（使用者 2026-11-13 定案採兩階段：「還沒有定版舊作發版部署跟重測，太智障了」；A WebRPA 五天發了 16 個正式版本，7 個的程式改動不到 100 行）：以 commit 識別與部署，不合併發版分支、不打版號、不發 Release，也不寫帶版本內容的文件，產品要靠版本字串辨識新舊時用預發行版本字串；真實環境測試發現、不擋後續情境的缺陷先收進缺陷清單，同一場走完再依同組一次修，會擋住後續測試或正在寫壞正式資料的才立刻修；真實環境情境在同一個候選走完一輪、沒有要改程式的新缺陷與未決新需求時才定版，受監督時由監督判定、主線不自行發版，未受監督時由主線判定；定版後才正式發版、部署定版、寫文件並重驗受影響項目，候選上的真實環境結果依影響清單沿用，契約寫明同一版本的項目照條文在定版後做。每版只跑受影響範圍的定向與快速自動化測試，某段或某檔失敗只重跑失敗的段或檔，其餘段附差異證明不受影響後沿用，不整場重跑；不跑整套，結案只重測有聯動到的範圍並把完整輸出存進證據（受監督時由監督親自跑、主線不另跑；中途版本與部署前監督只看主線的測試報告、不另重跑，報告要列出範圍、逐檔或逐段結果與受驗 commit）；部署後 2 小時內發現、正式資料沒受損的小修，併入下一版一起發，只有正在寫壞正式資料時才立刻熱修（使用者 2026-10-29 定案；GDB V32 整套測試每版跑 3～4 次、1.4.1～1.4.3 三次小修各花 50～60 分鐘）。完整測試失敗時，先把這一輪的失敗全部歸因、修正湊齊，再只重跑失敗的段或檔及修正影響到的範圍，不修一項跑一次。同組新冒出的項目，該組還沒開測就併入，已開測就排進下一組。每條未通過的驗收條件至少對應一條工作線；互不相依者同時開工，單包以 5～10 分鐘 AI 時間為目標，依 `pace.cjs estimate` 的本場模型速度與工具實測估算。查核、取樣、回歸、讀大量檔案／紀錄、瀏覽器操作與證據整理優先派成可獨立驗收的工作包；不為填席位切出交接與驗收成本高於工作本身的碎包。正式主機與現場電腦的部署留在主線，輸出寫進檔案、主線只讀摘要，不把整份輸出讀回對話（使用者 2026-11-12：主線只調度；A WebRPA 五天沒有子代理在跑的 49.9 小時裡，主線獨做 23 小時、3,027 次呼叫，每次都帶整包上下文）。主線做的每一項例外都寫入 sidecar「主線自做」及理由。

不為了填滿席位硬切零碎包：每包仍必須有可獨立交付的結果、能與主線有用工作同時進行，且交接與驗收成本不高於代理工作本身。若當下只有一包就緒，或其他包都有真實依賴／資源衝突，依序執行才是正確行為，並在 sidecar 記錄不並行的理由。

多個 B 技術包要並行修改 Git 專案時，主線預設為每包建立互相隔離、綁定同一 base commit 的 worktree，並在工作包與 sidecar 記錄 worktree 路徑與識別值；只有確定不會修改程式、不跑會讀取其他 dirty 檔案的整體測試、且實際資源互斥時，才可共用工作區。子代理仍不操作 Git；主線驗收後才將授權檔案整合進單一 canonical candidate，並遵守上層 Git 確認規則。共用同一 worktree 或同一整體測試工作區就是真實衝突，不得靠「不碰對方檔案」解除。有交集就隔離資源、加依賴改依序，或把共用項切給唯一一包。非 Git 的靜態成品可為每包建立同一基準的獨立工作複本，共用素材唯讀，交回後由主線核對並整合授權檔案；不得只因最終交付目錄相同，就讓能隔離的所有頁面依序建置。這不取消真正的內容前置、共用程式與資源限制。同一個瀏覽器工具或登入狀態同一時間只派一個介面子代理；要並行就各用隔離的瀏覽器與帳號。靜態截圖用 `pixel-diff.js capture-batch` 自帶的無頭瀏覽器，每包各一個，不占這個名額。

主線起的服務依「執行期資源收尾」登記。主線鎖定待驗候選版；視覺、互動、API、資料、權限與錯誤狀態證據對應當前候選版：任一修改只重驗受影響範圍、其連帶範圍與既定必要回歸，自動化測試只跑受影響範圍（不跑整套，結案只重測有聯動到的範圍，受監督時由監督跑），未受影響的舊證據附沿用核對後沿用（[共用規格](references/spec.md)不變量 7），不得未經核對拼接不同版本的 PASS；有畫面的成品每版用 `scripts/pixel-diff.js` 截各寬度長頁、與前一版比對；區段由獨立驗收者逐條驗收，結案由獨立驗收者重測聯動範圍並交付真人QA驗收腳本，主線不另跑全套人工回歸。

## 執行期資源收尾

並行派工閘只管「誰在用」；本節管「誰開、誰關」。主線或子代理啟動、會活過當下回合的資源（dev server、預覽 server、容器／compose 專案、其他常駐程序）一律經 `scripts/resource-ledger.py` 登記在 sidecar 同目錄的 `resources.json`：常駐程序用 `start --state <sidecar 目錄>/state.md --wp <id> -- <指令>` 啟動（獨立 process group，日誌在 `resources/`）；單一容器一律用 `run-container --state … --wp <id> --name <名> --ttl <時限> [--memory 1g] -- <docker run 的其餘參數與映像>`，一步完成啟動、任務標籤、登記與到期時間，不直接 `docker run`；`docker compose up -d` 等自行脫離的資源，啟動後立即 `register --compose-project <名>`；工作包專用與整合候選版的 worktree 建好當下就 `register --worktree <路徑>`（任務期間建立、紀錄裡寫到卻沒登記的 worktree，守門算需處理）；`run-container` 參數裡還不存在的具名資料卷會先帶同一組任務標籤建立，已存在的不動。不以 `&`、`nohup`、`disown` 直接把程序丟到背景。這個任務建的映像，第一次建就 `register --image-repo <映像庫> [--host <主機>] [--keep <基準版本>]`；在測試環境等遠端主機用 ssh 起的容器 `register --container <名> --host <主機>`，之後停止、移除與核對都經同一台主機。新候選部署並讀回後跑 `prune-images --id <r>`：保留最新兩版（部署中與上一版）、容器在用與指定保留的版本，其餘刪除並記進 `deletions.md`；還有可刪的舊映像時守門算需處理（使用者 2026-11-28；工區 E 在 Mac 留下 11 個、Staging 16 個舊映像，Staging 磁碟用到 79%）。

`run-container` 的容器到期（從建立或最後一次續期起算）只停止這一個、不刪除；還要用就 `renew --id <r> --ttl <時限>`。記憶體資料庫與正式資料副本（參數含 tmpfs，或加 `--protect`）到期不自動停，只由主線 `stop`。到期計時不跨重開機：重開機後要續用的先 `renew`，否則只由守門提示已過期（使用者 2026-11-16 定案；2026-11-14 實測 316 個已停止容器與 4 個沒標籤的容器沒人收）。

關閉時點預設 `--close wp`：所屬工作包判定（PASS／FAIL）後，主線 `stop --wp <id>` 關閉並核對已停止；判定 PASS 且不再需要的容器與 worktree 加 `--remove` 一併移除（worktree 另加 `--integrated-into <候選版 commit 或分支>`，分支不刪）。程式只移除所屬工作包 PASS、識別值沒被驗收結果帳、`evidence/` 與決策帳引用，且 worktree 已整合、沒有未提交變更的資源，每筆先記進 `deletions.md`、刪後讀回；不符的只停不刪並說明原因，不是 PASS 的停止滿 24 小時後，`stop --remove` 先把不含環境變數與主機設定的容器資訊存進 `evidence/`，日誌留在容器所在主機的受限資料夾（遠端 `/var/tmp/long-task-container-logs`，本機 `LONG_TASK_HOME` 下的 `removed-container-logs`），`evidence/` 只記位置、行數與雜湊，存不了就不移除；用 `register --host` 事後登記的遠端容器沒有任務標籤，以登記時的容器 ID、名稱與建立時間核對身分，24 小時從容器實際停止時間算起；判定後還沒移除的容器守門算需處理。主線自用服務用 `--wp 主線 --close final`，宣稱完成前關閉；只有要交使用者驗收的最終候選版預覽可用 `--close acceptance --reason <理由>`，未給 `--ttl` 時 72 小時到期自動關，驗收後由主線 `stop --id <r>`；確定不屬本任務者用 `--close external --reason <歸屬>` 只登記不關。子代理自行啟動的服務在交回前 `stop`，工作包明列保留者除外（回報附 resource id）。

**子代理用完即封存**（Codex App；使用者 2026-11-17 定案）：App 替每個子代理對話常駐兩個 node_repl（合計約 19MB），子代理結束後不會釋放，只有封存對話或重開 App 才收回（2026-11-17 實測：306 個合計約 2.9GB；封存後 20 秒內結束）。確定不再交辦某個子代理時（區段結束或換程式區塊後不再沿用、不合格後改開新子代理、模型換站後舊站子代理交件），派出它的一方（主線，或派出它的子代理）當下執行 `node <監督技能目錄>/scripts/subagent-archive.cjs plan --agent <子代理名稱>`，對回傳 `archive` 清單內每個 threadId 呼叫 App 工具 `set_thread_archived`（`archived:true`），再執行 `subagent-archive.cjs verify <threadId…> --log <sidecar 目錄>/archived-agents.jsonl` 讀回並留紀錄；`verify` 回 1 就重新封存未生效的那幾個。還要追問、等返工或仍在執行的子代理不封存；`plan` 只列已結束回合的子代理，連同它自己派出、也已結束的子代理，仍在執行或底下還有子代理在跑的會列在 `skip` 並寫明原因。原包需追問、補件或退回時，封存過的子代理仍可直接用 followup 處理原包，不必先解除（2026-11-17 實測照常回覆，且維持封存）；它的紀錄改寫在 `~/.codex/archived_sessions/`，監看與完成喚醒連同這裡一起讀，續派後的進度與完成照常追蹤；要讓它回到側邊欄，才用紀錄裡的 threadId 呼叫 `set_thread_archived`（`archived:false`）。宣稱完成前執行 `plan --all`，把剩下已結束的子代理一次封存並 `verify`。封存只收回 App 替子代理開的程序，不動工作區、資源帳本與證據。

`sidecar-guard.py` 每次派工前與判定後同時核對帳本與實況（另外列出本任務已停止還沒移除的容器，以及任務期間啟動卻沒有任務標籤的執行中容器；這兩種只提醒、不算需處理），並掃描從 Goal 建立到 sidecar 最後寫入之間（所以先更新 sidecar 再跑守門）出現在任務範圍內（專案根；sidecar、`archive.md`、`wp/*.md` 裡的 `path:` 工作區；紀錄裡提到的同 repo worktree，含整合候選版）、已脫離對話（父程序是 1）卻未登記的程序，以及 working_dir 在同範圍內或帶 `lt.task` 標籤的容器。已判定工作包的資源仍在執行、宣稱完成時 `wp`／`final` 資源仍在執行、`acceptance`／`external` 缺理由，或有未登記資源時回 4，主線關閉、補登記或改標並寫理由後重跑，不等待使用者。守門只報告、不自動關閉；`stop` 只作用於帳本內且啟動時間核對相符的資源，launchd 常駐服務、Goal 建立前已在執行的服務與其他任務帳本內的資源不列入、不關閉。

**測試瀏覽器與 worktree 結案**：測試自行開的瀏覽器在逾時或中斷時可能留下來（2026-11-18 一支前一天啟動的 Chrome for Testing 父程序已結束仍在跑）。守門把四項條件都符合的標成「reap 可收」：父程序已結束、工作目錄在本任務範圍、`--user-data-dir` 在系統暫存目錄、啟動時間在任務建立之後。主線看到就跑 `resource-ledger.py reap --state <sidecar 目錄>/state.md`，宣稱完成前必跑一次；它只關符合四項的瀏覽器（連同同組輔助程序），關前關後記進 `reaped.jsonl`，其他脫離程序照舊只報。宣稱完成前 `check --final` 也核對登記的 worktree：已 PASS、乾淨、已整合（或已在遠端）且沒被證據引用的要先 `stop --remove`；有未提交內容或未整合的列為保留並寫明原因，不擋完成（使用者 2026-11-18 定案；當天 ~/worktrees 287 個目錄、多數從沒登記）。

**工作包資料夾回收**（使用者 2026-11-19 定案）：重複使用的輸入（樣本文件、基準資料）全任務只放一份；工作包要自己的一份時用 `cp -c`（macOS 的寫入時複製複本：路徑、內容與讀寫方式不變，有改動的部分才另外佔空間；Linux 用 `cp --reflink=auto`），不整份複製；同一包內重跑整套輸出時覆寫，或只留最新一份與被引用的那幾份。非 git 的工作包資料夾建好當下就 `register --state <sidecar 目錄>/state.md --wp <id> --workdir <路徑> --keep <樣式>…`，`--keep` 列出交件標記、結果、回報、腳本與紀錄（例如 `DONE`、`result*.json`、`report*.md`、`scripts/*`、`logs/*`）。工作包判定 PASS 後，主線當下執行 `prune --state … --wp <id> -- <過程檔…>`，真的刪掉可重建的過程檔：輸入複本、演練工作區、被新版取代的整套輸出、建置產物；沒有可刪的用 `--none --reason <原因>` 記一筆。程式逐項核對在登記的資料夾裡面、不符合 `--keep`、沒被驗收結果帳、`evidence/` 與決策帳引用（受監督時加 `--search <RUN 目錄>`）、沒有程序在用，先記進 `deletions.md`、刪後讀回，不符的保留並說明；FAIL 或還沒判定的一律不刪，留作診斷。宣稱完成前 `check --final` 把已 PASS 卻沒 prune 也沒 `--none` 的工作資料夾列為需處理；任務期間建立卻沒登記的非 git 工作資料夾只列出提醒（2026-11-19 實測：一個實跑區 1,297 個已交件工作包佔 78.5GiB、一天多 19GiB，39,727 個 PDF 只有約 67 種內容；技能原本只規定回收容器、worktree、程序與子代理，沒規定工作包資料夾）。

**任務自己的暫存**（使用者 2026-11-19 定案）：測試與建置一律把暫存位置指到工作包自己的資料夾：`TMPDIR="$(python3 scripts/resource-ledger.py tmpdir --state <sidecar 目錄>/state.md --wp <id>)" <測試或建置指令>`（包在 `test-run.py` 裡跑時，`TMPDIR=…` 放在整道指令最前面）。瀏覽器設定檔、驅動暫存與測試框架的暫存都會落在 `/tmp/lt-<任務代碼>/<工作包>`（路徑短，unix socket 放得下；同一工作包重複呼叫回傳同一個）。工作包判定後 `stop --wp <id>` 把它整個刪掉並記入 `deletions.md`；還有程序在用就不刪、回 4，先關掉該程序再 `stop`。系統暫存區裡不是 `tmpdir` 建立的內容不碰；證據與測試結果不放暫存。守門把已判定工作包還留著的任務暫存列為需處理（2026-11-19 實測：重開機後 12 小時系統暫存區累積 12,291 項、2.24GiB，測試結束不會刪，只有重開機才清）。

## 路徑枚舉閘（找 X／確認沒有 X 型任務）

目標是「找出符合條件的 X」或「確認沒有 X」時，主線在深入任一候選或派工前，先在 sidecar「候選全集」寫出搜尋空間：每個條件維度（地區、標籤、類型、日期／時段等）的取值與來源、展開後的候選清單與筆數；清單沒寫完不得深入任何一個候選。每個候選用同一判準驗證：有 UI 的候選必須真實操作到底並保存可視畫面；純程式碼、檔案、DB 或 API 候選則以其原生來源的端到端查核、查詢或測試結果落檔。單一內部旗標、DOM 狀態或未走完的局部訊號只能當線索，不得當結論。宣稱「完整」「窮舉」「全部」時必附「候選 N／已驗 N／未驗 N＋原因」，數字對不上不得宣稱。使用者指定的範圍（日期、時段、地區）鎖進原始目標，不得為了找到結果而擴大；要擴大先問。

## 模型

主線沿用使用者實際選定的模型，監督交辦時執行主線使用同一完整 ID（預設 Opus xhigh）。依[模型路由](../long-task-supervisor/references/model-routing.md)從當回合派工工具的可見清單解析。子代理照子代理順位 Sonnet（Claude 訂閱）→ Sonnet（Claude API）→ Terra（OpenAI 訂閱）→ Terra（OpenAI API）→ DeepSeek → Muse，由背景程式依額度與限速決定當下第一站；主線在哪一家都照這條順位（使用者 2026-11-28，靠 OpenCodex 的 plaintextV2AgentMessages）；背景程式讀到這個設定沒開時，主線在 OpenAI 訂閱（Sol、Terra）上的子代理只能用 Terra 訂閱；一般包以 medium 起跳（開源固定 max），介面包以 low 起跳，明列 model 與 reasoning_effort。介面子代理需具備所需瀏覽器、視覺與實際操作能力。Goal 續跑／恢復沿用已鎖定模型，另有使用者新選擇或原模型失效時重新解析。精確指定與成本限制以使用者授權為準。角色缺少可用模型時，只標記該角色受阻並繼續其他工作。限速處置與恢復沿用既有流程。

## 檢查與證據

使用者 2026-11-09 要求找出長任務最花時間的地方：檢查比開發花得多，其中不少是每次手寫雜湊、索引與讀回腳本，把整份測試輸出貼回對話，以及每幾秒查一次長測試。以下做法取代這些手工步驟：

- **固定檢查指令**：雜湊、證據索引、正式環境讀回與驗收條件對照一律用 `scripts/evidence-check.py`，不另寫一次性腳本。`hash 路徑…` 印每個檔案的 SHA-256 與大小；`index 證據目錄 --out 索引.json` 建證據索引；`readback 網址或檔案 --expect 文字 [--sha256 值]` 讀回並核對狀態、預期文字與雜湊（不印內容與標頭）；`criteria 派工快照.json [--index 索引.json]` 列出每條驗收的狀態與證據，PASS 卻沒有證據、證據檔不在或索引後被改時 exit 1。
- **測試輸出精簡**：測試經 `scripts/test-run.py --log <證據目錄>/<名稱>.log [--timeout 分鐘] -- <原測試指令>` 執行：完整輸出寫進紀錄檔，畫面只印結果、總數、失敗行與紀錄檔雜湊，同名 `.summary.json` 就是這次測試的證據。整套測試、建置與預估超過 5 分鐘的加 `--slot long`：本機設了重型工作名額時在這個指令內排隊，排隊時間不計入逾時，名額留一個給短測試；不要自行背景化或另寫排隊。回報與 sidecar 只貼這段摘要，不貼整份輸出。
- **長測試一次等到結束**：子代理跑長測試時用 test-run.py 設好逾時（預設 60 分鐘），用 `exec_command` 啟動後以 `write_stdin` 空輪詢、`yield_time_ms` 設 300000 一次等滿；不每幾秒查一次輸出。逾時 exit 124 屬執行問題，照原規則診斷，收件判定記 external、不計次。
- **證據分級**：低風險項目（內部畫面微調、文件、單元與定向測試）一行記指令、結果與版本；改驗收、正式環境寫入與對外發送才保留完整證據（原始輸出、截圖、讀回、雜湊）。結案的聯動重測照舊保存 test-run.py 的完整紀錄（受監督時由監督跑，紀錄在監督工作區）。
- **狀態一步寫入**：受監督時，工作包狀態、證據與驗收表用監督技能的 `dispatch.cjs mark`／`collect`／`from-wp` 一步寫入，不手寫 JSON、不另寫腳本改 `dispatch.json`、`acceptance-history.jsonl` 或工作包的 `[狀態]` 行（2026-10-14～15 GDB 主線只為記帳就用了 99 分鐘、506 個回合）；資源一律用 `scripts/resource-ledger.py`。

## 驗收與錯誤

主線保留最終 PASS／FAIL。前台驗收由主線提供待驗版本、起始狀態、操作、預期結果、資料／授權邊界與證據要求；介面子代理以真實事件操作並回報 PASS／FAIL／BLOCKED，不改程式、案例或設計風格。

**放行紀律**：判定只依 sidecar「驗收標準」逐條表。任一條不是 PASS 或「核准不做」，就不得對整體或階段宣稱 PASS、完成、達成或全部通過，也不得寫「附條件 PASS」；只回報進度與剩餘條目，未達成的條件記為部分或待決。「核准不做」須在核准變更記錄使用者原話與時間。條文的改寫、縮窄、放寬、更換對照基準，或改以單元測試、本機結果、較少輪次作證據，都屬條文變更，須先在核准變更記錄使用者原話與時間；沒有紀錄就照原條文判，且不適用待決事項的「採推薦選項」與「最接近的可逆解讀」。`scripts/sidecar-guard.py` 每次列出逐條表與最新核准變更；最終判定宣稱完成但仍有未達成條目，或寫了「附條件」時 exit 3，由主線改判定或補證據後重跑，不等待使用者確認。

子代理沿用或新開依「派工流程」第 5、6 步；確定不再交辦後依平台封存。

唯一實機或需排時窗者，正式派工前先在目標機一次核對投送檔、腳本語法、目錄及回執格式，把全部缺漏一起交回；正式實測 FAIL 計入該案例的驗收條文。受監督時見[正式案例與目標機回執](../long-task-supervisor/references/formal-cases.md)。

**不合格交付**（使用者 2026-11-23 定案，2026-11-26 改為六次循環）：收件判定採用、品質不合格或非子代理責任三選一；品質不合格按驗收條文累計，換工作包、換代理、續接或研究都不清零。第 1、3、5 次：指正交回剛交件的子代理同檔重做。第 2、4 次：程式擋下該條文，先派研究子代理（用執行主線當下的模型與推理）上網搜尋可行方案、唯讀分析並登記（程式核對研究子代理確實有搜尋），免研究要監督核可；第 2 次研究後開新子代理升兩檔（開源改派下一款），第 4 次研究後開新子代理用執行主線當下的模型與推理，研究後重做的第一步是驗證小實驗。第 6 次：研究登記後由監督登記待決題交使用者裁決，裁決前只停這條。主線全程不接手。完整規則、指令與欄位只寫在[不合格交付與研究](references/execution.md#不合格交付與研究)。

## 待決事項（不阻塞主線）

長任務期間，只要還有已授權、不需等回答的工作可執行，主線就不使用會停住整條主線的互動提問工具，也不在回合中途以純文字要求使用者先回答才繼續。需要使用者決定的事項寫入 sidecar「待決清單」，依類別處理：

1. 已確認範圍內、可逆且主線有推薦選項：採推薦選項繼續，記「已採預設」與改回方式；使用者之後選其他方案再改。
2. 不可逆、付費、刪除、登入／憑證、對外發送、超出已確認目標或範圍的變更，或未受監督時上層規則明定必須事前確認的重大內容／設計變更：只把該動作記 `BLOCKED` 並附推薦方案，其餘已授權工作照常；先前明確授權已涵蓋者照授權執行；其餘才須使用者確認。 長任務另有使用者 2026-10-29 的[預設類別授權](../long-task-supervisor/references/authorization.md#長任務預設類別授權)：Git 操作（commit、merge、push、PR、tag）、標明「測試」的對外發送、開工已授權的帳號密碼／付費／正式部署直接做；仍要確認的只剩改驗收條件、刪除或永久改動既有資料、開工沒授權或超出上限的帳號密碼／付費／正式部署、改寫 Git 歷史（強制推送、刪遠端分支或 tag）、寄信與不是測試的正式對外發送、推翻禁令、使用者自設的核准關卡、要他本人到場或操作的事，以及沒有明確推薦的超出契約目標或範圍的變更（受監督時有明確推薦、不碰前述各項者由監督照推薦代決，使用者 2026-11-13 定案）；未受監督時另含經核對適用的上層規則仍要求事前確認的重大內容／設計／資訊架構變更。受監督時，前述預設類別先核對本案有效契約、授權與專案限制，需要決定的事以提問交監督：監督依[依規格代決](../long-task-supervisor/references/authorization.md#依規格代決)在契約範圍內直接決定（設計、資訊架構、參數與預設值、順序、測試細節等），只有上述底線才轉問使用者。使用者自設的核准關卡只擋依賴它的工作，等待期間照契約或監督指示繼續其他工作。本任務自己產生的測試中間產物已有使用者預設授權：必要時記入刪除清冊後直接刪，不列待決；可刪範圍、一律不刪的歷程、子代理限制與禁令範圍見[測試中間產物的刪除](../long-task-supervisor/references/authorization.md#測試中間產物的刪除)。
3. 專案文件、規格、runbook 或 sidecar 既有決策查得到答案：先查，不列待決。
4. 受監督時，可撤回且自己有推薦的執行細節不等監督答覆：照推薦先做並繼續其他工作，回合結束時補報做了什麼、怎麼改回，監督答覆不同再照答覆改（使用者 2026-11-13：「有推薦就照推薦做，連30分鐘都不要等」）；第 2 類仍要確認的事不適用，只停該動作，等待期間做與它無關的工作。

已回答的事項不重問；回答不明確時採最接近的可逆解讀，並標「待確認解讀」。只有主線無事可做、沒有已就緒可派包、也沒有可整合或驗證的成果時，才在回合結尾一次列出全部待決事項、推薦選項與選其他方案的後果，然後結束回合。

**授權續接**：依[授權承接與更新](../long-task-supervisor/references/authorization.md)，派工時附使用者原話、原始對話／訊息定位、操作與資料目的地、條件及禁令；接收端核對原始來源後承接同一授權，不要求使用者在每個子對話重說。先讀使用者最新原話、類別授權與禁令，再決定是否提問。明示持續授權的 Git 操作保留可回復紀錄後直接做；已授權瀏覽器登入先實際取用既有登入，不能只看到「登入／權限」就要求使用者介入。新授權解鎖的待辦當輪重新派工。

**發布授權核對**：對 merge、push、PR 合併、tag、Release、部署等動作，在第一次寫入 sidecar 時逐項記錄使用者原話與時間、儲存庫、來源／目標分支或部署環境、允許的候選變更範圍及放行條件；未明示者記「未授權」，不得把「完成上線」自行擴成整套 Git 發版。已授權的發版動作也只在定版後做一次：中途候選以 commit 部署，不合併發版分支、不打版號、不發 Release。候選版完成後，先給可審查的實際差異與測試結果；執行每項不可逆動作前，比對當下分支、候選提交、目標及條件，將實際提交記入表中。全部符合既有授權就直接執行、不重問；有新增動作、範圍或目標改變，或條件未過，只停該動作並一次提出具體差異。已問而尚未答的核准題沿用原題，不在續接回合重提，也不把單一待核准動作冒稱整個 Goal 的新故障；只有平台的 Goal 狀態規則確實要求時才標記整體 blocked。授權依使用者明示的範圍與期間；單次候選授權不自動延伸，明示涵蓋本任務後續修正的持續授權也不得自行縮成單次。

**提問紀律**：Goal 或任務描述已授權的工作（例如「發現缺陷就修復並上線」），其要不要修、怎麼修、畫面說法怎麼改，若在範圍內、可逆且有推薦選項，屬第 1 類，直接採推薦並記「已採預設」，不提問。使用者要求逐項確認時，只提出第 2 類事項與驗收條文變更，集中一次提出、不另增題目；已採預設的事項列成清單供使用者覆核。提問前先查待決清單、核准變更與使用者先前的定調，查得到答案的不問。每個提問須能單獨看懂：寫明畫面上看到什麼、後果是什麼，並附一個真實案例。

子代理不得修改正式規格、操作 Git、進行未獲使用者明確授權的對外發送或替使用者拍板；技術子代理只能修改工作包授權的原始碼，未經工作包明列授權不得安裝／移除套件、改 lockfile 或套件管理器、重啟共用服務或刪除別人建立的測試中間產物（自己在本包建立、位於 `[工作區]` path 或自己 scratch 內的檔案可刪並在回報列出；證據與測試結果一律不刪），migration 等全域編號由主線配發。所有不可逆或敏感操作仍依上層授權規則。
