# Goal 長任務協作

本 adapter 實作[共用規格](references/spec.md)，只管理 Goal 的分工、鎖定、驗收與續接。已有 Goal 就沿用；僅在使用者明確要求時建立 Goal 或設定 Token 預算。子代理不得建立或更動父 Goal。使用者最新明確指示與上層授權優先。

**監督中的執行對話**：若啟動訊息由 `long-task-supervisor` 指定精確監督對話、驗收契約及來源，照本技能原有的派工、隔離、品質錯誤與同版自查流程執行；這種交辦本身不等於要求建立原生 Goal。驗收條文只讀監督鎖定的契約，不自行縮窄。每次最終回覆末尾依監督技能的 [事件協定](../long-task-supervisor/references/runtime.md#執行對話的事件) 放一行 `LONG_TASK_EVENT`：有未完工作用含具體 `nextAction` 的 `progress`，需代答用 `question`，只剩未授權動作用 `blocked`，本地自查通過後用監督技能 `scripts/candidate.cjs` 產生候選清單與完整 `submission` 事件行，原樣貼上，不手寫雜湊。未收到監督逐條接受前，自己的 PASS 只表示「已送驗」，不得向使用者宣稱整體完成；退件沿原候選版修正再重交。

監督綁定完成後，依[派工快照協定](../long-task-supervisor/references/dispatch.md)在拆包、派出、收回／整合、依賴或資源變化及等待前，用監督技能 `dispatch.cjs write` 原子更新指定 run 的 `dispatch.json`。只記實際工作包、代理 handle、已核實容量與排他資源；先執行可做的工作，再向監督回報，不能為等待快照核准停住。收到 `dispatch_review` 指示時先查最新狀態，已完成或失效的指示不重做；結果一回來就核對並補派，不等整批。未綁定監督的單對話任務不需此快照。

## 啟動與續接

1. 依序讀本技能、[執行協定](references/execution.md)、原生 Goal，再找專案根目錄 `.codex/long-task/` 的 sidecar。使用者指名者優先；其次以原生 Goal id 精確匹配，無 id 時以 objective 原文與 SHA-256 匹配。多個未完成 sidecar 無法精確匹配時必須請使用者指定，不得以最近更新者猜測。原生 Goal 管理目標、狀態與 Token 預算；sidecar 保存 Goal 綁定、模型鎖定、工作包、錯誤次數與證據。沒有匹配 sidecar 時，依執行協定建立。
2. 新任務先鎖定原始目標、可判定的驗收標準（照 `templates/state.md` 寫成逐條表：條文原文、狀態、證據、核准依據）、候選版、角色模型與推理，寫入 sidecar 後才派工。「找 X／確認沒有 X」再先完成候選全集。同時盤點完成目標必需、只有使用者能提供或授權的前置（權限、帳號與憑證、付費或資源開通、主機與網域、不可逆或對外操作的授權、需使用者拍板的取捨）；先核對本次任務及先前對話的明確授權，逐項寫入 sidecar「發布授權」表。未授權項才進待決清單（類別「前置」），在啟動時一次列出；列出後不等回答，先做不依賴前置的工作。
3. 上下文被壓縮、Goal 恢復或對話續接後，先依「本技能 → 執行協定 → 原生 Goal → 精確匹配的 sidecar」重建狀態，再派工或判定；自動摘要不是規則或狀態來源。
4. Goal 完成條件若只是任務描述、無法客觀判定，在第一則回覆提供一句可判定條件供使用者改設；使用者不改也照走，不自行覆蓋 Goal。

## 分工與路由

任務可同時屬於 A、B、C；網頁預設 A＋B，只有完全無互動且無後端的純靜態頁只走 A。研究或系統規劃只走 C；需要正式文件的視覺排版時，另併用 A。

| 工作線 | 主執行緒 | 子代理 |
|---|---|---|
| A 視覺／設計：網頁視覺、圖片、簡報、PDF | 設計、排版、風格判定、修正與最終驗收 | 解析素材／來源並客觀查核真實畫面的裁切、遮擋、溢出、可讀性、對齊、響應式與已鎖定規格；不改成品、不判定風格 |
| B 系統／技術 | 定義需求與驗收、拆包派工、查核證據、最終判定；僅同一技術包錯 3 後接手實作 | 一般子代理實作前端邏輯、後端、資料整合、修復與必要測試；介面子代理只按案例操作前台並蒐證 |
| C 研究／系統規劃 | 鎖定研究問題、來源與截止時點；核對關鍵原始證據，判定系統取捨與架構，撰寫正式規劃文件 | 各自蒐集指定議題的來源、反證、比較與待確認事項；不替主線拍板、不修改正式文件 |

並行只限可修改範圍與實際共用資源都互斥的工作包：每包 prompt 必有 `[可修改範圍]` 與 `[共用資源]`（套件／lockfile、migration 等全域編號、worktree／整體測試套件、開發伺服器／資料庫／測試資料／帳號、瀏覽器工具）。`[共用資源]` 只寫實際會讀取、鎖定或改動的正值；「不使用／不安裝／不修改」寫在 `[禁止事項]`，不得當成共用資源來製造假衝突。每批派出前，以 `scripts/scope-overlap.py` 比對本批與所有在途包，exit 0 且結果記入 sidecar「並行批次」後才並行派出。

**積極派工（可派即派，不留空席）**：主線完成拆包與依賴後，每輪先找出所有依賴已滿足的工作包，連同在途包過並行派工閘，再依「先做會解鎖最多後續工作的包」優先，派到平台當下可用的子代理席位用滿為止。不得先只派一包「看看情況」，除非該包的結果會改寫其他包的範圍或判準。任一子代理完成後，不等同批其他包：先更新 sidecar、處理該回報解鎖的依賴，當輪立即補派下一批已就緒工作。主線在子代理執行期間繼續做整合、確定性操作、驗證與下一批準備；只有主線也無事可做、所有已就緒包都已派出時才純等待。等待平台不會主動通知的外部結果（CI、遠端排程、主機或外部系統上的長程序）時，先以背景程序掛上有間隔與逾時、結果出現或逾時會喚醒主線的監看，才可結束回合；不得在沒有喚醒機制時以「等某事完成後再做」結束回合。

不為了填滿席位硬切零碎包：每包仍必須有可獨立交付的結果、能與主線有用工作同時進行，且交接與驗收成本不高於代理工作本身。若當下只有一包就緒，或其他包都有真實依賴／資源衝突，依序執行才是正確行為，並在 sidecar 記錄不並行的理由。

多個 B 技術包要並行修改 Git 專案時，主線預設為每包建立互相隔離、綁定同一 base commit 的 worktree，並在工作包與 sidecar 記錄 worktree 路徑與識別值；只有確定不會修改程式、不跑會讀取其他 dirty 檔案的整體測試、且實際資源互斥時，才可共用工作區。子代理仍不操作 Git；主線驗收後才將授權檔案整合進單一 canonical candidate，並遵守上層 Git 確認規則。共用同一 worktree 或同一整體測試工作區就是真實衝突，不得靠「不碰對方檔案」解除。有交集就隔離資源、加依賴改依序，或把共用項切給唯一一包。同一個瀏覽器工具或登入狀態同一時間只派一個介面子代理；要並行就各用隔離的瀏覽器與帳號。

主線可自做確定性的操作型步驟（跑既有指令、起服務、查資料）並在 sidecar「主線自做」登記理由；新增／修改程式或資料轉換邏輯一律派技術包，錯 3 前不得自己動手。主線鎖定待驗候選版；視覺、互動、API、資料、權限與錯誤狀態證據必須屬於同一版號或雜湊，不得拼接不同版本的 PASS。任一修改只重驗受影響項目與既定必要回歸。

## 路徑枚舉閘（找 X／確認沒有 X 型任務）

目標是「找出符合條件的 X」或「確認沒有 X」時，主線在深入任一候選或派工前，先在 sidecar「候選全集」寫出搜尋空間：每個條件維度（地區、標籤、類型、日期／時段等）的取值與來源、展開後的候選清單與筆數；清單沒寫完不得深入任何一個候選。每個候選用同一判準驗證：有 UI 的候選必須真實操作到底並保存可視畫面；純程式碼、檔案、DB 或 API 候選則以其原生來源的端到端查核、查詢或測試結果落檔。單一內部旗標、DOM 狀態或未走完的局部訊號只能當線索，不得當結論。宣稱「完整」「窮舉」「全部」時必附「候選 N／已驗 N／未驗 N＋原因」，數字對不上不得宣稱。使用者指定的範圍（日期、時段、地區）鎖進原始目標，不得為了找到結果而擴大；要擴大先問。

## 模型

每個新 Goal 在角色首次需要時，以目前主機可用的 OpenAI 通用／代理模型解析並鎖定：

- 主線：GPT-6 Sol；High。技能不能切換已運行的主模型。
- A 視覺查核、B 技術實作、C 研究子代理：GPT-5.6 Terra；Medium。既有技術與研究工作包有通過主線驗收的紀錄；尚無相同工作包的 GPT-6 替代模型速度與總成本對照。
- 介面子代理：具備所需瀏覽器、視覺與模態能力者中，以整個工作包預期總成本最低者；Low。
- 新工作包一律從基準推理起跳，不得因預估難度預先派高一檔；太難就拆包。

使用者明確指定優先；否則依「當前 session／主機實際模型資訊 → 主機可用模型目錄與產品定位 → 官方 OpenAI 文件」核對模型、必要工具與推理檔次，不可用時記 `BLOCKED` 並揭露，不自行換成其他模型。Goal 續跑／恢復沿用已鎖定模型；只有使用者改變政策、模型失效或原鎖定缺失時才重解析。實際主線不是 GPT-6 Sol High 時揭露差距；除使用者明確指定沿用外，不建 sidecar、不派工、不判定。派子代理時明確指定鎖定模型與當次推理。

## 驗收與錯誤

主線保留最終 PASS／FAIL。前台驗收由主線提供待驗版本、起始狀態、操作、預期結果、資料／授權邊界與證據要求；介面子代理以真實事件操作並回報 PASS／FAIL／BLOCKED，不改程式、案例或設計風格。

**放行紀律**：判定只依 sidecar「驗收標準」逐條表。任一條不是 PASS 或「核准不做」，就不得對整體或階段宣稱 PASS、完成、達成或全部通過，也不得寫「附條件 PASS」；只回報進度與剩餘條目，未達成的條件記為部分或待決。「核准不做」須在核准變更記錄使用者原話與時間。條文的改寫、縮窄、放寬、更換對照基準，或改以單元測試、本機結果、較少輪次作證據，都屬條文變更，須先在核准變更記錄使用者原話與時間；沒有紀錄就照原條文判，且不適用待決事項的「採推薦選項」與「最接近的可逆解讀」。`scripts/sidecar-guard.py` 每次列出逐條表與最新核准變更；最終判定宣稱完成但仍有未達成條目，或寫了「附條件」時 exit 3，由主線改判定或補證據後重跑，不等待使用者確認。

品質錯誤只指代理交付本身錯誤、漏步驟、缺必要證據、誤讀判準或未依指示：

1. 錯 1：主線具體指正，同一鎖定模型升一個受支援推理檔次，重派同一工作包。
2. 錯 2：再次指正、再升一檔、重派同一工作包。
3. 錯 3：停止該工作包的子代理鏈，不作第四次派發；主線接手未完成部分並復用正確成果。

若品質錯誤後沒有更高的受支援推理檔，保留已累積的錯誤次數並記為執行阻塞；不得以相同檔次冒充升檔，也不得因此提早讓主線接手。取得可用升檔能力後再從同一工作包續派。

A 查核、B 技術、C 研究、介面操作各自計數，換代理、改名或恢復對話不清零。視覺代理如實發現成品問題不算它錯，由主線修 A；介面代理如實發現產品 FAIL 不算它錯，退回原 B 技術包；研究代理如實回報來源衝突或未證實事項不算它錯，由主線決定後續研究或取捨。工具、模型容量／路由、權限、來源、逾時或需求變更是執行問題，不計品質錯誤、不升檔，也不得冒充錯 3 讓主線接手技術實作。

## 待決事項（不阻塞主線）

長任務期間，只要還有已授權、不需等回答的工作可執行，主線就不使用會停住整條主線的互動提問工具，也不在回合中途以純文字要求使用者先回答才繼續。需要使用者決定的事項寫入 sidecar「待決清單」，依類別處理：

1. 已確認範圍內、可逆且主線有推薦選項：採推薦選項繼續，記「已採預設」與改回方式；使用者之後選其他方案再改。
2. 不可逆、付費、刪除、登入／憑證、對外發送，或上層規則明定必須事前確認的重大內容／設計變更：只把該動作記 `BLOCKED` 並附推薦方案，其餘已授權工作照常；該動作仍須使用者確認才執行。
3. 專案文件、規格、runbook 或 sidecar 既有決策查得到答案：先查，不列待決。

已回答的事項不重問；回答不明確時採最接近的可逆解讀，並標「待確認解讀」。只有主線無事可做、沒有已就緒可派包、也沒有可整合或驗證的成果時，才在回合結尾一次列出全部待決事項、推薦選項與選其他方案的後果，然後結束回合。

**發布授權核對**：對 merge、push、PR 合併、tag、Release、部署等動作，在第一次寫入 sidecar 時逐項記錄使用者原話與時間、儲存庫、來源／目標分支或部署環境、允許的候選變更範圍及放行條件；未明示者記「未授權」，不得把「完成上線」自行擴成整套 Git 發版。候選版完成後，先給可審查的實際差異與測試結果；執行每項不可逆動作前，比對當下分支、候選提交、目標及條件，將實際提交記入表中。全部符合既有授權就直接執行、不重問；有新增動作、範圍或目標改變，或條件未過，只停該動作並一次提出具體差異。已問而尚未答的核准題沿用原題，不在續接回合重提，也不把單一待核准動作冒稱整個 Goal 的新故障；只有平台的 Goal 狀態規則確實要求時才標記整體 blocked。授權只限本次範圍，不延伸到後續版本。

**提問紀律**：Goal 或任務描述已授權的工作（例如「發現缺陷就修復並上線」），其要不要修、怎麼修、畫面說法怎麼改，若在範圍內、可逆且有推薦選項，屬第 1 類，直接採推薦並記「已採預設」，不提問。使用者要求逐項確認時，只提出第 2 類事項與驗收條文變更，集中一次提出、不另增題目；已採預設的事項列成清單供使用者覆核。提問前先查待決清單、核准變更與使用者先前的定調，查得到答案的不問。每個提問須能單獨看懂：寫明畫面上看到什麼、後果是什麼，並附一個真實案例。

子代理不得修改正式規格、操作 Git、對外發送或替使用者拍板；技術子代理只能修改工作包授權的原始碼，未經工作包明列授權不得安裝／移除套件、改 lockfile 或套件管理器、重啟共用服務，migration 等全域編號由主線配發。所有不可逆或敏感操作仍依上層授權規則。

派工、前台案例、模型解析、恢復與證據欄位的操作細節，僅在實際需要時讀[執行協定](references/execution.md)。行為驗證見[行為案例](references/behavioral-cases.md)。
