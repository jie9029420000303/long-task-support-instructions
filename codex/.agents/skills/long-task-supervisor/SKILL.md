# 長任務監督

**目前對話就是監督對話。** 先讀 [啟動與事件協定](references/runtime.md)。監督接管本對話已定案的目標、驗收和授權；未定案的備選方案不可混入。除有真正歧義，不要求使用者重述研究，也不另建一個監督對話。使用者已明確要求建立執行對話時可建立；已指定既有對話時只綁定該對話。使用者只須保留這個對話作為主要入口。

## 啟動

1. 完整核對已定案原文、專案規則及驗收來源。逐條建契約，記來源位置與 SHA-256；對話內容先保存含訊息識別的原文摘錄。技術修復、已定案答覆及發送給指定執行對話的監督指示沿用本次授權；新的商業取捨與不可逆操作照上層規則處理。
2. 擬好可直接執行的 prompt，要求執行者使用 `goal-orchestrator` 的派工、隔離、自查與恢復能力，並依 [事件格式](references/runtime.md#執行對話的事件) 送驗。明寫「問題交監督依契約查證並代答；只有具體未授權操作才暫停該操作，其餘工作續行」；送出前檢查並刪除舊 prompt 中「監督會把問題轉成使用者選擇題」等相反指示。沒有使用者明確要求 Codex 原生 Goal 時，不建立原生 Goal。
3. 建立或綁定執行對話前，依[模型路由](references/model-routing.md)核對監督實際模型：Claude 監督以實際模型前綴 `anthropic-apikey` 或 `anthropic` 鎖定本次系列，執行主線 Opus 與子代理 Sonnet 均沿用該系列，不依全域預設跨系列選模；新建對話明傳 model／thinking，既有對話在安全回合邊界套用，使用者明確指定優先。把路線交給執行主線，再由其核對子代理工具清單。
4. 先找使用者已指定的執行對話；沒有時，只有使用者在本次要求中明確授權「建立／啟動另一個執行對話」才以 Codex App 的 `list_projects` 定位本專案並用 `create_thread` 建立。授權原文、來源位置、可建立的專案與用途寫入契約；沒有這項直接授權就停在建對話這一步，先完成契約、prompt 與其他唯讀準備，不把一般「監看」自行擴成建立新 task。預設同專案 local 對話；只有使用者明確要求才使用 App worktree。取得真實 threadId 後才綁定，不把預備中的 clientThreadId 當目標。往執行對話傳送啟動 prompt、代答、退件與續接，也只能在同一份直接授權明確涵蓋跨對話傳訊時進行；每次仍保存精確收件證據。
5. 用 `scripts/supervise.cjs init` 鎖定契約、兩個精確對話及可讀取的工作區；啟動本機監看，取得 `native-ready.json`、首次讀到執行對話及 `status.active=true` 才說「已啟動」。若本機 App 通道受權限限制，依工具正常的權限流程處理；失敗就明說尚未啟動，不能只憑 PID 或技能載入狀態宣稱成功。

## 工作分工

- 執行對話是唯一開發主線：派子代理、整合候選版、自測、修正和送驗。監督不得同時改執行者的檔案；必要的獨立測試及證據放在監督工作區。
- 背景程式處理等待、精確事件、送出後讀回、去重與重連。普通 `progress` 依下一步發一則短續接；純背景等待用 `waiting` 或 `progress + waitMinutes`，到期前不傳續接，等待期間仍跑獨立進度時鐘，結果改變或期限到才喚醒。等待文字若夾帶使用者授權、push／merge／發布等阻塞，一律轉交監督，不能藏在等待。重複停滯、提問、送驗、異常、意外結束，或監督自己的進度時鐘發現問題時，把短事件送回本對話。事件送達後若 45 秒仍沒有監督模型輸出且 decision 不存在，背景程式只補一則指向原事件的喚醒訊息，不重送業務事件；STOP 優先且每事件至多一次。平常由本機常駐程式無模型地監看，不定時啟動模型。**主動追蹤**：依[主動進度查核](references/runtime.md#主動進度查核)，時鐘分層查核：程式先確認工作有在動（兩個對話、執行端子代理、在跑的測試程序），再比對派工快照的 AI 時程基準，每 30 分鐘留紀錄；只有全部靜止 15 分鐘、在途包超過基準 1.5 倍且該包 15 分鐘沒有新增產出，或沒有基準、測試程序 15 分鐘沒有產出、同一指令連續失敗 3 次或同一下一步連報兩次，才喚醒模型。時程基準一律以本場模型實測每秒輸出 token 推估（`scripts/pace.cjs`），不用人類開發經驗；執行端寫進派工快照，監督用同一公式重算。喚醒只帶事件識別及 `scripts/supervise.cjs context RUN EVENT_ID` 指令；context 一次含 brief、相關事件與授權來源，進度事件不重載整份契約，依[單次事件處理](references/event-review.md)判定；證據不足時具體詢問執行進度／阻塞，查到落後或重複時發具體加速建議，有需要推進的具體指引才向執行對話發訊，進度正常只記錄、不傳訊。`executor_blocked` 只表示指令尚未返回，先核對真實工具錯誤，不推定缺授權；確認需要本人放行，或確有電腦睡眠時，再告知具體處理方式。不可重問既有授權或空泛催促。不要用排程反覆投放整段 prompt，也不要讓模型回合持續 sleep 或輪詢。
- 監督依原契約獨立檢查真實候選版和證據。每條皆須有同版實測依據。未通過就寫具體預期、實際、缺項及修正要求；全數通過才對使用者宣稱整體完成。執行者的「完成」字樣只視為送驗。
- 執行者的提問先由監督查契約、已定案對話、專案決策與真實環境。已授權範圍內選最可行的可逆做法，記下來源、代答與改回方法，直接送回原執行對話；提問本身不等於要使用者選擇。條款同意、DNS／正式發布、付費、push／merge 等先核對既有授權；確實未授權的具體動作才標待核准，指示執行者先完成其他工作。其他可做工作完成後，再集中向使用者呈現具體操作；不得為每個問題中斷他，也不得把待核准算 PASS。

監督在 run 工作區保存決策帳，逐項記執行者問題、依據、代答、待核准動作與送達證據；驗收完成時一次交代做過的決定。監督模型處理完事件後正常結束回合；本機監看繼續運作。停止或恢復先讀既有狀態和收件紀錄，送達不明不得盲重送。Codex App 或電腦不在運作時不宣稱仍有即時監看；重新啟動後依保存的 run 對帳續接。 **授權與來源核對**：規格列為必測／必做，不等於使用者已核准故障演練、真實資料寫入或對外發送；先查使用者直接授權的原文、目標資源、用途與副作用，缺授權只停該具體動作。代理查核、監督提案與使用者原話分開記，不把代理意見冒記為使用者要求；新增數值門檻只能作診斷線索，未核准不得變成驗收條件。

對執行者純確認或已知待核准事項，核對後使用 `observe`（記錄後繼續監看）決策，保存原因與仍待核准動作，不再向執行者發送「收到」而製造新回合。依 runtime 完成決策並維持背景監看；不得要求使用者先答業務核准題或再說「續監看」才接收其他新事件。待核准不等於已授權，靜默處理也不等於驗收通過。`progress_review` 核對後仍有可行工作或證據不足時用具體 `reply`；靜默類（`silence`、`wait_changed`）只剩已知且未變的等待時，依 runtime 用含查核來源及 `wait` 的 `observe`；其他原因核對後進度正常，用含查核來源的 `observe`。背景仍接收新事件。

本機常駐程式的子程序異常時由同一個無模型父程序重連；若持有 App 工具通道的整個父程序消失，不能宣稱仍在監看，也不能靠自己喚醒。下次 App 對話活動時須先依 run 的 PID／鎖、游標、待送及收件對帳後安全重掛；不得為此另設會定時啟動模型的心跳。

**授權續接**：啟動、續接與提問前，讀[授權承接與更新](references/authorization.md)，核對使用者最新類別授權及禁令。Git 已獲持續授權就留存可回復紀錄後直接執行；瀏覽器已獲授權就先實際取用既有登入，不把可自行處理的登入或 Push 轉問使用者。後續授權另存原文快照、更新待決帳並傳給原執行主線，不改原驗收契約。

**派工效率監督**：依[派工狀態與監督檢查](references/dispatch.md)，讓執行對話在拆包、派出、收回與等待前更新精簡快照。新 run 預設啟用；init 綁定完成後只通知執行者一次 run 路徑，補齊首份快照。背景程式只在漏派、等待時未收回成果、資源衝突或返工等可處理事件喚醒監督，同一問題去重。監督核對真實代理、原驗收未達項、依賴與主機資源，給具體工作範圍及產出，再由執行對話當輪收回、補派；不只要求增加代理數。送出前重查目前狀態，過期指示不送；不能以加速為由降低原驗收。

**驗收進度與重測成本**：依[驗收進度、重測與成本](references/acceptance.md)，新 run 保存逐條成果與每次實測，背景程式從持久結果辨識反覆未通過及 PASS 撤回。監督先讀精簡摘要，核對變更影響、核心旅程、帳號續期與剩餘排程，再讀相關原始證據；執行次數不算通過次數。沿用證據以原契約及使用者授權為準，不重問已涵蓋的決定。
