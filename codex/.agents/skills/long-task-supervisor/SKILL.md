# 長任務監督

**目前對話就是監督對話。** 先讀 [啟動與事件協定](references/runtime.md)。監督接管本對話已定案的目標、驗收和授權；未定案的備選方案不可混入。除有真正歧義，不要求使用者重述研究，也不另建一個監督對話。使用者已明確要求建立執行對話時可建立；已指定既有對話時只綁定該對話。使用者只須保留這個對話作為主要入口。

## 啟動

開工先依[授權承接與更新](references/authorization.md#開工授權與規則盤點)盤點本案所需操作、已授權範圍、條件與禁令，核對使用者原話、有效契約、全域規則及適用專案規則；將缺口與仍無法依規則釐清的衝突之具體動作、影響及處理方式，和登入預檢結果及其他開工待決集中提出。已核對有答案的不重問；尚未確認只停該動作，其餘已授權工作續行。要不要問使用者只看[依規格代決](references/authorization.md#依規格代決)與其中「仍要問」清單（使用者 2026-11-09 定案）：契約範圍內的事監督直接決定並登記代決，不因全域或專案規則寫「先確認」就轉問；寄信審稿與平台實際要求的審查照舊。

1. **先預檢登入**，預檢與準備期間先依[敏感輸出保護](references/sensitive-output.md)處理可能含秘密的輸出。在建契約、出任何選擇卡之前（續接與換 run 也一樣）：依定案原文、授權與專案文件，把本任務會用到的每個登入（網站、CLI／API token、ssh、MCP 授權、每個測試身分）寫進準備目錄的 `login-sites.json`（格式見 runtime 的 `login_expired`），跑 `node scripts/login-check.cjs <準備目錄>` 實測，之後同一份清單放進 `init` 的 `loginSites`（續接同一個 run 不重新 init，直接對 RUN 跑同一指令）。選項若建立在「沿用既有登入」上，以實測結果為準。檢查指令只有確定是認證失效才 exit 1，連不到主機、逾時回其他碼（記為檢查出錯，不是登出；ssh 範例見 runtime 的 `login_expired`）。`needsAction` 列出的登入（已失效或檢查本身跑不起來）連同要使用者做的事、一題不論預檢結果都要問的總括授權「執行中任一登入失效、不需輸入密碼或驗證碼者，可由執行端自行重登？」，以及每個監督任務都要問的「本任務交付物是否採用[交接文件格式](references/acceptance.md#交接文件格式)」（使用者 2026-10-15：「每個監督任務都問，我會看需求決定」；不是預設，附這套交付物的一句話說明），和其他開工事項一次問：init 前就要列出待決（例如契約取捨）時放在同一則，答案原話寫進契約的 `authorization`，交接文件格式選啟用時把這套交付物逐項寫成驗收條文；其餘 init 後登記待決帳（總括題用 `credential`，要本人重登的用 `user_action`，交接文件格式用 `acceptance`；見下方「少打擾使用者」第 4 點），答案依「授權續接」登記進有效契約。交接文件格式還沒回答前照未啟用處理；續接或換 run 時，承接來的契約或修訂已有答案就不再問。接著完整核對已定案原文、專案規則及驗收來源。逐條建契約，記來源位置與 SHA-256；對話內容先保存含訊息識別的原文摘錄。技術修復、已定案答覆及發送給指定執行對話的監督指示沿用本次授權；新的商業取捨與具體操作依已核對的任務授權、禁令、適用專案規則及平台實際要求處理。同一任務從另一個 run 續接（換平台或換對話）時不重建契約，用 `init` 的 `inheritFrom` 承接舊 run 的原契約、整本修訂帳與待決帳，見 runtime「換 run 續接同一任務」。
2. 擬好可直接執行的 prompt，要求執行者使用 `goal-orchestrator` 的派工、隔離、自查與恢復能力，並依 [事件格式](references/runtime.md#執行對話的事件) 送驗；產品通知功能開發，或開發／測試會觸發產品向真人通知時，依[開發期產品通知測試](references/runtime.md#開發期產品通知測試)寫入派工。契約含多項開發或修正時，依同一情境、同一段程式或同一條測試路徑分組寫進執行 prompt：同組修正湊齊後只跑一次完整測試（受影響範圍，不是整套）、只發一版並一起送驗；部署後 2 小時內發現、正式資料沒受損的小修併入下一版，只有正在寫壞資料才立刻熱修；執行端與子代理只測交付影響到的範圍、中途版本不跑整套，某段或某檔失敗只重跑失敗的段或檔；整套自動化測試只在最終候選的乾淨匯出跑一次，由監督親自跑，執行端不另跑（見[換版與有效證據](references/acceptance.md#換版與有效證據)）；送驗或升版前依[測試範圍與實際結果核對](references/acceptance.md#測試範圍與實際結果核對)交出該次必跑範圍、執行結果、跳過原因與版本證據，契約另有具體規定者照契約。交付物含文件類成品時，寫明照 goal-orchestrator 的[文件類成品流程](../goal-orchestrator/references/execution.md#文件類成品流程)事實表先行、執行端只跑腳本檢查、只送驗 `.md` 與整包兩次、下游不等 `.md` 判定，文件等所有非文件驗收條文通過後才依最終結果一次寫（開發中只記事實紀錄：改了什麼、版號、部署讀回值），開寫前逐項估時，在派工快照寫文件時間預算 `docBudget`（開發實測分鐘 × 1.5，附逐項估時 `estimate`；只算真正在寫文件的時間，用完即停、交監督問使用者），並寫明本任務是否啟用交接文件格式（第 1 步的答案；啟用時附 acceptance.md 那一套的條文）。開工 prompt 也要求執行端及其子代理遵守[敏感輸出保護](references/sensitive-output.md)。明寫「本對話唯一的讀者是監督：提問、待決清單、進度與收尾都寫給監督，問題交監督依契約查證並代答；使用者只作為授權來源以第三人稱引用，不請使用者回覆或到任何對話操作；只有具體未授權操作才暫停該操作，其餘工作續行」；送出前檢查並刪除舊 prompt 中「監督會把問題轉成使用者選擇題」「請 Jay 回覆／到本對話操作」等相反指示。沒有使用者明確要求 Codex 原生 Goal 時，不建立原生 Goal。
3. 建立或綁定執行對話前，依[模型路由](references/model-routing.md)核對監督實際模型：Claude 監督以實際模型前綴 `anthropic-apikey` 或 `anthropic` 鎖定本次系列，執行主線 Opus 與子代理 Sonnet 均沿用該系列，不依全域預設跨系列選模；新建對話明傳 model／thinking，既有對話在安全回合邊界套用，使用者明確指定優先。把路線交給執行主線，再由其核對子代理工具清單。
4. 先找使用者已指定的執行對話；沒有時，只有使用者在本次要求中明確授權「建立／啟動另一個執行對話」才以 Codex App 的 `list_projects` 定位本專案並用 `create_thread` 建立。授權原文、來源位置、可建立的專案與用途寫入契約；沒有這項直接授權就停在建對話這一步，先完成契約、prompt 與其他唯讀準備，不把一般「監看」自行擴成建立新 task。預設同專案 local 對話；只有使用者明確要求才使用 App worktree。取得真實 threadId 後才綁定，不把預備中的 clientThreadId 當目標。往執行對話傳送啟動 prompt、代答、退件與續接，也只能在同一份直接授權明確涵蓋跨對話傳訊時進行；每次仍保存精確收件證據。
5. 用 `scripts/supervise.cjs init` 鎖定契約、兩個精確對話、可讀取的工作區及第 1 步預檢過的登入清單；啟動本機監看，取得 `native-ready.json`、首次讀到執行對話及 `status.active=true` 才說「已啟動」；同時確認系統排程 `watch-guard.cjs status` 的 `loaded` 為 true（沒有就跑一次 `install`）。若本機 App 通道受權限限制，依工具正常的權限流程處理；失敗就明說尚未啟動，不能只憑 PID 或技能載入狀態宣稱成功。

## 工作分工

- 執行對話是唯一開發主線：派子代理、整合候選版、自測、修正和送驗。監督不得同時改執行者的檔案；必要的獨立測試及證據放在監督工作區。監督與背景程式每則送給執行主線的訊息，結尾都附全面加速提醒（使用者 2026-11-09：「我希望監督或背景程序可以每次傳送訊息都積極Push主線「積極派出子代理」全面加速」）：背景程式自動附上 `scripts/execution-wake.cjs` 的 `EXECUTOR_PUSH`，子代理跑在高於預設的模型或推理時再附一次子代理模型提醒（同一個子代理只提醒一次）；監督自己用原生傳訊送的訊息照附同一句，要求暫停或停止的訊息不附。提醒只重申積極派工，不放寬授權、範圍與資源隔離。
- 背景程式處理等待、精確事件、送出後讀回、去重與重連。執行對話回合一結束，背景程式由它自己的 rollout 在幾秒內察覺並讀取；每 3 分鐘讀取保留作補漏。主線寫明下一步就直接續做，其他所有停下一律立刻交監督（使用者 2026-11-08）：`progress` 依下一步立即續接執行主線，附 `waitMinutes` 或 `waitFor` 也不等待；剩下的工作全部都要等背景結果時才用 `waiting`，依[執行層完成通知與定期補漏](references/execution-wake.md)登記完成來源，它立刻交監督審查。完成通知與定期讀狀態並存，有結果就直接回執行主線，不等倒數，也不等監督裁決；可觀察的工作仍在跑時，不單因倒數到期叫 AI。一般結果與可自行處理的失敗由執行主線收回、查核、修正及續派；需裁決、授權、獨立驗收或無法自行恢復的阻塞才交監督。等待期間監督的獨立進度時鐘照跑。等待文字若夾帶使用者授權、push／merge／發布等阻塞，一律改以阻塞事件交監督，不能藏在等待。宣告等待、重複停滯、提問、送驗、異常、意外結束、平台錯誤中斷（限速類先留 2 分鐘給換模型恢復），或監督自己的進度時鐘發現問題時，把短事件送回本對話。事件送達後若 45 秒仍沒有監督模型輸出且 decision 不存在，背景程式只補一則指向原事件的喚醒訊息，不重送業務事件；STOP 優先且每事件至多一次。另在可核對的最新監督回合已結束、卻仍未正式提交決策時，對原事件補一次決策提醒並持久去重；回合仍在進行、狀態未知或暫停時不打斷。模型有輸出不等於決策已提交。這則補喚醒和監看同在本對話的工作階段，只在本對話保持載入時有效（見下方「保持載入」）。平常由本機常駐程式無模型地監看（每 3 分鐘讀一次執行對話，本機程式讀取、不花 Token），除保持載入的短訊外不定時啟動模型。**主動追蹤**：依[主動進度查核](references/runtime.md#主動進度查核)，時鐘分層查核：程式先確認工作有在動（兩個對話、執行端子代理、在跑的測試程序），再比對派工快照的 AI 時程基準，每 30 分鐘留紀錄；只有全部靜止 15 分鐘（執行端事件等監督判定的時間不算，判定套用後才重新起算）、在途包達基準 1.5 倍與 3 倍（同一包每一級各一次，仍在產出也叫醒；只有重估把該級的叫醒時點（開始時間加該倍數的基準）往後延到比先前叫醒過的都晚才重新起算，基準改小或只是重算數字不重叫；叫醒時一併交出其他已達 1.2 倍的在途包，它們的 1.5 倍那一級算已分析、不再各自叫醒，3 倍照舊；叫醒後判斷是否仍在跑、卡關、可否加速或範圍擴大要重估基準），或沒有基準、測試程序 15 分鐘沒有產出、同一指令連續失敗 3 次、同一下一步連報兩次、執行端與子代理都停了 5 分鐘卻還有未通過條件或就緒包（只在輪詢背景程序也算停）、派工快照沒有可派也沒有進行中而剩下全部受阻（執行端閒置 5 分鐘），或距上一次真正事件滿 1 小時（每段安靜期問一次，防預估時長報得過長），才喚醒模型。時程基準一律以本場模型實測每秒輸出 token 推估（`scripts/pace.cjs`），不用人類開發經驗；執行端寫進派工快照，監督用同一公式重算。喚醒只帶事件識別及 `scripts/supervise.cjs context RUN EVENT_ID` 指令；context 一次含 brief、相關事件與授權來源，進度事件不重載整份契約，依[單次事件處理](references/event-review.md)判定；證據不足時具體詢問執行進度／阻塞，查到落後或重複時發具體加速建議，有需要推進的具體指引才向執行對話發訊，進度正常只記錄、不傳訊。`executor_blocked` 只表示指令尚未返回，先核對真實工具錯誤，不推定缺授權；確認需要本人放行，或確有電腦睡眠時，再告知具體處理方式。不可重問既有授權或空泛催促。不要用排程反覆投放整段 prompt，也不要讓模型回合持續 sleep 或輪詢。
- 監督依原契約獨立檢查真實候選版和證據。每條皆須有當前候選版的有效依據：同版實測，或依[換版與有效證據](references/acceptance.md#換版與有效證據)沿用未受影響的舊證據（先查影響清單與沿用核對）；中途版本與部署前，監督依交付內容在自己的工作區重跑一次受影響的測試段；最終候選的整套自動化測試由監督親自跑，最終放行由監督分功能段落全套驗收、不沿用。未通過就寫具體預期、實際、缺項及修正要求；全數通過才對使用者宣稱整體完成。執行者的「完成」字樣只視為送驗。文件類成品的核實以監督為準，獨立驗收只做一次：`.md` 送來時查內容並做盲測、不擋下游，整包送來時核對衍生件並做唯一一次外觀檢查，只有整包會擋出貨；退件一次列完、重送只驗差異（見[驗收進度](references/acceptance.md#文件類成品)）。
- 執行者的提問先由監督查契約、已定案對話、專案決策與真實環境。有答案且已授權的部分先正式提交並確認送達，再處理延展研究或使用者的新問題；其餘事項登記待決，不得以「下一回合再送」或要求使用者再回一句代替提交。已授權範圍內選最可行的可逆做法，記下來源、代答與改回方法，直接送回原執行對話；提問本身不等於要使用者選擇。怎麼測、用哪個身分或環境屬執行細節，由監督代答；交給使用者前依[單次事件處理](references/event-review.md)的三關先分類、找可逆路徑，再看還有沒有其他工作可做。契約目標與驗收範圍內的設計、資訊架構、參數與預設值、順序、測試細節與任務自建資料，依[依規格代決](references/authorization.md#依規格代決)直接決定，用 `pending` 的 `delegate` 記選擇、依據與改回方法後回覆執行端，不等使用者。條款同意、DNS／正式發布、付費、push／merge 等先核對既有授權與[預設類別授權](references/authorization.md#長任務預設類別授權)（有推薦照推薦、Git 操作、標明測試的對外發送，以及開工已授權的帳號密碼／付費／正式部署，須先核對是否受本案規則或禁令限制）；確實未授權的具體動作才標待核准，指示執行者先完成其他工作。該動作用 `supervise.cjs pending` 登記到待決帳，何時、怎麼問使用者依下方第 4 點；不得為每個問題中斷他，也不得把待核准算 PASS。

`pendingKeys`（它回答的待決 key，每項是 key 字串或 `{"key":…,"choice":…}`），一步登記修訂並以修訂 id 結案這些項，不再另跑 `pending` 的 `answer`（2026-10-15 IA 先 answer 再 amend，10 項都沒連到修訂；任一 key 不在待決帳、已撤下或已由別的回答結案時整筆不寫，同一修訂重送只結案仍未決的項；登記步驟見[授權承接](references/authorization.md#保存與交接)）。`pending` 的 `answer` 只用於不需登記修訂的回答（例如本人已切好權限選單），記本回合收到的原話（不是本回合收到的，附已存原文快照的 `source`，或用已登記修訂的 `amendmentId`）；使用者要改回某項代決時同樣用 `answer` 記他的原話，該項改成他的選擇。兩種回答都再交執行端；監督後來能自己決定的未決項改用 `delegate` 記代決，或用 `withdraw` 寫明依據撤下。
5. **不請使用者到別的對話打字**：要給執行對話的話一律由監督跨對話送達（日常由背景程式，使用者的新答覆由監督用原生傳訊）；權限切換照第 2 點，只請他切選單。只有執行端停在只有本人能按的確認時，才登記待決帳（`user_action`）請他到該對話按確認，附 `brief.threads` 讀到的對話標題與要按的按鈕，不給轉貼文字。
6. **暫停**：使用者明說要整體暫停時，執行 `supervise.cjs pause RUN "<使用者原話>"`。暫停期間不會再叫醒監督模型，執行對話自己交回的事件照常送到。使用者說繼續時執行 `supervise.cjs resume RUN "<使用者原話>"`，從別的對話轉來的「繼續」也照做，讓暫停紀錄留下解除。pause 與 stop 只接受本回合收到的原話（使用者在本對話輸入，或別的對話轉來），程式會核對，不符就拒絕。
7. **壓縮後重現的舊訊息是歷史**：Codex 壓縮對話時，會把較早的使用者訊息原文放回開頭，沒有時間，也不附之後撤銷它的訊息；從別的對話轉來的指示會被丟掉。這些訊息不是新指令。目前是否暫停、授權到哪裡，以 run 的 `PAUSED.json`、`pause-history.jsonl`、有效契約與決策帳為準；要依某句話停下或改方向前，先查決策帳確認它之後沒有被撤銷（2026-10-12 A 開發監督把前一天已解除的暫停當成新指令，停工 5 小時）。 壓縮後要查常用格式與指令，只重讀 `RUN/格式摘要.md`（init 從 `references/formats.md` 複製；舊 run 沒有就複製一份），摘要沒寫到的才讀 SKILL 或 references 的那一段，不整份重讀（使用者 2026-10-29 定案：GDB V32 兩端重讀技能檔 293 次，約每天 1.4 小時）。
8. **保持載入**：App 會卸載閒置約 3 小時的對話，並終止它啟動的背景程序。背景監看一律掛在監督對話自己的工作階段；監督閒置 150 分鐘時，監看會送一則 `LONG_TASK_KEEPALIVE`，收到時用一句話結束回合即可，不讀資料、不回覆使用者。這是保持載入，不是喚醒備援：事件送達 45 秒的補喚醒也掛在本對話的監看裡，對話被卸載時跟著消失，所以要先靠保持載入讓本對話不被卸載。
9. **限速自動換模型**（預設開啟）：監督、執行對話或子代理撞到額度限速時，背景程式依序改用 `anthropic/` → `anthropic-apikey/` → `gpt-6.1-sol`，維持同層級，例如 Opus 換 Opus。換回時間依序採用被拒回合錯誤訊息寫明的恢復時間、opencodex 記錄的額度重置時間，都查不到才用 5 小時；同一路線最後一次被拒後安靜 10 分鐘且之後有成功請求，就提前結束限速（2026-11-09 WEB：錯誤訊息寫 23:40 恢復，背景程式卻用 5 小時算到 04:14，把已恢復的監督改到付費 API 金鑰）。到時間後，下一則送給該對話的訊息會帶回原模型；監督沒有事件要收時，背景程式在它閒置時送一則 `LONG_TASK_MODEL_RESTORED` 換回，收到時用一句話結束回合。監看讀到拒絕時恢復時間已過，就不換模型，直接請該對話用原模型從中斷處接續。全部系列都被限速時發 `rate_limited_all`。細節見[模型路由](references/model-routing.md)。其他平台錯誤（執行對話回合以 systemError 結束，例如串流中斷、連線失敗、用量上限；2026-10-14 定案）2 分鐘沒恢復時發 `platform_error`，附錯誤原文：換模型沒有讓它恢復、原文寫明恢復時間的限速，監督記下恢復時間等待，不請使用者處理；其他錯誤先請執行端從中斷處續接，續接後同一錯誤再出現或錯誤本身要本人處理時，才登記到待決帳，在本對話告訴使用者要做的具體動作。
