# 長任務監督

**目前對話就是監督對話。** 先讀 [啟動與事件協定](references/runtime.md)。監督接管本對話已定案的目標、驗收和授權；未定案的備選方案不可混入。除有真正歧義，不要求使用者重述研究，也不另建一個監督對話。監督可自動建立或綁定執行對話，使用者只須保留這個對話作為主要入口。

## 啟動

1. 完整核對已定案原文、專案規則及驗收來源。逐條建契約，記來源位置與 SHA-256；對話內容先保存含訊息識別的原文摘錄。技術修復、已定案答覆及發送給指定執行對話的監督指示沿用本次授權；新的商業取捨與不可逆操作照上層規則處理。
2. 擬好可直接執行的 prompt，要求執行者使用 `goal-orchestrator` 的派工、隔離、自查與恢復能力，並依 [事件格式](references/runtime.md#執行對話的事件) 送驗。沒有使用者明確要求 Codex 原生 Goal 時，不建立原生 Goal。
3. 先找使用者已指定的執行對話；沒有就以 Codex App 的 `list_projects` 定位本專案，用 `create_thread` 自動建立。預設同專案 local 對話；只有使用者明確要求才使用 App worktree。取得真實 threadId 後才綁定，不把預備中的 clientThreadId 當目標。
4. 用 `scripts/supervise.cjs init` 鎖定契約、兩個精確對話及可讀取的工作區；啟動本機監看，取得 `native-ready.json`、首次讀到執行對話及 `status.active=true` 才說「已啟動」。若本機 App 通道受權限限制，依工具正常的權限流程處理；失敗就明說尚未啟動，不能只憑 PID 或技能載入狀態宣稱成功。

## 工作分工

- 執行對話是唯一開發主線：派子代理、整合候選版、自測、修正和送驗。監督不得同時改執行者的檔案；必要的獨立測試及證據放在監督工作區。
- 背景程式處理等待、精確事件、送出後讀回、去重與重連。回合結束但還有工作時，依執行者明列的下一步發一則短續接；重複停滯、提問、送驗、異常和意外結束才把短事件送回本對話。不要用排程反覆投放整段 prompt，也不要讓模型回合持續 sleep 或輪詢。
- 監督依原契約獨立檢查真實候選版和證據。每條皆須有同版實測依據。未通過就寫具體預期、實際、缺項及修正要求；全數通過才對使用者宣稱整體完成。執行者的「完成」字樣只視為送驗。
- 已授權的答覆直接送回原執行對話；新的商業決策或未授權動作才請使用者處理。保留原工作，不以待決事項凍結可獨立完成的工作包。

監督模型處理完事件後正常結束回合；本機監看繼續運作。停止或恢復先讀既有狀態和收件紀錄，送達不明不得盲重送。Codex App 或電腦不在運作時不宣稱仍有即時監看；重新啟動後依保存的 run 對帳續接。
