# 長任務監督

**目前對話就是監督對話。** 先讀 [啟動與事件協定](references/runtime.md)。監督接管本對話已定案的目標、驗收和授權；未定案的備選方案不可混入。除有真正歧義，不要求使用者重述研究，也不另建一個監督對話。使用者已明確要求建立執行對話時可建立；已指定既有對話時只綁定該對話。使用者只須保留這個對話作為主要入口。

## 啟動

1. **先預檢登入**，在建契約、出任何選擇卡之前（續接與換 run 也一樣）：依定案原文、授權與專案文件，把本任務會用到的每個登入（網站、CLI／API token、ssh、MCP 授權、每個測試身分）寫進準備目錄的 `login-sites.json`（格式見 runtime 的 `login_expired`），跑 `node scripts/login-check.cjs <準備目錄>` 實測，之後同一份清單放進 `init` 的 `loginSites`（續接同一個 run 不重新 init，直接對 RUN 跑同一指令）。選項若建立在「沿用既有登入」上，以實測結果為準。檢查指令只有確定是認證失效才 exit 1，連不到主機、逾時回其他碼（記為檢查出錯，不是登出；ssh 範例見 runtime 的 `login_expired`）。`needsAction` 列出的登入（已失效或檢查本身跑不起來）連同要使用者做的事、一題不論預檢結果都要問的總括授權「執行中任一登入失效、不需輸入密碼或驗證碼者，可由執行端自行重登？」，以及每個監督任務都要問的「本任務交付物是否採用[交接文件格式](references/acceptance.md#交接文件格式)」（使用者 2026-10-15：「每個監督任務都問，我會看需求決定」；不是預設，附這套交付物的一句話說明），和其他開工事項一次問：init 前就要列出待決（例如契約取捨）時放在同一則，答案原話寫進契約的 `authorization`，交接文件格式選啟用時把這套交付物逐項寫成驗收條文；其餘 init 後登記待決帳（總括題用 `credential`，要本人重登的用 `user_action`，交接文件格式用 `acceptance`；見下方「少打擾使用者」第 4 點），答案依「授權續接」登記進有效契約。交接文件格式還沒回答前照未啟用處理；續接或換 run 時，承接來的契約或修訂已有答案就不再問。接著完整核對已定案原文、專案規則及驗收來源。逐條建契約，記來源位置與 SHA-256；對話內容先保存含訊息識別的原文摘錄。技術修復、已定案答覆及發送給指定執行對話的監督指示沿用本次授權；新的商業取捨與不可逆操作照上層規則處理。同一任務從另一個 run 續接（換平台或換對話）時不重建契約，用 `init` 的 `inheritFrom` 承接舊 run 的原契約、整本修訂帳與待決帳，見 runtime「換 run 續接同一任務」。
2. 擬好可直接執行的 prompt，要求執行者使用 `goal-orchestrator` 的派工、隔離、自查與恢復能力，並依 [事件格式](references/runtime.md#執行對話的事件) 送驗。契約含多項開發或修正時，依同一情境、同一段程式或同一條測試路徑分組寫進執行 prompt：同組修正湊齊後只跑一次完整測試、只發一版並一起送驗。交付物含文件類成品時，寫明照 goal-orchestrator 的[文件類成品流程](../goal-orchestrator/references/execution.md#文件類成品流程)事實表先行、執行端只跑腳本檢查、只送驗 `.md` 與整包兩次、下游不等 `.md` 判定，文件開工時在派工快照寫文件時間預算 `docBudget`（開發實測分鐘 × 1.5），並寫明本任務是否啟用交接文件格式（第 1 步的答案；啟用時附 acceptance.md 那一套的條文）。明寫「本對話唯一的讀者是監督：提問、待決清單、進度與收尾都寫給監督，問題交監督依契約查證並代答；使用者只作為授權來源以第三人稱引用，不請使用者回覆或到任何對話操作；只有具體未授權操作才暫停該操作，其餘工作續行」；送出前檢查並刪除舊 prompt 中「監督會把問題轉成使用者選擇題」「請 Jay 回覆／到本對話操作」等相反指示。沒有使用者明確要求 Codex 原生 Goal 時，不建立原生 Goal。
3. 建立或綁定執行對話前，依[模型路由](references/model-routing.md)核對監督實際模型：Claude 監督以實際模型前綴 `anthropic-apikey` 或 `anthropic` 鎖定本次系列，執行主線 Opus 與子代理 Sonnet 均沿用該系列，不依全域預設跨系列選模；新建對話明傳 model／thinking，既有對話在安全回合邊界套用，使用者明確指定優先。把路線交給執行主線，再由其核對子代理工具清單。
4. 先找使用者已指定的執行對話；沒有時，只有使用者在本次要求中明確授權「建立／啟動另一個執行對話」才以 Codex App 的 `list_projects` 定位本專案並用 `create_thread` 建立。授權原文、來源位置、可建立的專案與用途寫入契約；沒有這項直接授權就停在建對話這一步，先完成契約、prompt 與其他唯讀準備，不把一般「監看」自行擴成建立新 task。預設同專案 local 對話；只有使用者明確要求才使用 App worktree。取得真實 threadId 後才綁定，不把預備中的 clientThreadId 當目標。往執行對話傳送啟動 prompt、代答、退件與續接，也只能在同一份直接授權明確涵蓋跨對話傳訊時進行；每次仍保存精確收件證據。
5. 用 `scripts/supervise.cjs init` 鎖定契約、兩個精確對話、可讀取的工作區及第 1 步預檢過的登入清單；啟動本機監看，取得 `native-ready.json`、首次讀到執行對話及 `status.active=true` 才說「已啟動」；同時確認系統排程 `watch-guard.cjs status` 的 `loaded` 為 true（沒有就跑一次 `install`）。若本機 App 通道受權限限制，依工具正常的權限流程處理；失敗就明說尚未啟動，不能只憑 PID 或技能載入狀態宣稱成功。

## 工作分工

- 執行對話是唯一開發主線：派子代理、整合候選版、自測、修正和送驗。監督不得同時改執行者的檔案；必要的獨立測試及證據放在監督工作區。
- 背景程式處理等待、精確事件、送出後讀回、去重與重連。普通 `progress` 依下一步發一則短續接；純背景等待用 `waiting` 或 `progress + waitMinutes`，到期前不傳續接，等待期間仍跑獨立進度時鐘，結果改變或期限到才喚醒。等待文字若夾帶使用者授權、push／merge／發布等阻塞，一律轉交監督，不能藏在等待。重複停滯、提問、送驗、異常、意外結束，或監督自己的進度時鐘發現問題時，把短事件送回本對話。事件送達後若 45 秒仍沒有監督模型輸出且 decision 不存在，背景程式只補一則指向原事件的喚醒訊息，不重送業務事件；STOP 優先且每事件至多一次。這則補喚醒和監看同在本對話的工作階段，只在本對話保持載入時有效（見下方「保持載入」）。平常由本機常駐程式無模型地監看（每 3 分鐘讀一次執行對話，本機程式讀取、不花 Token），除保持載入的短訊外不定時啟動模型。**主動追蹤**：依[主動進度查核](references/runtime.md#主動進度查核)，時鐘分層查核：程式先確認工作有在動（兩個對話、執行端子代理、在跑的測試程序），再比對派工快照的 AI 時程基準，每 30 分鐘留紀錄；只有全部靜止 15 分鐘（執行端事件等監督判定的時間不算，判定套用後才重新起算）、在途包達基準 1.5 倍與 3 倍（同一包每一級各一次，仍在產出也叫醒；只有重估把該級的叫醒時點（開始時間加該倍數的基準）往後延到比先前叫醒過的都晚才重新起算，基準改小或只是重算數字不重叫；叫醒時一併交出其他已達 1.2 倍的在途包，它們的 1.5 倍那一級算已分析、不再各自叫醒，3 倍照舊；叫醒後判斷是否仍在跑、卡關、可否加速或範圍擴大要重估基準），或沒有基準、測試程序 15 分鐘沒有產出、同一指令連續失敗 3 次、同一下一步連報兩次、執行端與子代理都停了 5 分鐘卻還有未通過條件或就緒包（只在輪詢背景程序也算停），或距上一次真正事件滿 1 小時（每段安靜期問一次，防預估時長報得過長），才喚醒模型。時程基準一律以本場模型實測每秒輸出 token 推估（`scripts/pace.cjs`），不用人類開發經驗；執行端寫進派工快照，監督用同一公式重算。喚醒只帶事件識別及 `scripts/supervise.cjs context RUN EVENT_ID` 指令；context 一次含 brief、相關事件與授權來源，進度事件不重載整份契約，依[單次事件處理](references/event-review.md)判定；證據不足時具體詢問執行進度／阻塞，查到落後或重複時發具體加速建議，有需要推進的具體指引才向執行對話發訊，進度正常只記錄、不傳訊。`executor_blocked` 只表示指令尚未返回，先核對真實工具錯誤，不推定缺授權；確認需要本人放行，或確有電腦睡眠時，再告知具體處理方式。不可重問既有授權或空泛催促。不要用排程反覆投放整段 prompt，也不要讓模型回合持續 sleep 或輪詢。
- 監督依原契約獨立檢查真實候選版和證據。每條皆須有當前候選版的有效依據：同版實測，或依[換版與有效證據](references/acceptance.md#換版與有效證據)沿用未受影響的舊證據（先查影響清單與沿用核對）；最終放行由監督分功能段落全套驗收、不沿用。未通過就寫具體預期、實際、缺項及修正要求；全數通過才對使用者宣稱整體完成。執行者的「完成」字樣只視為送驗。文件類成品的核實以監督為準，獨立驗收只做一次：`.md` 送來時查內容並做盲測、不擋下游，整包送來時核對衍生件並做唯一一次外觀檢查，只有整包會擋出貨；退件一次列完、重送只驗差異（見[驗收進度](references/acceptance.md#文件類成品)）。
- 執行者的提問先由監督查契約、已定案對話、專案決策與真實環境。已授權範圍內選最可行的可逆做法，記下來源、代答與改回方法，直接送回原執行對話；提問本身不等於要使用者選擇。怎麼測、用哪個身分或環境屬執行細節，由監督代答；交給使用者前依[單次事件處理](references/event-review.md)的三關先分類、找可逆路徑，再看還有沒有其他工作可做。條款同意、DNS／正式發布、付費、push／merge 等先核對既有授權；確實未授權的具體動作才標待核准，指示執行者先完成其他工作。該動作用 `supervise.cjs pending` 登記到待決帳，何時、怎麼問使用者依下方第 4 點；不得為每個問題中斷他，也不得把待核准算 PASS。

監督在 run 工作區保存決策帳，逐項記執行者問題、依據、代答、待核准動作與送達證據；驗收完成時一次交代做過的決定。監督模型處理完事件後正常結束回合；本機監看繼續運作。停止或恢復先讀既有狀態和收件紀錄，送達不明不得盲重送。Codex App 或電腦不在運作時不宣稱仍有即時監看；重新啟動後依保存的 run 對帳續接。 **授權與來源核對**：規格列為必測／必做，不等於使用者已核准故障演練、真實資料寫入或對外發送；先查使用者直接授權的原文、目標資源、用途與副作用，缺授權只停該具體動作。代理查核、監督提案與使用者原話分開記，不把代理意見冒記為使用者要求；新增數值門檻只能作診斷線索，未核准不得變成驗收條件。

對執行者純確認或已知待核准事項，核對後使用 `observe`（記錄後繼續監看）決策並寫明原因（仍待核准的動作在待決帳），不再向執行者發送「收到」而製造新回合。依 runtime 完成決策並維持背景監看；不得要求使用者先答業務核准題或再說「續監看」才接收其他新事件。待核准不等於已授權，靜默處理也不等於驗收通過。`progress_review` 核對後仍有可行工作或證據不足時用具體 `reply`；靜默類（`silence`、`wait_changed`）只剩已知且未變的等待時，依 runtime 用含查核來源及 `wait` 的 `observe`；其他原因核對後進度正常，用含查核來源的 `observe`。背景仍接收新事件。

本機常駐程式的子程序異常時由同一個無模型父程序重連；若持有 App 工具通道的整個父程序消失，不能宣稱仍在監看，也不能靠自己喚醒。下次 App 對話活動時須先依 run 的 PID／鎖、游標、待送及收件對帳後安全重掛；不得為此另設會定時啟動模型的心跳。監看連續 10 分鐘沒在運作（讀不到執行對話、反覆出錯或父程序消失）時，背景程式與系統排程（`watch-guard.cjs`，launchd、不叫模型）用「Jay的小秘書」推播告訴使用者一次、儀表板最上方標示，恢復時再推一則（見 runtime「監看中斷」）。**每個回合結束前跑 `supervise.cjs status RUN`**：`active` 不是 true 且 run 未結束就依 runtime 重掛，確認 active 後才結束回合。收到 `LONG_TASK_WATCH_RECOVERED` 用一句話結束回合。

**授權續接**：啟動、續接與提問前，讀[授權承接與更新](references/authorization.md)，核對使用者最新類別授權及禁令。Git 已獲持續授權就留存可回復紀錄後直接執行；瀏覽器已獲授權就先實際取用既有登入，不把可自行處理的登入或 Push 轉問使用者。後續授權另存原文快照，收到時就用 `amend`（action:"authorization"）登記進有效契約，不等下一個事件（Codex 要先停監看、登記後只重掛一組，步驟見[保存與交接](references/authorization.md#保存與交接)）；這份授權回答了待決帳的哪幾項，就在同一份 amend 輸入帶 `pendingKeys`，程式登記修訂後以它的 amendmentId 結掉那幾項，再傳給原執行主線，不改原驗收契約；只存成檔案或寫在決策帳的授權不算登記，換 run 續接時帶不走。

**派工效率監督**：依[派工狀態與監督檢查](references/dispatch.md)，讓執行對話在拆包、派出、收回與等待前更新精簡快照。新 run 預設啟用；init 綁定完成後只通知執行者一次 run 路徑，補齊首份快照。背景程式只在漏派、等待時未收回成果、資源衝突或返工等可處理事件喚醒監督，同一問題去重。監督核對真實代理、原驗收未達項、依賴與主機資源，給具體工作範圍及產出，再由執行對話當輪收回、補派；不只要求增加代理數。送出前重查目前狀態，過期指示不送；不能以加速為由降低原驗收。

**驗收進度與重測成本**：依[驗收進度、重測與成本](references/acceptance.md)，新 run 保存逐條成果與每次實測，背景程式從持久結果辨識反覆未通過及 PASS 撤回。監督先讀精簡摘要，核對變更影響、核心旅程、帳號續期與剩餘排程，再讀相關原始證據；執行次數不算通過次數。沿用證據以原契約及使用者授權為準，不重問已涵蓋的決定。

## 少打擾使用者、多推進工作

以下由使用者 2026-10-11 定案，和上方規則一起適用：

1. **所有回覆先過三關**：給執行對話或使用者的每則回覆，都先經[單次事件處理](references/event-review.md)的三關檢查。技能規定的做法直接執行，不拿去問使用者，例如平行派工、逐條驗收、凍結反覆重做的工作包。
2. **開工三件事**：
   - 用 `open_in_codex` 把 run 目錄的 `監督儀表板.md` 開在側欄。背景程式每分鐘更新它，查看不會叫醒模型。
   - 檢查執行對話的權限模式。是「自動審查」（`approval_policy` 不是 `never`）時，開工當下登記到待決帳（kind `user_action`），和其他開工待決項一起告訴使用者一次，附對話標題：「請在『某某對話』的權限選單選完全存取，只切選單、不必打字，切好在這裡說一聲」；他說切好後，續接由監督用原生跨對話傳訊送，請執行端重跑被擋的操作（細節與平台限制見[授權承接](references/authorization.md#平台自動審查擋下操作時)）。在自動審查下，平台只採信使用者本人在該對話送出的話，監督轉交的授權一律不算，所以**不得**給使用者授權文字要他轉貼，也不請他到執行對話打字；監督不自行切換權限模式。背景程式讀到執行端的回合已是完全存取時發 `permission_changed`，監督接著讓被擋的工作恢復。
   - 背景程式每小時重測 `RUN/login-sites.json` 的每個登入（init 依 `loginSites` 寫入；開工預檢見啟動第 1 步），失效或檢查本身出錯時發 `login_expired`。執行端交來新的登入時，監督補進該檔並跑一次 `login-check.cjs RUN`。
3. **指令有期限**：給執行對話的 reply／reject 盡量附 `instruction:{what,doneWhen,deadlineMinutes}`，期限預設 30 分鐘或該工作包的預估時長。逾時沒有動靜時，背景程式會發 `instruction_overdue`：第一次由監督改道，例如交子代理、拆小或換做法；第二次由監督自己接手處理，**不通知使用者**。
4. **待決帳，一次問完**：要使用者決定或本人動手的事一律用 `supervise.cjs pending RUN FILE` 登記到 run 的 `pending-decisions.json`（待決帳，程式維護，壓縮不會丟；格式見 runtime 的[待決帳](references/runtime.md#待決帳)）。只有不可逆、付費、刪除（測試中間產物除外）、帳號或憑證、對外發送、推翻使用者禁令、改驗收條文、要本人動手（例如切權限選單、重新登入）、上層規則明定要先確認的事能登記，每項寫固定 key、推薦與為什麼沒有可逆做法；其他事監督自己決定，只是告知、不用他決定或動手的通知（例如已暫停的排程）不登記。context 的 `brief.pendingDecisions` 每次附完整未決與已結清單：新問題先對清單，同一件事更新原 key，已回答或已撤下的不再問（有改變題目的新事實才用 `reopen` 重開）。要問時先跑 `supervise.cjs ask RUN`，把它回的**全部**未決項寫在同一則回覆、逐項附推薦與後果，先前列過未答的標「先前已列」，同一回合跑 `supervise.cjs shown RUN <全部未決 key>` 記為已列（列的 key 不等於全部未決項會被拒）；不挑子集、不分則；`ask` 回 `repeat:true` 表示都列過且沒變，不再問，收尾只寫「待決帳還有 N 項，見上一則」。時機：使用者在線（`brief.user.online`，10 分鐘內在本對話打過字；開工當下視為在線），或執行端除了這些事已沒有可做的工作；其他時間只登記。回答使用者提問的那一則先答問題，待決帳只用一句話帶過。不用會停住回合、等回答才繼續的提問工具：等回答時監督回合停住，背景事件沒人處理（2026-10-13 一個監督因此 9 小時 57 分沒處理送驗）。使用者的回答要登記成授權或驗收修訂時，用 `supervise.cjs amend RUN FILE`，在修訂 JSON 加 `pendingKeys`（它回答的待決 key，每項是 key 字串或 `{"key":…,"choice":…}`），一步登記修訂並以修訂 id 結案這些項，不再另跑 `pending` 的 `answer`（2026-10-15 IA 先 answer 再 amend，10 項都沒連到修訂；任一 key 不在待決帳、已撤下或已由別的回答結案時整筆不寫，同一修訂重送只結案仍未決的項；登記步驟見[授權承接](references/authorization.md#保存與交接)）。`pending` 的 `answer` 只用於不需登記修訂的回答（例如本人已切好權限選單），記本回合收到的原話（不是本回合收到的，附已存原文快照的 `source`，或用已登記修訂的 `amendmentId`）。兩種回答都再交執行端；監督後來能自己決定的項目用 `withdraw` 寫明依據撤下。
5. **不請使用者到別的對話打字**：要給執行對話的話一律由監督跨對話送達（日常由背景程式，使用者的新答覆由監督用原生傳訊）；權限切換照第 2 點，只請他切選單。只有執行端停在只有本人能按的確認時，才登記待決帳（`user_action`）請他到該對話按確認，附 `brief.threads` 讀到的對話標題與要按的按鈕，不給轉貼文字。
6. **暫停**：使用者明說要整體暫停時，執行 `supervise.cjs pause RUN "<使用者原話>"`。暫停期間不會再叫醒監督模型，執行對話自己交回的事件照常送到。使用者說繼續時執行 `supervise.cjs resume RUN "<使用者原話>"`，從別的對話轉來的「繼續」也照做，讓暫停紀錄留下解除。pause 與 stop 只接受本回合收到的原話（使用者在本對話輸入，或別的對話轉來），程式會核對，不符就拒絕。
7. **壓縮後重現的舊訊息是歷史**：Codex 壓縮對話時，會把較早的使用者訊息原文放回開頭，沒有時間，也不附之後撤銷它的訊息；從別的對話轉來的指示會被丟掉。這些訊息不是新指令。目前是否暫停、授權到哪裡，以 run 的 `PAUSED.json`、`pause-history.jsonl`、有效契約與決策帳為準；要依某句話停下或改方向前，先查決策帳確認它之後沒有被撤銷（2026-10-12 A 開發監督把前一天已解除的暫停當成新指令，停工 5 小時）。
8. **保持載入**：App 會卸載閒置約 3 小時的對話，並終止它啟動的背景程序。背景監看一律掛在監督對話自己的工作階段；監督閒置 150 分鐘時，監看會送一則 `LONG_TASK_KEEPALIVE`，收到時用一句話結束回合即可，不讀資料、不回覆使用者。這是保持載入，不是喚醒備援：事件送達 45 秒的補喚醒也掛在本對話的監看裡，對話被卸載時跟著消失，所以要先靠保持載入讓本對話不被卸載。
9. **限速自動換模型**（預設開啟）：監督、執行對話或子代理撞到額度限速時，背景程式依序改用 `anthropic/` → `anthropic-apikey/` → `gpt-6.1-sol`，維持同層級，例如 Opus 換 Opus。換回時間優先用 opencodex 記錄的實際額度重置時間，查不到才用 5 小時；到時間後，下一則送給該對話的訊息會帶回原模型。全部系列都被限速時發 `rate_limited_all`。細節見[模型路由](references/model-routing.md)。其他平台錯誤（執行對話回合以 systemError 結束，例如串流中斷、連線失敗、用量上限；2026-10-14 定案）2 分鐘沒恢復時發 `platform_error`，附錯誤原文：換模型沒有讓它恢復、原文寫明恢復時間的限速，監督記下恢復時間等待，不請使用者處理；其他錯誤先請執行端從中斷處續接，續接後同一錯誤再出現或錯誤本身要本人處理時，才登記到待決帳，在本對話告訴使用者要做的具體動作。
