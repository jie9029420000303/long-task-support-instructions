# 執行層完成通知與定期補漏

三層責任不變：監督看執行主線，執行主線看子代理。子代理成果、測試與CI的一般結果及可自行處理的失敗先回執行主線，主線核對、整合、修正及續派；需裁決、未授權操作、獨立驗收或無法自行恢復的阻塞再交監督。一般完成不是送驗，也不是PASS。

## 完成通知與巡查並存

- 原生子代理完成通知照常回執行主線。監看以已登記子代理及工作包核對，主線忙碌時不重複啟動；來源不完整不能當作已完成。
- `native-watch.cjs` 用檔案通知觀察資源帳本及結果檔；原有本機維護循環與三分鐘對話查核直接重讀狀態補漏。即時通知掉失不會把已完成工作留到原倒數才接。
- 主線以 `waiting` 結束回合時，背景程式立刻把事件交監督審查（使用者 2026-11-08），事件附 `completion`：仍在跑的來源（`running`）、已完成的來源（`finished`，已送回主線的標 `delivered`）與讀不到的來源（`issues`），只列位置、不含內容。登記的來源照常觀察；監督審查期間有結果，同樣直接續接執行主線，監督裁決隨後送達。`progress` 不登記等待：附 `waitMinutes` 或 `waitFor` 仍立即續接，續接訊息提醒主線真要等時改用 `waiting`。
- 只在有結果、來源失效需診斷或缺少可觀察來源而原檢查時間已到（監督已裁決該等待）時，續接精確綁定的執行主線。可觀察的工作仍在跑時，`waitMinutes` 到期不單獨製造AI回合；原有停滯、逾期及監督獨立查核照常。
- 完成通知及定期補漏共用 `continue-<事件ID>`、inflight、收件與結果鍵。送達不明沿原流程對帳，不能盲重送；`executionWakeReceipts` 只代表訊息送達，不是成功或收包。是否真正接手仍看執行回合、派工快照及原有進度查核。
- 新的問題、阻塞或送驗優先處理。STOP、暫停、有效契約與來源核對不被普通續接繞過。

## 讓完成狀態可查

工作包在途狀態應記錄實際資源，例如 `resources:{"ledger":"/絕對路徑/resources.json","id":"r1"}`；或沿用 `handle:"resource:r1"` 和 `resources/r1.log` 的證據。主線工作包也可記資源。資源帳本只看本包、本階段的process紀錄；舊階段及其他包不算本次完成。

等待事件可明確附 `waitFor`，補充無法從派工快照辨認的來源：

```json
{"kind":"waiting","nextAction":"讀回原始測試結果，再整合及續派","waitMinutes":20,"waitFor":[{"ledger":"/允許根目錄/resources.json","id":"r1"}]}
```

結果檔尚未產生時可用 `{"path":"/允許根目錄/finished.json","sha256":null}`；重寫既有結果則填目前SHA-256。使用真正的完成結果或最終旗標，不用持續更新的日誌或只有時間戳改變的CI快照當完成訊號。CI可由原本有界的背景追蹤程序寫最終結果，或由該程序的資源帳本記錄自然結束。

來源只限有效綁定的允許根目錄，包含realpath核對；不為查結果執行事件內提供的命令。檔案消失、帳本無法讀取都不代表成功。只有傳統計時等待而沒完成來源的舊事件，檢查到期時先由執行主線核對並補登來源；不把它當作通過，不為此重跑已完成工作。
