# 單次事件處理

只處理 context 指定的事件。STOP、已處理或事件已換就結束；不重建 run、不重讀整段聊天。context 已含 brief 及授權查核入口；只有實際遇到授權問題才執行 authorization，問題與送驗事件直接附有效授權及來源；一般進度只補缺少的直接證據，不重讀 SKILL、全部驗收或自己的歷史。送驗才讀完整有效契約，逐條獨立驗證同版候選，不能採信自報 PASS；換版沿用的項目查影響清單、沿用紀錄、原始變更與像素比對報告，不重開瀏覽器重驗；中途候選與升版／部署前的送驗，監督看執行端的測試報告、不自己重跑；最終放行的送驗由監督分功能段落全套驗收、不沿用，並先對乾淨匯出親自跑整套自動化測試（[換版與有效證據](acceptance.md#換版與有效證據)）。中途候選只以 commit 部署與測試、不正式發版；真實環境情境在同一個候選走完一輪、沒有要改程式的新缺陷與未決新需求時，由監督用 reply 通知執行端定版，定版後才做整套測試、正式發版與帶版本內容的文件（同一節的「候選版與定版」）。文件類成品的送驗依 [acceptance.md 的文件類成品](acceptance.md#文件類成品)：先查內容、內容全對才查外觀；單件驗過用 reply 放行下游，整包且全部條文通過才 accept；樣片、樣張不轉給使用者先看。

先完成本事件的正式提交，再處理延展討論；已有可執行答覆時，不得只在對話說已處理、留到下一回合傳送。需本人決定的部分只登記待決，其餘已授權工作先解鎖。

進度正常或指示已被執行：observe，不傳「收到」、不催促。有可行下一步或證據不足：reply，指出具體工作／問題。背景事件無新進展或新決定時，給使用者的回合結尾只寫一句仍在監看或等待；需提問時仍按 SKILL 集中列完整待決。派工事件送出前重查快照，過期不送。silence／wait_changed 若只剩已核對等待，observe 另附 wait；不能把等待當驗收通過。阻塞只停該動作，其餘已授權工作繼續。

`waiting`（執行端宣告等待，2026-11-08 起一律立刻送來）：讀事件的 `completion`（`running` 仍在跑、`finished` 已完成且 `delivered` 表示已送回主線、`issues` 讀不到的來源），對照最新指示、未通過條件與可派工作。剩下的工作確實都要等結果、來源可觀察時用 observe：結果一出來由背景程式直接續接執行主線，不需監督轉達。還有可並行的工作，或來源缺失、讀不到時，用 reply 給具體下一步或要求補 `waitFor`。結果已送回主線（`delivered`，或 `status` 顯示等待已結束）就 observe，不重複催促。`brief.allBlocked` 不是 null（剩下全部受阻）時，先照 `all_blocked` 的做法逐包核對再決定；執行端只說「沒有可並行工作」不接受。

引用外部文件作為事實依據前，先讀原始文件並記錄查閱時間及可核對的安全網址；網址不得包含權杖、私人存取參數或其他秘密，需保護時保留去敏的公開來源或安全的來源識別。無法讀取或尚未核實時明確標示，不聲稱已查證。

授權疑問依 authorization.md 核對使用者原文、來源、操作及資料目的地；不能因轉派就要求使用者重說，也不能把代理自述當授權。executor_blocked 只是未取得指令結果的線索，先查實際工具回應；沒有拒絕證據不得宣稱需要本人放行。遇到工具明確拒絕，保留工具名、拒絕原文與受阻操作，不換路徑繞過。

**每則回覆都先過三關**（給執行對話或使用者都一樣；使用者已授權監督依驗收目標代答時尤其如此）：

1. 分類：怎麼測、用哪個身分／環境／資料／工具、先後順序與證據做法屬執行細節，由監督依原驗收條文決定並代答。契約目標與驗收範圍內的設計、資訊架構、技術路線、參數與預設值、順序與並行、測試細節與任務自建資料，依[依規格代決](authorization.md#依規格代決)由監督直接決定：照四條選擇原則選，用 `pending` 的 `delegate` 記問題、選擇、依據與改回方法後回覆，不等使用者；專案規則寫「由使用者確認」而沒寫監督不得代的，同樣代確認。只有「仍要問」的事才是使用者決定：改寫驗收條文（縮窄、列例外、換證據或對照基準）、刪除或永久改動既有資料、開工時沒授權或超出上限的帳號密碼／付費／正式部署、會改寫歷史的 Git 操作（強制推送、刪遠端分支或 tag）、寄信與對客戶或公開的正式發送、推翻使用者明示的禁令、使用者在契約自設的核准關卡（`gate`，只擋依賴它的工作）、本人須到場或動手及只有他知道的事實（`user_action`），以及沒有明確推薦的超出契約目標或範圍的變更（`major_change`）。有推薦且合乎選擇原則、不碰須確認事項就照推薦直接回覆；超出契約範圍的方向選擇有明確推薦、推薦的做法不碰其餘須確認事項時也照推薦，用 `delegate`（kind `major_change`）登記後回覆、不等使用者（使用者 2026-11-13 定案）；Git 操作、標明「測試」的對外發送、開工已授權的帳號密碼／付費／正式部署，確認預設授權適用且無本案限制後直接交辦，不問使用者。可撤回、有推薦的執行細節，執行端不等答覆、照自己的推薦先做並在回合結束時補報（2026-11-13 起不再等 30 分鐘）；回覆前先看它做了沒，已做且合理就 observe 記錄。本任務自己產生的測試中間產物（暫存容器與資料卷、測試票與紀錄、草稿、已被取代的中間輸出）必要時刪除已有使用者預設授權，不算使用者決定：由產生它的執行端照做（監督只刪自己建的驗證副本），刪前記入刪除清冊；決策帳、驗收證據、測試結果、清冊、版本控制歷史與證據引用到的測試物件不刪；「不准刪東西」這類泛用禁令只保護非本任務建立的資源，點名特定資源或明說包含測試中間產物的禁令才優先（[authorization.md](authorization.md#測試中間產物的刪除)）。
2. 找路：即使屬使用者決定的範圍，先找能滿足原條文又不越界的可逆做法，例如已授權類別內的暫時調整（先備份、測完逐位元組還原並驗證）、隔離環境、測試資料或既有已授權身分。找到就直接交辦執行端，記下依據與還原方法；每條路都越界時，才把該具體動作記為待核准，並寫明各路為何不可行。
3. 時機：屬使用者決定且找不到可逆路的事，用 `supervise.cjs pending` 登記到待決帳（先對 `brief.pendingDecisions`：同一件事更新原 key，已答的不重問），並在同一則回覆點名執行端接著做的、不依賴該事項的工作（已知缺陷的修正與測試、中途候選上不需本人的情境、唯讀查核、下一批實作；帶版本內容的文件不算），確實沒有時逐條寫明每個未通過條文為何依賴該事項（使用者 2026-11-13：「等我回覆期間，跟這沒關係的工作應該要求執行主線繼續做，而不是整個停下來等我」）；何時、怎麼問使用者依 SKILL 第 4 點：`supervise.cjs ask` 回的全部未決項一次列完，不用會停住回合的提問工具。

技能規定的做法直接做，不當成問題問使用者：平行派工、逐條驗收、兩份以上送驗時派子代理平行驗收、同一工作包重做 2 次仍未送驗就凍結並換方法、開工即把準備工作（部署腳本、回退步驟、規格草稿）列為可派。不請使用者到別的對話打字或轉貼；權限切換與只有本人能按的確認依 SKILL「少打擾使用者」第 2、5 點。

**新事件的處理**（reasons 或 dispatch issue 的 kind）：

- `instruction_overdue`：上一則指示到期仍沒有動靜。`misses=1` 時改道，用 reply 交子代理、拆小或換做法，並附新的 instruction；`misses>=2` 時監督自己接手，例如自己派子代理、自己判定或直接查證，不通知使用者。
- `permission_review`：收到文字掃描找出的疑似拒絕紀錄；文字可能只是引用，先從事件的安全紀錄來源核對實際工具回應、受阻操作、審查原因及授權。只見引用或證據不足時記 `observe`、不稱平台拒絕、不要求改權限；確認是實際拒絕才依[平台自動審查擋下操作時](authorization.md#平台自動審查擋下操作時)處理。不因審查模式要求切換權限，不繞過平台拒絕；只有確需本人處理時才依待決帳集中提出，同一已列事項沒有新事實不重問；其餘已授權工作繼續。
- `permission_changed`：觀察到執行端權限設定改變；這本身不證明原拒絕已解除。先核對原拒絕、平台要求與實際狀態，僅在允許且條件滿足時正當續接；未解決的待決不撤下。
- `automation_found`：有排程正在操作本監督或執行對話。用 Codex App 的 automation_update 把它設成 PAUSED（不刪除），在回覆裡告訴使用者排程名稱和原因，然後 observe。
- `login_expired`：`loggedOut` 列出要處理的登入，`status` 分兩種。`logged_out`（已失效）：開工時使用者給的總括重登授權（有效契約的授權更新）或[先實際使用已授權的登入](authorization.md#先實際使用已授權的登入)涵蓋、不需本人輸入密碼或驗證碼者，用 reply 請執行端依該筆 `login` 自行恢復，恢復後監督跑 `login-check.cjs RUN` 確認；需要本人時用 `supervise.cjs pending` 登記（kind `user_action`，寫名稱與 `url` 或 `login` 的處理方式），依 SKILL 第 4 點的時機問。`error`（檢查本身跑不起來，例如 chrome-relay 沒連上、指令找不到、連不到主機或逾時）不是登出：監督自己重跑 `login-check.cjs RUN` 找原因、修好 `RUN/login-sites.json` 裡的檢查，修不好才登記。其他工作照常推進。
- `rate_limited_all`：可用的模型都在限速中。記下恢復時間，有不受影響的工作就交辦；沒有就 observe，附 resumeAt 等到恢復時間。不改全域設定。
- `platform_error`：執行對話的回合被平台錯誤中斷；一出現就送來，限速類等 2 分鐘仍沒恢復才送（`platformError.text` 是錯誤原文，`kind` 是 `codex_error_info`）。brief 的執行端最後幾段話在錯誤之後已有新回合就 observe。限速類錯誤（`usage_limit_exceeded`、429、「rate-limited」）到這裡代表換模型沒讓它恢復（已全部限速、`modelFallback` 關閉或該請求不經 opencodex）：原文寫明恢復時間（例如「try again at Oct 14th, 2026 12:03 PM」）時，observe 附 `wait:{kind:"external_result",conditions:[],resumeAt:<該時間換算的 ISO 時間>}`，不 reply、不請使用者處理，到時背景程式以 `wait_changed` 叫醒，再請執行端從中斷處接續；沒寫恢復時間的照其他錯誤處理。其他錯誤用 reply 請執行端從中斷處接續，不重做已完成部分。續接後同一錯誤又出現（brief 的最近決策已有同一錯誤的 platform_error），或錯誤本身要本人處理（沒寫恢復時間的帳號用量或 API 額度上限、提供者停用或路由設定、需重新登入）時，才用 `supervise.cjs pending` 登記到待決帳（kind `user_action`；要新建或取得憑證，例如換 API key，用 `credential`），在本對話告訴使用者要做的具體動作，並 observe 附 `wait:{kind:"user_approval",conditions:[]}`；執行端被這個錯誤卡住、已沒有其他可做的工作，所以當下就問。不請使用者到執行對話打字，除限速換模型外不換模型或帳號。
- `overdue`、`no_event_hour`（進度查核原因）：`overdue` 列出的包已達基準 1.5 倍或 3 倍（看 pace 的 ratio；同一包每一級最多叫醒一次，重估把該級的叫醒時點往後延到比先前叫醒過的都晚才重新起算），同一事件的 `nearOverdue` 也一併列出其他已達 1.2 倍、還沒到 1.5 倍的在途包：它們的 1.5 倍那一級記為已分析、不會再各自叫醒（3 倍照舊各自叫醒），所以這次要逐包一起分析，不能只看觸發的那一包；`no_event_hour` 是距上一次真正執行事件已滿 1 小時。先用 pace 以同一公式重算基準，對照執行端填的時長、子代理實際輸出與測試或程序紀錄，判斷四件事：仍在跑、只是估短；卡關（等權限、工具呼叫沒有回傳、程序已停）；可否加速（拆包並行、只跑受影響測試、換做法）；範圍是否擴大（例如同一包接著做下一階段，卻沿用前一階段的基準）。重估過的包看 basis 的重估原因與次數，對照子代理紀錄的實際開始時間判斷累計是否失控。卡關或可加速時 reply 具體指示；範圍擴大、基準明顯估短或過長、產出與進度不符或證據不足時，reply 請執行端回報完成到哪、剩下什麼，用 `pace.cjs estimate` 重估並更新派工快照（能獨立的新範圍拆成新工作包）；只是估短而仍正常產出，或只剩已核對的使用者核准或外部結果等待時用 observe 並寫明理由。這類事件不是 silence，observe 不需 wait。
- `planning_review`（新定案尚未反映到派工）：核對事件的決策版本、有效契約與 `brief.dispatchReconciliation`，重新檢視全部剩餘工作、已解鎖依賴與資源；沿用有效成果，不為對帳重跑測試。請執行端在既有工作包更新時加 `--reviewed "核對依據與結果"`；單改時間或計畫名稱不能結案，不替未定案討論增加工作。
- `dependency_ready_review`（登記的前置包已完成）：核對成果、目前授權與資源後，才請執行端改為可派並補派；這是線索，不自動清掉其他資料、核准或測試前置。
- `dispatch_review` 的 `snapshot_mismatch`、`untracked_agent`、`main_work_review`、`unrecorded_activity_review` 與 `brief.dispatchCrossChecks` 是待核實線索：查工作包檔、子代理原始活動、快照時間與執行端實際工作，核對依賴、資源和主線例外；未能查證或僅有 main、commit、零代理，不據此判違規。依未通過條件另查未登記的可行工作，程式無法保證發現所有漏包。確有可安全並行的工作才具體交辦；合理或已解決就記錄並續監看。`dispatch-preflight.current` 為 null 或來源標為 unknown 時不能判已解決，待來源恢復後重新查核；背景暫緩事件期間繼續接收其他事件。
- 任何 `progress_review`（包含 `idle_with_work`）：除核對正在執行或等待的工作，也讀 `brief.agentActivity` 的子代理原始活動線索、最新使用者指示、尚未通過的條件與待做事項，查未登記工作能否獨立並行；核對前置、授權、共同工作區與實際排他資源。`observedActive` 是找到的未結束回合，不保證來源完整；空清單或無法讀取不能認定沒有代理。可派就具體交辦；真正不能並行則記來源及原因，不能只以主線有活動作結。已有使用者待決不代表其他工作都受阻。
- `parallel_test_review`（進度查核原因）：這是可辨識的完整閘門／明確標註長測試工具呼叫線索，`parallelTestReview.tests` 只含來源位置、呼叫時間、雜湊及 `running`／`unknown`；`unknown` 不代表測試已啟動、遭拒或仍活著。明細缺失時 `sourceCoverage:unknown` 表示來源未知，監督需自行核對，不能當事件已解決。依來源查真實程序與結果、代理實況及尚未拆包的工作，有可安全並行且已授權的工作才要求補派；測試已結束、來源未知或全部確有依賴時據實記錄，不憑長測試或零代理判違規。提交後背景程式套用前再次讀取來源：確定測試已完成就不送舊指示；派工快照或觀察到的代理有變化時重新交監督查證，不自行斷定滿席。同批還有其他原因或未解決線索時保留原決策、以新事件交監督，不能覆寫原檔。來源讀不到是未知，不當成結束；`brief.executor.sourceReadError` 提供去敏錯誤代碼與來源，既有事件繼續處理。這不改變既有整套測試範圍，也不要求重跑。
- `all_blocked`（進度查核原因）：派工快照沒有可派、沒有進行中，剩下的工作包全部受阻，執行端已閒置 5 分鐘（`allBlocked.packages`、`allBlocked.minutes`）。依[受阻只限四種](dispatch.md#受阻只限四種)逐包核對：排在後面、輪到才做，或 kind 沒有寫出四種原因之一的，用 reply 請執行端改列 ready 或拆出準備包並當輪派出；真受阻的也看能否先做準備（規格草稿、測試腳本、部署與回退步驟、唯讀查核）。每包都確實是四種原因之一、也沒有能先做的準備時才 observe，寫明逐包原因。
- `unplanned_criteria`（進度查核原因）：這些未通過的條件已 30 分鐘沒有任何工作包負責，而且執行端已閒置（沒有指令在跑，也不在等監督核對過的外部結果）（`unplannedCriteria.criteria`；`unplannedCriteria.freeCapacity` 是空著的子代理席位）。用 reply 逐條點名要派的工作包，寫明範圍、產出、隔離資源和可解鎖的條件；真的只能等核准或外部結果的，請執行端把它列進 blocked 並標 acceptanceIds。
- `doc_budget`（進度查核原因）：文件時間預算過半（`docBudget.stage` 為 `half`）或用完（`spent`）。`half`：核對剩下的工作放不放得進另一半——簡報與影片是否已在 .md 送驗後開工、退件是否一次列完、重送是否只驗差異、有沒有工作在等判定；有落差就用 reply 給具體做法，進度正常用 observe。`spent`：不延長預算；用 reply 請執行端停下文件工作（其他工作照常），把現況（已完成項、剩餘項、再需多久與依據，對照開寫前的 `docBudget.estimate`）與選項「追加時間／簡化做法（例如只出 .md、省略流程圖或影片）／暫停」登記進待決帳（kind `acceptance`），當回合就在本對話列出並跑 `shown`（同時推播到小秘書），不等使用者在線（使用者 2026-10-29：「如果真的太久的話，我有可能會考慮暫停，或是用簡化的方式做」）。使用者同意追加時，請執行端把同意處寫進 `docBudget.approval`；選簡化會改交付範圍，用 `amend` 登記成驗收修訂；選暫停時只停文件工作。`usedMinutes` 只算真正在寫文件的時間（有文件包在途、5 分鐘內有人在做），等待與做別的工作不算。
- `recurring_rework`：同一包重做 2 次仍沒送驗，用 reply 凍結它，指定新做法或改派其他模型／子代理。

將 eventId、disposition 寫入 context 的 decisionPath；`brief.decisionError` 有值表示上一版決策檔沒通過檢查（附錯誤原文），修正草稿後須再執行 decision 提交。observe 填非空 reason，不含 reply；待決事項只登記在待決帳，決策檔不帶 pendingApprovals（程式會拒絕）。reply／reject 填具體 reply，並盡量附 `instruction:{what,doneWhen,deadlineMinutes}`（期限預設 30 分鐘，可依工作包預估時長調整）；progress_review 另填 progressCheck:{evidence:[實際查核來源],finding:判斷,guidance:具體下一步}，reply 中須有 guidance 原文。silence／wait_changed 的 observe 必須有 wait:{kind:user_approval/external_result,conditions:[{path,sha256}],resumeAt:僅有既定期限才填}。等使用者核准的 wait 另填 dependsOn:[{id:未通過條文 ID,pendingKey:待決帳 key,reason:為何依賴}]：涵蓋每個未通過條文、對應待決項仍未決且沒有可派工作包時，才不再發閒置（idle_with_work）與整點（no_event_hour）提醒；沒寫或沒寫全時這兩種提醒照發，收到就交辦不依賴該事項的工作，或補齊 dependsOn。使用者明示整案暫停時執行 `supervise.cjs pause RUN "<原話>"`，暫停期間不會叫醒模型；needs_user 只在仍須凍結當前事件時使用。

accept 填同版 revision、contractStateSha256（有效契約有此欄時）及逐條 results:[{id,status:"PASS",method,expected,actual,evidence:[{path,sha256}]}]。`brief.eventQueue` 有較新的送驗時不接受這一份，observe 寫明「被排隊中的送驗 <id> 取代」；context 的 `queued`（排在它後面、不是送驗的事件，例如提問或阻塞）不擋接受：讀完原文，驗收時一併結案並列進給使用者的收尾清單。草稿寫完後執行 supervise.cjs decision RUN DECISION_PATH，通過才提交給背景程式；提交前草稿不會送出。提交被平台拒絕時，不得改由其他方式轉發。提交 accept 後須再查 `status` 確認 `phase:accepted`，才能宣稱已接受；背景程式負責傳訊及收件，不自行重送。正常結束回合，等待交背景監看。
