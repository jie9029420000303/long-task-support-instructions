# 驗收進度、重測與成本

本協定追蹤有效成果，不以訊息、工作包數或測試執行次數代表完成。原始契約、最新使用者授權及獨立送驗判定仍決定放行；進度快照不能自動授權或放寬驗收。

## 執行與持久化

新 run 的派工快照包含 `acceptance`；舊 run 可繼續使用既有格式，接入前由原監督在安全停點核對相容性，不直接改 live run。每個測試完成即更新快照並執行 `dispatch.cjs write`，不要等整批結束才記錄。

`acceptance.revision` 是目前候選版，`items` 必須逐一覆蓋有效契約 ID 與有來源的排除項。每筆包含 `id`、`status`、`evidence`；status 為 PASS（已有通過證據）、FAIL（判準未達）、BLOCKED（具體前置阻塞）、PENDING（待執行或待判定）、INCONCLUSIVE（已執行但不足判定）。沒有足夠判定證據時不能填 PASS；已有代判授權則由監督查證判定，不把使用者未在場當成必等。有效契約中的排除項填 EXCLUDED，保存核准來源，不算通過次數。

每筆 `lastAttempt` 記最新完成案例：`id`（這次執行的唯一識別）、`caseId`（同一測試案例的固定識別，換代理／工作包／候選版仍沿用）、`revision`、`outcome`、`reason`、`evidence`、實際 `startedAt`／`finishedAt`。結果只允許 PASS、FAIL、BLOCKED、INCONCLUSIVE。使用者離開、逾時、未走到指定路徑，依逐字稿和後端證據判定原因；不能只按結束標籤判 PASS 或產品 FAIL。執行數、通過數、同案例連續通過數分開呈現。

寫入工具先將完成結果保存於 `acceptance-history.jsonl`，再原子替換當前快照。重試同一識別不重複計數，已記錄結果不可改寫；更正另建實測記錄並保留舊證據。只有執行主線寫此帳本，監督不能另行重寫或清空歷史。歷史缺失、為空、格式損毀或未涵蓋快照中的結果時，摘要與寫入會報錯，背景查核視為無效快照；先由原始結果與備份對帳修復，不能清檔重置計數。

同一 run 的寫入以 `dispatch-write.lock` 排他；重疊寫入回報忙碌，由執行主線等原寫入結束後以相同 attempt ID 重試。程序異常退出留下鎖時，核對鎖內 PID 確已退出、快照與歷史已對帳，才移除這個失效鎖續寫；不能移除仍有程序持有的鎖或刪掉結果帳。

背景程式沿用既有「同項至少重做兩次交監督」規則，從帳本查出同一案例反覆未通過，即使執行者未填 `recurringRework`、換計畫名稱或下一步文字，仍產生查核事件；先前 PASS 被撤回也須查核。這些都是診斷，不自動判缺陷或停止任務。同一問題持久去重，更新時間或增加一次相同返工不反覆喚醒；解決後重現才是新事件，兩次監督讀取之間發生的 PASS 與再次返工也由結果帳辨識。

## 換版與有效證據

換版先對照實際變更、直接呼叫、共享模組、環境、Client、權限與測試依賴，保存影響對照。`acceptance.change` 記 `id`、`fromRevision`、`toRevision`、`affectedCaseIds`、`requiredRegressionCaseIds`、`impactEvidence` 與 `policyEvidence`（允許此重測／沿用方式的原契約或最新使用者授權）。寫入工具拒絕無影響對照的候選切換；受影響與必要回歸案例的連續通過數重算，其餘保留。

換版後晚到的舊結果仍保存並計入歷史執行數與歷史 PASS 結果數。已失效版本的結果另列 `staleAttempts`，不增加目前有效連續通過數、不消除新返工，也不能據此把當前條目改成 PASS；未受影響案例的沿用仍須有前述契約與核對依據。

每個舊證據的沿用須記來源版本、未變的依賴與核對證據，監督抽查原始變更；判斷不出影響就重測。契約明定全部同 commit、全套回歸或特定連續次數時照原要求；未授權不得自行改為局部重測。不要用本協定覆蓋使用者既定條文，也不要在條文允許沿用時無條件作廢所有舊證據。

換版前先把同組的耦合修正、必要修復與放行缺口湊齊，整合成一版只跑一次完整測試；執行端要為單一修正重跑完整測試或換版、而同組修正還沒湊齊時，監督請它先湊齊。會阻止目標達成的缺陷照常修，不以省 Token 留下必修問題。已跑通項目與剩餘項同步更新，不能把過期總表當成當前進度。

## 品質方向與正式達標

視覺案先核對使用者明定參考、禁止元素與代表桌機／手機核心互動，依既有代判授權選方向；方向品質未成立前不要擴大整站細節 QA。已獲完整開發與代判授權時，代表畫面查核由監督完成，不新增本人核准閘；也不能把操作正確当作使用者設計意圖已滿足。

問題回答按原規格的「正確原因／有效下一步」與安全邊界逐題判定，答案空泛、只說未越權或只跑完案例不能算產品達標。通知到達率、指定輪數及其他硬條文照有效契約，不把缺口改成可選。實測、安全、內容正確与整案驗收分開記錄。

## 文件類成品

說明文件、交接文件、流程圖、簡報、影片等文件類交付物，不論是否啟用交接文件格式，都照執行端的[文件類成品流程](../../goal-orchestrator/references/execution.md#文件類成品流程)交來：唯一內容來源是完整說明 `.md`，每完成一件（`.md` → 流程圖 → 影片 → 簡報 → 整包）就送驗一次。使用者 2026-10-15 定調文件核實以監督為準（執行對話可能夾帶太多開發過程的思考，讓原始目標理解飄移），所以執行端的自評不算，監督的判定才算；建構型程式工作照原流程。

- **先內容、後外觀**：先逐句對照程式、設定與主機實況查內容（派子代理平行查時，每個只給該件、內容來源與要對照的程式／設定／讀值檔路徑），內容全對才查外觀；不要先改外觀再驗內容（GDB 2026-10-14～15 兩次退件 21 項中 15 項是內容不符，只有 6 項是外觀）。
- **主機值**：核對讀值檔表頭的讀取時間晚於最後一次主機或設定變更，且全部值出自同一次讀取；不符就退件請執行端重讀，不拿不同時點的值拼接。
- **單件放行**：單件驗過用 reply 寫明「這一件已驗過，可給下游取用」並附查核證據；不合格用 reject 寫具體缺項。下游件只能取材已驗過的上游件。只有整包且全部有效條文通過才 accept，accept 會結束整場監看。
- **外觀只重查改到的頁**：外觀逐頁查核放在內容驗過之後；退件修正後只重查改到的頁，其餘頁以位元組或像素對照確認未變、留下核對紀錄後沿用。
- **樣片、樣張由監督驗**：不停下來等使用者先看，除非使用者另行要求。

## 交接文件格式

不是預設。每個監督任務啟動時都問使用者這一題（[SKILL 啟動第 1 步](../SKILL.md#啟動)），使用者依需求決定；答案記進契約或修訂，並寫進執行 prompt。使用者 2026-10-15 原話：「我要修改一下，這種交付方式要在監督啟動時詢問是否要啟用這種交付格式。 每個監督任務都問，我會看需求決定」。啟用時交付物是以下一整套（有效契約對交付物另有規定時照契約），交付順序與驗收照上節「文件類成品」：

1. **流程說明文件**：用 Archify 產生，分成總體流程與細部流程單元；每張都通過 `archify deliver --quality showcase`。
2. **交接說明會簡報**：一份 15 頁以內、可播放的 HTML，供系統交接說明會議使用；單一 HTML 檔，影片 mp4 放同一資料夾，離線雙擊即可開，鍵盤與點擊都能換頁，每頁有頁碼。第一頁放一支 5 分鐘以內的概覽影片，內容是這個專案解決什麼問題、解決方案簡介、執行重點、觀察重點、預期結果，讓與會同事先聚焦整體，再開始討論簡報內容；旁白每一句在完整說明 `.md` 都有出處，沒有出處的數字不寫。
3. **完整說明 `.md`**：純文字，讓使用者想知道細節時交給 AI 讀取問答；每張流程圖都要寫成文字（AI 看不到圖）。它也是流程圖、影片與簡報的唯一內容來源。

驗收時另把這份 `.md` 交給只讀這一個檔、沒有其他上下文的子代理，問至少 15 題交接時會被問到的問題，逐題對照程式、設定與主機實況比對答案。

## 開跑前與重新排程

先走真實 Client 的核心成功旅程及必要失敗分支，再擴大昂貴多輪模擬。確定性測試可補文字邊界、狀態轉換等覆蓋，不能替代契約指定的真實操作。

每個測試帳號實測登入、底層工作階段、應用授權與續期；修改有效期不代表舊登入已取得新效期。先用既有登入與已授權續期，只有確需本人驗證才交使用者；不自行放寬安全效期。

開發測試期間，驗收條件要等定時工作（每日、每小時排程）才跑得到時，不把驗收排在排程之後，請執行端在已授權的環境直接手動觸發該路徑取得證據（使用者 2026-10-15：「開發測試期間，驗收不要等這種正式上線的排程，直接手動啟動」；GDB B1 依此直接觸發備份，不必等到台北 08:00）；不刪除、不覆蓋正式環境既有資料（例如遠端已存在的備份集），需要時用該程式的強制參數或另一個目的地。

以實測單位耗時、規模、並行能力與排他資源建立剩餘排程，候選版、前置或影響範圍改變即重算。測試先核對底層共用資源：限流的實際 IP／帳號、工作階段、共用 DB／資料集及高負載主機。不同瀏覽器或代理不代表底層已隔離；沿用排他資源快照，把會干擾其他 UAT 的限流／故障演練隔離或排後，正常核心旅程可繼續。環境互相干擾造成的無效案例記 INCONCLUSIVE 並保留來源，不能當產品 PASS，也不能據此把未受影響證據全數作廢。

排隊工作留 ready／blocked，不冒列 inFlight。監督查實際成果、未達條目、返工原因與可解鎖工作，不以「有活動」視為健康。依既有授權選擇可行方案，不重問已涵蓋的做法。

## 精簡讀取

`node <skill>/scripts/dispatch.cjs summary <ABS_RUN>` 輸出目前逐條狀態、分案例執行／通過／連續通過數、最近未通過原因與實測耗時中位數；沒有量測就回 null，不填估計值。一般事件先讀此摘要及待決帳，僅對變更項、失敗案例或授權疑點讀原始證據，不反覆整讀全部歷史。摘要不是獨立驗收證據。

等待、狀態讀取、計數、送達對帳與排程計算交確定性程式；模型只判影響、證據、授權及下一步。等待既有背景完成通知，避免每次 sleep／重查都經主模型。不得用週期長 prompt 保活，或為降低成本自行換模型、縮輪數、砍案例。

state.md 只留當前候選、逐條結果、有效證據索引、在途工作、阻塞與最新決策；歷史另存可查檔案，不把歷史壓成一條超長行。續接先讀精簡當前快照及來源差異，保留契約、授權、未解項、游標與收件，不能讓摘要變成新真相。

## 平行驗收（2026-10-11 定案）

同時有 2 份以上送驗待判時，監督用 `spawn_agent` 派子代理，各自獨立驗一份或一組條件，並給每個子代理同版候選、條文原文和證據路徑。子代理的結論只算草稿；監督逐條核對證據雜湊和關鍵輸出，再寫入 accept／reject 決策。子代理不改執行端的檔案，也不傳訊給執行對話。
