# 依監督模型選擇執行與子代理

執行主線預設 Opus xhigh（使用者 2026-11-26：執行主線主責切分、派工與收件判定），監督交辦時用監督選定的完整 ID。子代理照下方子代理順位選模，由背景程式依額度與限速決定當下第一站（使用者 2026-11-26）。主線在哪一家，子代理都照子代理順位（使用者 2026-11-28 放寬 2026-11-27 第 37 項）。這要靠 OpenCodex 的實驗設定 plaintextV2AgentMessages 開著，ChatGPT 訂閱與其他家才能互讀子代理的任務與過程訊息（2026-11-28 00:16 實測 Opus 派 Terra 訂閱、Sol 訂閱派 DeepSeek 都能交接）。背景程式讀到它沒開或讀不到時，回到第 37 項：執行主線在 OpenAI 訂閱（Sol 訂閱、Terra 訂閱）上時子代理一律用 Terra 訂閱，不看子代理降級階梯。各層級內以數字比較版本，只選目前顯示且可呼叫的型號。使用者明確鎖定的角色、推理、費用或帳號限制優先，工具缺少明確指定的能力時記錄該角色受阻。

| 角色 | 模型 | 基準推理 |
|---|---|---|
| 執行主線 | 監督選定的完整 ID（預設 Opus） | xhigh |
| A 查核、B 技術、研究 | 子代理順位的當下第一站 | Medium，Sol 與 Terra High（開源固定 max；研究 xhigh） |
| 介面操作 | 子代理順位的當下第一站 | Low，Sol 與 Terra Medium（開源固定 max） |

一般子代理以 Medium 起跳（使用者 2026-11-26，取代 2026-11-23 的 Sonnet High 起跳），介面操作從 Low 起跳。Sol 與 Terra 起跳高一檔：一般子代理 High、介面 Medium（使用者 2026-11-28：11/14～11/28 Terra Medium 有 16% 首回合就交回沒做完的成果，Sonnet Medium 是 1%；Sol 從 Medium 換到 High，要追加指示的比例由 41% 降到 10%）。第 2 次不合格研究後從起跳的檔次升兩檔，最高 max。開源模型不能升檔，改派開源順位的下一款。

Claude 的 `anthropic/`（訂閱）、`anthropic-apikey/`（API） 代表不同帳號路徑，各是順位上的一站；監督、執行主線與子代理都會用到 API（使用者 2026-11-26，取代 2026-11-21「API 只留給監督」）。舊工作從目前進度接續。監督變更路線時在安全回合邊界更新，保存契約、失敗次數與在途成果。錯誤 `unreadable_encrypted_agent_task` 表示父子交接資料無法在該組合讀取：plaintextV2AgentMessages 沒開而主線在 OpenAI 訂閱上時，平台把子代理任務加密給 ChatGPT 原生後端，其他家模型都讀不到（2026-11-27 工區 E 與清票派 DeepSeek、Muse、OpenAI API 子代理全被拒，14:42 實測 Sol 訂閱派 Terra 訂閱可交接、派 DeepSeek 重現此錯誤）。

## 解析及實際呼叫

1. 只盤點現在需要的角色。model-route CLI 會把 OpenCodex 模型目錄（背景程式選站用的同一份）併入 catalogs，主線與監督不必自己整理清單，catalogs 可省略。spawn_agent、send_message_to_thread 的模型說明只列部分模型：2026-11-27 工區 E 的 Opus 主線清單只列到第 16 個，看不到 Terra 訂閱與 Terra API，子代理因此從 Sonnet 直接落到 DeepSeek。目錄列出不代表供應商已啟用：停用、額度用完與派發被拒由背景程式記進 model-fallback.json，model-route 讀它跳過。完整 ID 與支援推理以目錄與工具資訊為準，不自行拼接版本或把 Sonnet 別名當成可呼叫 ID。首次派出後讀子代理執行紀錄的實際模型與推理，相符才記已套用，被拒就保留錯誤原文、記該角色不可用，不把接受參數當執行成功。
2. 在本任務工作區寫一份選模輸入，執行 `node <long-task-supervisor>/scripts/model-route.cjs INPUT.json`。只輸出選模結果，不發訊、不修改設定。輸入格式如下（實際值必須來自工具）：

```json
{
  "supervisorModel": "anthropic/claude-opus-5-5",
  "roles": ["executor"],
  "catalogs": {
    "executor": [{"id":"anthropic/claude-opus-5-5","efforts":["low","medium","high","xhigh"]}]
  }
}
```

派子代理時改用 `roles:["general"]` 或 `["ui"]`，附目前執行主線完整 ID `executorModel`。執行端呼叫 CLI 時會以目前對話的實際模型與推理校正 `executorModel`、`executorEffort`，`catalogs` 可省略，CLI 會併入 OpenCodex 模型目錄。不合格交付（流程見執行技能「不合格交付與研究」）在 `failures` 填這條條文累計的不合格次數（`rework.cjs status` 的 failures，研究後不歸零）：1、3、5 回傳 `reuse:true` 與剛才的模型、推理，表示用 `followup_task` 交回原子代理重做，輸入要附 `previousModel`、`previousEffort`；2 是研究後開新子代理，同一模型推理升兩檔、最高 max，開源模型改派下一款（basis `open-source-next`），也附 `previousModel`、`previousEffort`；4 是研究後開新子代理，用執行主線的模型與推理（basis `executor-equivalent`）；6 以上回 unavailable，等使用者裁決。研究子代理用 `research:true`，用執行主線的模型與推理（basis `executor-equivalent`，使用者 2026-11-27），只在 failures 為 2、4、6 時派。舊欄位 `errors` 會被拒收。已到平台上限時以 `effortAtCeiling` 記錄沿用最高檔；文字回報只將實際提高的項目記為升級。`overrides` 只接已核對的使用者指定，例如 `{"executor":{"model":"完整 ID","effort":"high"}}`；輸入檔本身不證明授權。某角色 unavailable 只表示該角色沒有可派選項，不擋其他已可做的工作，不跨供應商靜默替代。

3. 新建執行對話：把結果明確放入 `create_thread({model:結果.model, thinking:結果.effort, ...})`，不能省略後依賴 App 預設。交辦 prompt 附監督實際模型 ID、供應商路徑、來源與角色分工；執行主線再自己呼叫 model-route 解析子代理，不能從監督端假定子代理也可用。
4. 綁定既有執行對話：已鎖定且符合路線就保留。新啟動需要套用選定模型時，在回合結束後下一則本來就要送的啟動／續接訊息明確傳 `send_message_to_thread({model,thinking,...})`；不為改模型打斷在途回合、額外催促或丟棄成果。使用者明確指定保留的模型不覆寫。背景 watcher 後續傳訊省略模型，沿用該對話目前設定。
5. 子代理使用 `spawn_agent({fork_turns:"none",model:完整ID,reasoning_effort:該包推理,...})`，prompt 只附完成此包所需來源。完整歷史 fork 不能覆寫模型／推理，不能拿它假裝指定了 Sonnet。工具只有繼承模式時，僅在已核對繼承的實際模型與推理符合該角色要求時使用；不以未經本機版本驗證的預設設定繞過工具限制。按下述失敗次數決定模型與推理。工具不支援指定值時如實記錄，只阻塞該角色派工，其他已授權工作繼續，不偽稱已套用。子代理自稱的模型來自系統提示，常與實際不符，不能當證據；實際模型以子代理執行紀錄（session 的 turn_context）或代理伺服器紀錄為準。
6. 把路線、供應商、各角色完整 ID、實際推理、工具清單來源與時間寫進既有 sidecar「模型／推理鎖定」。工具接受只代表已派出；從新回合實際模型資訊核對後才記已套用。原生 Goal 與第三方模型使用均不因此另獲建立新對話、傳訊或敏感操作的授權。

## 額度限速時自動換模型（使用者 2026-10-11 定案，預設開啟；2026-11-21、2026-11-26 改版）

目的：任務持續運作，延長執行主線、監督與使用者本人使用前段資源的時間（使用者 2026-11-26：「延長重長任務重要節點跟真人使用期間」）。切換全由背景程式（native-watch）執行與換回，不靠監督或執行端自己判斷時機；兩邊從儀表板與 `RUN/model-fallback.json` 讀目前順位。

| 角色 | 順位（前一站被拒或降級階梯輪到才往下） |
|---|---|
| 監督、執行主線 | Opus（Claude 訂閱）→ Opus（Claude API）→ 最新 Sol（OpenAI 訂閱）→ 最新 Sol（OpenAI API，`openai-apikey/`）→ 最新 Terra（OpenAI 訂閱）→ 最新 Terra（OpenAI API）→ DeepSeek V4.1 Flash 1017 max → Muse Ember max |
| 子代理 | Sonnet（Claude 訂閱）→ Sonnet（Claude API）→ 最新 Terra（OpenAI 訂閱）→ 最新 Terra（OpenAI API）→ DeepSeek max → Muse max |

- 監督與執行主線用同一條順位，差別只在讓位：降級階梯讓監督比執行主線早兩階往下（使用者 2026-11-26：「監督跟執行主線模型切換順位應該一樣，只是讓位 執行主線最優先」）。監督與執行主線的 Claude 站一律是 Opus，不論對話從哪個模型開始，換回也一律回到角色順位第一站（使用者 2026-11-27：工區 D 執行主線從 11/26 測試用的 Sonnet 開始，15:34 被換回 Sonnet）。被拒紀錄依角色分開記，監督只在自己被拒或階梯輪到時往下換；執行端或子代理被拒不會動到監督。每一站記錄自己的恢復時間，到時間背景程式換回較高順位。開源一律 DeepSeek 先、Muse 後（使用者 2026-11-26，取代 2026-11-22 的 Muse 先），binding 的 fourthExecutorModel 只影響執行主線。
- 監督推理依事件分（使用者 2026-11-26）：背景程式送監督的訊息指定推理，送驗裁決用 xhigh，其他事件（等待、派工檢查、進度檢查）用 High；開案在研究對話照開工流程用 xhigh。開源暫代時固定 max，換模型恢復時帶回原推理。
- 降級階梯（使用者 2026-11-26）：全體共用一個階數 k。子代理在順位第 k 站、監督在第 k−2 站、執行主線在第 k−4 站（第 0 站是順位第一站，負數視為第 0 站）。可用量低於 50% 進第 1 階，越接近用完間距越密：50、35、24、16、10、6、3、1%（使用者 2026-11-27）。所有還有週額度的 Claude 帳號 5 小時額度都用到 80% 時臨時多降一階（離 5 小時重置不到 30 分鐘時不算），重置後回來；讀不到用量時各角色都不換站：沿用最後一次讀成功的數字，每 2 分鐘重讀，連續讀不到 30 分鐘才通知監督登記待決帳；還沒讀成功過時各角色也先不換（使用者 2026-11-28：11/28 09:28 讀取失敗一次，監督 E 就被換到 DeepSeek）。可用量回升時階數往回退。一個角色往下最多退到它最後一個還能用的站，順位最後一站一直保留。只有訂閱帳號讀得到額度，API 只在被拒時往下換。
- 可用量（使用者 2026-11-26）：Σ份數×max(0, 停用線−週已用) ÷ Σ份數×停用線，合併 Claude 訂閱與能跑 Sol 的 OpenAI 訂閱計算。份數 Max 20x 4、Max 5x 1、OpenAI prolite 1；free 帳號不支援 Sol，不計入；使用者自己暫停的帳號不計。沒設停用線以 100 計。停用線以上保留給使用者本人，不算進長任務可用的額度；100% 表示本週長任務被允許用的額度全部未用。同一 OpenAI 帳號的主欄位與帳號池欄位算一個，取有設停用線的那一欄。兩欄都有 upstreamAccountKey 時以它對應；有一欄讀不到時，以遮罩後的 email 與方案對應（2026-11-27 prolite 主欄位三次讀取有一次沒有這個值，被算成兩個帳號）。
- 換站時在途的工作包照舊做完，新的工作包開新站的子代理，舊站子代理交件後封存；第 1、3、5 次不合格仍交回原子代理重做（使用者 2026-11-26）。
- Claude API 是月額度。API 以 HTTP 400 回報帳戶用量上限時，背景程式以同一對話、同一模型及該次失敗回合的供應商錯誤核對；附 UTC 恢復日就記成「本月已用完」，寫進 `~/.config/long-task-supervisor/anthropic-api-month.json`，這台電腦所有 run 的各角色都跳過 API 到該日（暫存目錄下的測試 run 只記在自己的 run 目錄）。
- 讀額度（使用者 2026-11-25）：背景程式每 30 分鐘及任一帳號重置後 1 分鐘，用 `ocx account list anthropic --quota --refresh --json` 與 `ocx account list openai --quota --refresh --json` 讀一次用量。訂閱帳號每次都先重新整理額度再計算。API key 沒有額度可讀，只在被拒時跳過。背景程式要送換模型通知時，最近一次讀值超過 1 分鐘就先即時再讀一次，依新讀值重新判斷要不要換、換到哪一站（使用者 2026-11-27 第 45 項：「掃模型的排程只是多做一個即時確認剩餘額度」）。重置優惠或原廠自己提前重置，不必等下一次例行讀取就算數。OpenCodex 設定改了也立刻重讀（使用者 2026-11-27）：背景程式每一輪比對帳號標籤、停用線、模型與供應商開關及模型目錄，有變就不等 30 分鐘。帳號憑證更新不算設定改變。
- 換模型前先試打（使用者 2026-11-27 第 44 項）：背景程式選好目標站後，先經 OpenCodex 對該模型送一個極短的串流請求，串流出現 `response.completed` 才算通，只回 HTTP 200 不算。不通就跳過這一站、不切換，下一輪取下一站；錯誤碼寫明額度、儲值或帳號不支援時，照下方對應規則記成被拒。試打結果寫在 `~/.config/long-task-supervisor/route-probe.json`，這台電腦所有 run 共用 1 分鐘，三個工區同時要換時只打一次。每次試打約 2～3 秒、用極少量額度。
- 換模型通知只在對話閒置時送。進行中的回合沿用它開始時的模型，回合中途插進去的通知會被當成回合內的指示（2026-11-27 清票執行主線 14:56 在回合中收到通知，該回合用 Opus 跑到 15:19）。被拒的回合已經結束，所以被拒時會立刻送。
- OpenAI 訂閱留給使用者（使用者 2026-11-25、2026-11-26）：OpenAI 訂閱帳號有設停用線（OpenCodex 的自訂門檻）時，週已用達到停用線就算到線；沒設的，目前的 5 小時、週或月額度只剩 2% 以下才算到線。使用者沒暫停的每個 OpenAI 訂閱帳號都到線時，監督、執行主線與子代理都跳過 OpenAI 訂閱的 GPT 模型，改用下一順位 OpenAI API。只跳過、不暫停帳號（共用帳號除外，見下一項）。停在訂閱 GPT 模型的主線立刻收到換模型通知，下一回合生效。在途的訂閱 Terra 子代理做完目前回合，主線不再發訊給它。讀到的帳號回到線下（重置後 1 分鐘那次讀取）就換回。其他對話（例如使用者的語音）成功使用不算恢復。重新整理後仍讀不到用量的帳號照常可用。
- 停用線依帳號來源處理（使用者 2026-11-26）：OpenCodex 帳號別名（label）含「共用」二字的是跟別人共用的帳號，到停用線就暫停，使用者本人也不能用；其餘是使用者自己的帳號，到停用線不暫停，只在可用量裡算 0，由降級階梯讓長任務往下換，使用者本人照 OpenCodex 機制繼續用。兩個共用帳號 label 相同時，儀表板與紀錄用遮罩後的 email 區分。
- 共用帳號的暫停與恢復（使用者 2026-11-23 Q68 A，2026-11-26 改為只限共用帳號）：OpenCodex 裡有設「自訂門檻」的共用帳號（Claude 與 OpenAI），背景程式在同一次讀用量時發現週已用達到該數字，就用 `ocx account pause` 暫停它，週額度重置後 1 分鐘的那次讀取再 `ocx account resume`。每次讀用量時，背景程式暫停的帳號都用 OpenCodex 當下的門檻重新判斷（使用者 2026-11-26）：門檻調高到週已用以上，或門檻被清掉，就立刻 `ocx account resume` 並刪掉暫停紀錄，之後照新門檻再停。沒設自訂門檻的帳號與使用者自己的帳號不暫停，帳號池的共用門檻仍只是分配偏好。只恢復背景程式自己暫停的帳號（記在 `~/.config/long-task-supervisor/claude-account-stops.json`，兩個任務共用）；使用者自己暫停的帳號不動。使用者在重置前自己恢復被停用的帳號時，到重置前不再暫停。讀不到週用量的帳號不暫停也不恢復。暫停或恢復失敗顯示在儀表板的額度一行。最多晚 30 分鐘才停或才恢復（兩次讀取之間），沒有長任務在跑時沒有程式會暫停或恢復。
- 被拒紀錄依角色分開記。執行端的 Claude 訂閱限速只在額度讀值顯示可再用，或被拒回合錯誤寫明的恢復時間到了才結束；監督在同一訂閱上的成功不算執行端恢復。其他路線在最後一次被拒後安靜 10 分鐘、且之後有成功請求，就提前結束限速。
- 恢復時間：先用被拒回合錯誤訊息寫明的時間；沒有時，用 opencodex 記錄的 Anthropic 帳號最早重置時間；都查不到才用被拒後 5 小時。
- 帳號不支援該模型（使用者 2026-11-25 第 1 題選 A）：OpenCodex 回 HTTP 400 且標記 `model_unavailable`（例如 free 帳號跑 Sol）時，算該路線被拒，第一次就往下換，不等連續 3 次失敗。該順位 5 小時後再試；期間這條路線安靜 10 分鐘、且之後有任一對話成功，就提前換回。這項紀錄寫進 `~/.config/long-task-supervisor/model-unavailable.json`，這台電腦所有 run 的監督與執行端都一起跳過（使用者 2026-11-25 第 4 題選 A）。
- API 儲值用完（使用者 2026-11-27 第 36 項）：OpenCodex 標記 `billing_exhausted`（例如 OpenAI API 回 HTTP 429）時，同一組 API key 上的所有模型（例如 `openai-apikey/` 的 Sol 與 Terra）都算被拒，監督、執行主線與子代理第一次就往下換。紀錄寫進同一個 `model-unavailable.json`，這台電腦所有 run 一起跳過，5 小時後再試；期間其他請求成功也不提前結束，不需要使用者儲值後回來通知。
- 兩個 run 共用同一個監督對話時（例如工區 D 與清票），只由一個背景程式換這個監督的模型（使用者 2026-11-27 第 39 項）：每次讀額度時寫入 `~/.config/long-task-supervisor/supervisor-route-owner.json`，負責的 run 超過 10 分鐘沒更新，另一個 run 才接手。不負責的背景程式不讀監督的被拒紀錄，也不送換模型通知給它。
- 子代理的請求在 OpenCodex 記在主線同一個對話底下。被拒紀錄依「對話＋路線」各看最後一筆，主線的被拒不會被子代理另一個模型的紀錄蓋掉；同一對話同時有多筆被拒時，換模型以主線目前設定的模型那筆為準（使用者 2026-11-25 第 2 題選 A）。
- 切換有沒有生效，看對話紀錄裡切換之後新開的回合實際用哪個模型（rollout 的 `turn_context`）：用新模型就記為生效；仍用換走的那個模型，表示這次切換沒生效，背景程式在對話閒置時重送換模型通知，每個這樣的回合送一次，訊息寫明第幾次與原因，最多 3 次，新站不因此暫停（使用者 2026-11-27 第 44 項，取代第 38 項依失敗請求判斷重送）。經過多久都不用來判斷，請求失敗也不用來判斷：子代理的請求或新回合開始前的壓縮可能還用舊模型，回合失敗會照平台錯誤叫醒監督處理（使用者 2026-11-25 第 1 題選 A）。
- 非額度失敗：同一路線連續 3 次失敗，且第一次到最後一次相隔 60 秒以上（取消的請求不算），暫停該順位 30 分鐘並往下換。監督的這種暫停可以提前結束（2026-11-23 定案）：該路線最後一次失敗或被拒後安靜 10 分鐘、且之後有任一對話的成功請求，背景程式就把監督換回；執行端的照 30 分鐘。OpenCodex 在上游連線中斷、不重送請求時自己回的 429（`upstream_reset_replay_refused`）不代表額度用完：對監督算一次失敗，不算被拒；執行端照舊換下一順位。開源順位 429 冷卻 15 分鐘；OpenRouter 回 402（點數用完）時兩個開源順位一起停用，到錯誤寫明的時間，沒寫就 5 小時後再試。
- 開源暫代監督照常依原契約收件、查證與派工。要結案時照常寫裁決並提交，程式會把結案保留成 `held-acceptance-<事件>.json` 而不生效；Sol、Astra、Opus 或 Fable 回到監督且沒有在處理其他事件時，背景程式把最新一件保留的候選重送，監督在該高階回合逐條核對原件、重寫裁決後才結案。
- 手動選型指定當前使用的模型，包含直接從 Sol 開始，之後仍由背景程式備援。背景程式換過模型之後，使用者又手動改成別的模型（對話設定的時間晚於那次換模型）時，以手動選的模型為新的起點，照順位與降級階梯判斷，不再沿用自己的換模型紀錄（使用者 2026-11-25 選 A；工區 E 13:26 手動改成 Opus，紀錄仍寫 Muse，背景程式因此沒換模型，也沒啟動當時的 Claude 保留）。不在本角色順位上的模型不算手動起點：主線停在開源模型（例如模型自己依已廢止的規則換過去）或 Claude 的其他層級（例如主線停在 Sonnet）、背景程式又沒有它的換模型紀錄時，背景程式以該角色順位第一站為原模型往上換，執行主線與監督都回到 xhigh，之後照同一套規則換回或保留。進行中的回合不會中途換模型，所以這則往上換的通知只在對話閒置時送，同一個回合最多送一次；對話已經設定成上位模型、只等下一回合生效時不送。新回合開始後仍停在原處才會再送，訊息結尾會寫明第幾次通知與重送原因。新 run 的 `modelPolicy` 預設為 `automatic`。只有使用者明確要求固定模型且禁止備援時才用 `locked`。舊 run 的 `modelFallback:false` 視同 locked，經使用者確認恢復自動後才遷移。續接同一任務時繼承既有政策。
- 開源順位：DeepSeek V4.1 Flash 1017 在前、Muse Ember 在後（使用者 2026-11-26），兩款均須在 OpenCodex 目錄可用、鎖定 max 推理且有合格供應商。OpenCodex 每日依加權成本篩選及排序各模型的供應商，對每次請求套用該模型的名單。技能每次選模讀取目前設定，單一合格端點也可使用，某款沒有合格端點時略過該款；兩款都沒有時儀表板會寫明。舊安裝的 Ambient FP4（DeepSeek）或 Google Vertex Global（Muse）單點設定仍適用。每個角色分別保留等待狀態，背景自動重查各順位，較高順位先恢復即續接。送達回執證明訊息到達，對話由目標模型產生輸出才確認接手。
- 平台限制（2026-10-11 實測）：所有 OAuth 帳號都被限速時，App 會照 opencodex 給的最早恢復時間，讓當下的回合原地等待；帶 `model` 的訊息會立即改掉該對話的模型設定，但不會中斷正在等待的回合，新模型從下一個回合起生效，排隊的訊息在回合恢復後照常收進去。App 工具沒有中斷別的對話回合的功能，所以已在等待的回合無法提早改用新模型。
- 子代理：執行端將 `RUN/model-fallback.json` 視為可選限速紀錄，新 run 未遇限速時允許缺檔。在 model-route 輸入加上 `"fallback":"RUN/model-fallback.json"`，會依 `limits`、`ladder.floors` 與 `openaiQuota` 選子代理順位的當下第一站並回傳 `restoreAfter`；`plaintextAgentMessages` 是背景程式即時讀到的 OpenCodex 設定（每次讀額度時用 `ocx agent status --json` 讀執行中的服務，OpenCodex 設定或服務重啟後立刻重讀），`enabled` 為 true 時子代理照順位派；不是 true 而 `executorModel` 是 OpenAI 訂閱模型時只回 `subscriptionMainlineWorker`（Terra 訂閱，basis `subscription-mainline`），它不能用時回 unavailable，由背景程式把主線換到下一站，換站後再派；背景程式讀到設定由開變關時通知監督登記待決帳，恢復時再通知一次；`chain` 列出三個角色目前的順位，`ladder` 是降級階梯的階數、可用量與各角色退到第幾站；`supervisorLimits` 是監督自己的紀錄，子代理不看。候選由 model-route 依 OpenCodex 模型目錄與這份紀錄算出，首次派出後照第 1 點核對實際模型。
