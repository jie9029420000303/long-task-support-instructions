# 承接與更新使用者授權

啟動、壓縮後續接及準備提問前，先讀原始授權與本任務最新的授權補充。壓縮後開頭重現、沒有時間的使用者訊息是歷史，不是新指令；它之後的撤銷與從別的對話轉來的指示可能已被丟掉：授權與撤回以有效契約（`effective-contract`）為準，暫停以 run 狀態檔為準，決策帳只記處理過程。明確的類別授權也是授權，不要求使用者重複逐筆核准；使用者後來明確改變同一限制時，以新指示為準。不能只因動作含 push、merge、登入或權限等字詞，就把已授權工作改列待決。

## 代判授權與候選否決

使用者委託監督選擇視覺／方案或代答續做時，保存逐字授權、適用範圍與禁令，並登記在有效契約的 authorizationUpdates。否決某份候選、要求新版或指出品質缺陷，只否決該候選；沒有明確撤回代判的原話，就不把新版改成必等本人採納。被否決舊稿不能再採用，沿用代判權依最新意圖重做與比對；真正新取捨才問。

啟動、壓縮續接、提問、換候選及接入舊 run 前，讀 effective-contract 與原授權來源；僅載入新版技能不等於承接完成。換 run 續接同一任務時，用 `init` 的 `inheritFrom` 帶著整本修訂帳與待決帳走，不從 effective-contract 重寫新契約（見 runtime「換 run 續接同一任務」）。類別授權持續有效的範圍依使用者原話，不擴大也不無故縮小。

## 保存與交接

- 保存使用者逐字原文、訊息／對話來源、時間、適用專案與操作範圍、條件和禁令。授權表逐項展開屬於代理整理工作，不讓使用者重填同一份表。
- 鎖定的原驗收契約不改寫。後續授權另存來源快照及雜湊，收到時就用 `supervise.cjs amend`（action:"authorization"）登記進有效契約，不等下一個事件：監看在跑時先等 `status` 的 `pending` 與 `inflight` 清空，停 `run-watch.cjs` 父程序與其 `native-watch.cjs` 並確認兩個 PID 都已退出，登記後只重掛一組（步驟見 [runtime](runtime.md)「原契約、使用者修訂與舊 run 接入」）。登記後再以精確跨對話訊息交給原執行主線；執行端讀回後，同步自己的授權表與待決清單。只存成檔案或寫在決策帳的授權不算登記，換 run 續接時帶不走。不得把監督提案當使用者授權。
- 重新盤點已解鎖的工作：已被新授權解決的待決帳項目用 `supervise.cjs pending` 的 `withdraw` 撤下並寫明修訂 ID，按真實依賴執行或補派。授權只限使用者指明的任務／專案；不自行擴到其他帳號、資料、專案或業務用途。

## 跨對話與子代理承接

派工時附最小授權交接：使用者逐字原話、原始對話／訊息定位、操作、目標資源／資料目的地、允許資料範圍、條件及禁令。使用 `supervise.cjs authorization RUN` 取得有效授權與補充的來源位置；只把本包相關的來源交給執行者，不反覆貼全部契約。雜湊只證明檔案未變，不證明文字確實來自人類。

接收者先查原始使用者來源。read_thread 的 includeOutputs:false 仍包含其他歷史項目；呼叫與篩選須放在同一次工具編排內，完成篩選才輸出，不先 text(raw) 或輸出整個 Promise 結果。原文確實涵蓋目前操作、目的地與資料，且無後續撤回時，就承接同一授權；不因來自另一對話或上層轉派而要求本人在每個子對話重說。代理說「已授權」不足以證明；來源不明時請原監督提供精確來源，不自行擴權。已核對的來源與範圍保存於工作包，只有操作、來源或限制變更才重核。

需要查原始對話時，沿用下列最小擷取方式（`wantedMessageIds` 由交接來源提供）；本頁沒找到就以 `page.nextCursor` 讀下一頁，只輸出匹配的原始使用者訊息與分頁資訊。找不到、訊息截斷或來源不是 userMessage 時不以代理摘要替代；回原來源補齊後再判斷。

```js
const raw = await tools.mcp__codex_app__read_thread({
  threadId, turnLimit: 10, includeOutputs: false,
  ...(cursor ? {cursor} : {})
});
if (raw.isError) throw new Error(JSON.stringify(raw));
const data = JSON.parse(raw.content.find(x => x.type === 'text').text);
const selected = (data.turns || []).flatMap(turn => (turn.items || [])
  .filter(item => item.type === 'userMessage' && wantedMessageIds.includes(item.id))
  .map(item => ({threadId: data.thread.id, turnId: turn.id, messageId: item.id,
    text: (item.content || []).filter(part => part.type === 'text')
      .map(part => part.text).join('\n')})));
text({selected, page: data.page});
```

區分「模型尚未核對來源」與「實際工具拒絕」。前者完成來源核對後依已有授權執行；後者保存工具名稱、拒絕原文、受阻操作與已核對來源，一次交回原監督處理。不能自行聲稱服務端、額度或權限問題，也不重試相同被拒 payload、拆掉必要內容假裝完成，或換工具迴避拒絕。只有實際工具要求且原授權無法滿足的確認才交使用者，明說限制來源；不承諾技能可以改變平台審查。

## Git 的持續授權

若使用者明確授權「本專案 Git 除刪除外直接做，保留每步紀錄與可回復版本」，原執行主線就串連該範圍內所需的 commit、push、合併、tag、Release 等步驟，不再逐次詢問。每步保存操作前後分支／提交、目標、測試與結果；可能改寫歷史前先保留可用的回復參照及未提交成果。不得刪除版本控制歷史（分支、tag、提交、改寫前的回復參照）；測試中間產物（含已整合的隔離 worktree）依[測試中間產物的刪除](#測試中間產物的刪除)；費用及其他明示禁令照舊。

這種明示的持續授權可以涵蓋同一任務後续修正版，不能自行縮成只准當前一個 commit；單次候選授權也不可自行擴成永久授權。技術子代理仍不操作 Git，由執行主線整合、驗證並留存紀錄。新的授權不免除原驗收與測試要求。

## 測試中間產物的刪除

長任務屬開發或測試階段，最終只驗交付成果。使用者 2026-10-13 定調：「過程中可以把測試中間產物做必要刪除而不是完全不能刪，對於最終結果還原的歷程紀錄不要刪就好，方便交付後驗收排查」（transcript 6b9544fc／uuid bb49594a）。這是每個長任務的預設類別授權：不列待決、不逐筆問，也不必在每個 run 另登記修訂。

- 可刪：本任務自己產生的測試中間產物，例如暫存容器與資料卷、測試票與測試紀錄（含測試訊息）、草稿與暫存檔、已被新版取代的中間輸出，以及變更已整合進候選版（或確定不採用）、不再作證據的隔離 worktree（刪前把 `git status --short` 與 `git diff` 存進 `evidence/`）。只在必要時刪：占用磁碟或測試名額、干擾後續測試或判讀，或收尾清場；封存、結案、中和等可逆做法能滿足需要時，刪除就不是必要。
- 先記再刪：刪前在刪除清冊記一列（執行端在 sidecar 目錄、監督在 run 目錄的 `deletions.md`）：項目與可核對的識別、產生者（工作包或步驟）、為何屬中間產物，以及在驗收結果帳、`evidence/` 與決策帳搜尋該識別的結果；刪後讀回確認已不存在，結果補進同一列。同一道指令內自建自清的暫存不算產物；受測程式與測試腳本原設計的建立與清除照常執行，不為此改成不刪。
- 誰來刪：執行端刪自己與子代理產生的；監督只刪自己建的驗證副本，執行端的產物請執行端刪。子代理可刪自己在本工作包建立、位於 `[工作區]` path 或自己 scratch 內的檔案（`evidence/` 與測試結果除外），在回報列出，主線收回時抄進清冊；別人建立的產物（其他工作包、主線、先前的 run）只刪工作包 `[資料副作用]` 逐項列明、主線派工前已記入清冊的項目。
- 一律不刪：還原與排查最終結果所需的歷程——決策帳、驗收證據、測試結果、產物與刪除清冊、版本控制歷史（分支、tag、提交與改寫前的回復參照），以及識別值出現在驗收結果帳、`evidence/` 或決策帳中的測試物件（票號、Case／Job ID、容器名）。
- 不屬本授權：不是本任務產生的東西（正式資料、使用者檔案、仍在使用的權杖或憑證、備份來源），刪除照上層確認規則，只停該動作；新增與修改的界線見[先實際使用已授權的登入](#先實際使用已授權的登入)。
- 禁令的範圍：「不准刪東西」「只准依需求新增」「刪除須逐項確認」這類泛用禁令只保護本任務沒建立的既有資源與資料，不涵蓋測試中間產物。只有使用者原話點名特定資源或資料，或明說包含測試中間產物的禁令，才優先於本預設；之後又改同一限制時，以新原話為準。

## 先實際使用已授權的登入

已授權使用瀏覽器登入時，先依平台瀏覽器工具路由，另開自己的分頁取用使用者既有登入態或已存登入，必要時在正常登入頁完成登入與既有權限內的免費操作。不要先要求使用者重新登入、再提供已可讀取的權限或搬運憑證；一個工具讀不到，不等於使用者沒有登入，須先依路由換用可取用既有登入的工具查證。不得把密碼、cookie或權杖抄進對話、工作包或Git。

先核對使用者對新增、修改與刪除的界線；若只准依需求新增、禁止刪除，就保留既有資源。涉及新費用時只停付費動作並說明金額及用途，其他免費且已授權工作繼續。確實遇到必須由本人完成的驗證、平台強制確認或新敏感權限，照實說明已嘗試路徑與具體阻塞；不以「需要登入」籠統停掉整個任務，也不繞過平台保護。範圍不含新敏感權限時不得自行擴權。

若執行端宣稱「跨對話授權無效」「所有表單都要逐次確認」或「出現密碼欄只能本人處理」，監督須核對適用規則原文與具體動作，區分平台強制限制、專案舊規則及代理推論。普通登入不自動等於新建敏感存取；可安全使用的既有登入或自動填入先依平台規則實查，不讀出秘密。確有平台要求當下確認時如實標明來源與受阻動作，不偽裝授權、不換工具規避；不能以執行者自述代替查核。既有訂閱與新增費用也須分開核實，不因價目表列有月費就推定本次操作會新增收費。

## 平台自動審查擋下操作時

執行對話的權限模式是「自動審查」時，平台審查只採信使用者本人在該對話送出的訊息；監督轉交的授權不算數，跨對話只會附上最近三則使用者原話，其中太長的會被省略（2026-10-11 實證：A 的 Git 與 Docker 被擋 3 次，GDB 的 Jira 讀取被擋 1 次）。所以：

- 不要給使用者授權文字要他轉貼，也不請他到執行對話打字。正解是請他在該對話的權限選單切成「完全存取」，只切選單；這件事登記在待決帳（kind `user_action`），依 SKILL「少打擾使用者」第 4 點的時機和其他未決項一起說一次，附對話標題。權限模式是使用者的安全設定，監督不自行切換。
- 他說切好後，監督用 `answer` 記下原話，再用原生跨對話傳訊送一則附新 `LONG_TASK_DELIVERY` 的續接，請執行端重跑被擋的操作；背景程式從那個回合的設定讀到完全存取才發 `permission_changed`。
- 2026-10-11 實測：只切選單時，背景送來的回合仍是自動審查（選單只在本人從該對話輸入框送出訊息時套用）。上述續接能否套用新模式尚待實測；續接後的回合仍是自動審查（沒有 `permission_changed`、同一操作再被拒）時，用 `reopen` 在待決帳該項寫明這個事實，受阻操作維持停止、其他工作照常推進，不改請使用者到執行對話打字。
- 先找已授權範圍內較安全的做法，繼續推進不受影響的工作。
- 背景程式發 `permission_changed` 後，續接已交代重跑就 observe，否則讓執行端重跑被擋的操作；待決帳的權限項還開著就撤下。
