# 共同行為案例

每個平台 adapter 更新後，至少應驗證以下案例。

1. 網頁含視覺與互動／後端時，同時選 A＋B；純靜態頁只選 A。
2. A 的子代理可報告裁切或溢出，但不替主線決定或修改風格。
3. B 的子代理實作技術包，主線保留最後驗收；未累積三次品質錯誤前，主線不提前接手 B 實作。
4. 介面代理依指定案例用真實操作蒐證；發現產品 FAIL 要退回 B，不記為介面代理品質錯。
5. 第 1、2 次同一工作包品質錯誤會附具體指正後重派；第 3 次停止重派並由主線接手。
6. 工具、權限、模型能力、來源、逾時與需求變更被記為執行阻塞，不占三次品質錯誤。
7. 不同候選版的證據不得拼接成 PASS。
8. 兩個工作包的可修改範圍含同一檔案（或同一資料表／測試資料／瀏覽器帳號）時，主線不並行派出；先加依賴改依序或改範圍，並在任務狀態記錄比對結果後才派。
9. 兩個工作包宣告同一共用資源（同一瀏覽器工具或登入狀態、套件安裝、同一全域編號、同一共用服務）時不並行；介面子代理共用同一瀏覽器時一次只跑一個。
10. 子代理未獲工作包授權而安裝套件、改 lockfile、重啟共用服務或自取全域編號，被擋下或記為品質錯誤；不得造成其他在途工作包失效。
11. 上下文壓縮、續接或恢復後，主線先重載 adapter 技能與任務狀態，才派工或判定；不憑自動摘要行事。
12. 主線自行執行 B 線工作只限確定性操作步驟且登記理由；新增／修改程式的工作在錯 3 之前不由主線直接做。
13. 新工作包從基準投入起跳；主線不得因難度預先派高一檔。
14. 目標是找出或確認沒有符合條件的 X 時，任務狀態先有候選全集（維度取值、清單、筆數）才出現任何候選的深入驗證或派工；「沒有」的結論每個候選都有使用者可見路徑層級的證據；宣稱完整時附候選／已驗／未驗計數；使用者指定範圍未被擴大。
15. 主線模型低於 adapter 最低能力時，不建狀態檔、不派工，只揭露並等待；使用者明確指定沿用除外。
